# 关系树

> **文档版本：0.5.0-dev**
>
> 这份文档讲清楚「关系树」这个模块：为什么家谱、组织架构、军团编制能共用一套画布、
> 「变体」是什么、关系词表怎么做到换模板不改数据、卡片为什么严格贴着网格走、
> 以及为什么它要单独开一个全屏页面。
> 目标是让刚学会 Python、还没写过 Web 应用的人，也能顺着读下来。

如果你还不清楚「文档」「卡片」是什么，先看 [工作区与文档树](03-工作区与文档树.md)
与 [卡片·类型·属性](04-卡片·类型·属性.md)。

---

## 1. 一句话理解关系树

关系树是**一种文档**（`Document` 里 `document_type = "familyTree"`，常量 `DOC_TREE`），
用来画「谁和谁是什么关系」：家谱、公司组织架构、军团编制、皇室联姻……
形式上都是**一堆卡片 + 卡片之间的连线**。

它跟时间线一样，也是「二十个工具之一」，但因为画树是**全屏的活**，
所以除了工作区面板，还单独开了一个全屏页面 `/relationship`（见 §6）。

---

## 2. 三层结构：变体 → 人物 → 关系

一棵关系树在数据库里由三张表搭成，层级分明：

```
Document（关系树文档）
   └── TreeVariant（变体：一套关系视角）
          ├── TreeNode（人物 或 备注）   ← 画布上的卡片
          └── TreeEdge（关系）           ← 卡片之间的连线
```

### 2.1 TreeVariant：同一批人的多套视角

```python
# apps/graph/models.py —— TreeVariant
name  = models.CharField("名称", max_length=60, default="Main")
kind  = models.CharField("模板", max_length=12, choices=TREE_KINDS, default=TREE_FAMILY)
edge_labels = models.JSONField("关系名", default=dict)   # 逐个改过的关系名
settings    = models.JSONField("设置", default=dict)     # 朝向、关系清单、setup 标记
```

**为什么需要「变体」**：同一批人在不同情境下关系不一样。比如「官方的王室家谱」
和「野史里的私生子传闻」是同一群人、两张图。用变体承载这种「多套视角」，
比让用户建两个文档更贴切——毕竟人物是共享的。

`fork()` 方法用来复制一份变体：节点全部照搬，**边要重新映射到新节点的 id 上**
（因为新节点是新插入的行，id 变了）。这是所有「深拷贝一张图」时的通用处理。

### 2.2 TreeNode：一个人，或一张便签

```python
# apps/graph/models.py —— TreeNode
NODE_PERSON = "person"   # 人物：参与关系连线
NODE_NOTE   = "note"     # 备注：画布上的便签，不参与连线

card      = models.ForeignKey(Document, null=True, ...)   # 可以吸附到一张卡片（也可以没有）
name      = models.CharField("名称", max_length=120, default="新成员")
generation = models.IntegerField("世代", default=0)       # 第几代（排 y 用）
x = models.FloatField("横向位置", default=0.0)            # 像素
y = models.FloatField("纵向位置", default=0.0)
```

关键设计：**人物可以没有卡片，也可以吸附到一张卡片**。
- 只想快速画个家谱：直接写名字即可，不必先建卡片。
- 想让这个人物有完整设定：把它绑到一张卡片上（`card` 字段），
  点它就能跳到卡片页（`to_payload()` 里顺手带了 `card_slug`，只读画布点人可以直接跳站点页）。

`kind` 区分「人物」和「备注」：备注就是画布上随手写的一段话，不连任何线。

### 2.3 TreeEdge：关系

```python
# apps/graph/models.py —— TreeEdge
kind  = models.CharField("关系", max_length=32, choices=TREE_EDGE_KINDS, default="parent")
label = models.CharField("自定义关系名", max_length=40, ...)   # 空 = 用模板/默认叫法
style = models.CharField("线型", max_length=10, ...)          # "" / dashed / dotted

class Meta:
    unique_together = [("variant", "source", "target", "kind")]   # 同一条关系不重复
```

`unique_together` 保证「A 是 B 的父母」这同一条边不会因为重复点击而存两次。

## 3. 关系词表与模板：换模板不改数据

### 3.1 一套 kind，多种叫法

看一个场景：家谱里那条从父亲指向孩子的边，`kind` 是 `"child"`（子女）；
到了公司模板里，同样这条「上级→下级」的边应该叫「下属」；军事模板里叫「百夫长」。

如果为每个模板都发明一套 `kind`，那么**换模板就得改所有已存的边**。所以这里
做了一次关键抽象：**落库的 `kind` 是中性、通用的**，界面上的「叫法」由模板覆盖。

```python
# apps/world/relations.py —— 规范关系表（kind 是落库值，字符串是中性叫法）
RELATION_KINDS = [
    (REL_PARENT, "父母"),
    (REL_CHILD, "子女"),
    (REL_SPOUSE, "伴侣"),
    ...
    (REL_CUSTOM, "自定义"),
]
```

于是**一条边换模板不用改数据**：边还是那条 `kind="child"` 的边，只是显示出来的名字
从「子女」变成「下属」。

### 3.2 线型：一眼区分血缘与非血缘

```python
# apps/world/relations.py
RELATION_STYLES = {
    REL_EX: "dashed",            # 前任
    REL_HALF_SIBLING: "dashed",  # 同父异母/同母异父
    REL_ADOPTIVE: "dashed",      # 收养
    REL_STEP: "dashed",          # 继
}
```

前任、收养、继这种「非婚生直系」的关系统一画**虚线**，
一眼就能和实线画的血缘直系分开。这是**信息可视化**里很省事的技巧：
用线型区分「性质」，用位置区分「层级」。

### 3.3 起步模板

新建关系树时，左侧会列出一批模板（`TREE_TEMPLATES`），每个模板自带一份现成的关系清单
和一张示例图：

| 模板 id | 名字 | 关系主轴 |
| --- | --- | --- |
| `family` | 家庭 | 父母 / 子女 / 伴侣 / 前任 / 兄弟姐妹 / 收养 / 继 |
| `corporate` | 公司 | 经理 / 下属 / 合伙人 / 同事 / 导师 / 代理主管 |
| `military` | 军事 | 军团长 / 百夫长 / 副将 / 同袍 / 护民官 |
| `royal` | 皇家宫廷 | 领主 / 封臣 / 配偶 / 庶出 / 继承人 / 摄政 |
| `blank` | 从空白开始 | 不带任何预设，关系名字由你随手定 |

**为什么要预置关系清单**：像「父母 / 子女」这种到处都是的关系，如果每次都要用户
从零命名，工具就变得很烦。预置一份，用户删掉不要的即可。而「从空白开始」保证了
**想完全自定义的人也有出口**——这是「预设」类功能必须留的后门。

## 4. 网格：卡片为什么严格贴着线走

关系树画布是「贴网格」的，这一节解释它怎么工作。

### 4.1 坐标分两套：格数与像素

```python
# apps/world/relations.py
GRID = 28              # 一个网格的边长（像素）
CARD_COLS = 5          # 一张卡片宽 5 格
CARD_ROWS = 8          # 一张卡片高 8 格
GAP_X = 3              # 列与列之间空 3 格（当走线通道）
GAP_Y = 4
COL_STEP = CARD_COLS + GAP_X   # 8：相邻两列的格距
ROW_STEP = CARD_ROWS + GAP_Y   # 12：相邻两行的格距
```

约定：
- **卡片宽高都是整数格**（5×8 格），所以只要把卡片左上角放在整数格上，
  它的**边框就天然落在网格线上**——不需要额外对齐算法。
- **关系线不受网格约束**，可以任意走。
- 模板示意数据里写的是「第几列第几行卡片」，用 `slot()` 换算成格坐标，
  避免在数据里写魔数：

```python
# apps/world/relations.py —— slot
def slot(col, row):
    return {"col": col * COL_STEP, "row": row * ROW_STEP}
```

### 4.2 落库要乘成像素

模板的示意图给的是**格数**，但落库要换成**像素**（`TreeNode.x/y` 一直是像素，
因为工作区里那个老编辑器按像素读写，两边得对得上）：

```python
# apps/world/relationship.py —— _seed_demo
x = float(item["col"] * GRID),
y = float(item["row"] * GRID),
```

乘完正好是 `GRID` 的整数倍，卡片边框因此严格贴在网格线上。

### 4.3 两套行号：格坐标 vs 第几行

模板节点同时给出两种坐标（见 `relations.py` 的 `_node()`）：
- `col` / `row`：**格坐标**，画布落点用；
- `col_index` / `row_index`：**第几列 / 第几行**，喂给 `TreeNode.generation`。

**为什么区分**：工作区里的简版渲染器是**按世代排 y** 的（不是按像素）。
如果喂给它格坐标（值会是 0、8、16…），它会把节点拉到一片空白的地方去。
所以世代用「第几行卡片」这个整数，而不是格坐标。这类「同一份数据、两种消费者」
的坑，靠明确的字段命名来避免。

## 5. 关系清单：每个树自己的那一列

### 5.1 关系清单存在变体的 settings 里

一棵树「可用的关系」是它自己的一份清单，存在 `TreeVariant.settings["relations"]`
里，形如 `[{kind, label, style, enabled}, ...]`。

**为什么要存清单，而不是直接用模板那份**：用户可以在界面上改名字、加自定义关系。
如果每次都从模板现取，用户改的东西就丢了。判断「有没有存过」看的是
**有没有这个键**，而不是「是不是空」：

```python
# apps/graph/models.py —— TreeVariant.stored_relations
stored = (self.settings or {}).get("relations")
if not isinstance(stored, list):
    # 没存过 → 用模板自带那份（老数据因此不需要迁移）
    stored = [... template_relations(self.kind) ...]
```

**关键点**：用户把关系全删光也是他的选择，不能因为清单变成空列表就又给他弹回模板那套。
所以判据是「有没有 `relations` 这个键」，不是「列表长不长」。

### 5.2 关系的名字：四级优先级

同一条 `kind` 的边，显示出来的名字是谁定的？`label_for()` 定了一条清晰的优先链：

```python
# apps/graph/models.py —— TreeVariant.label_for
1. edge_labels[kind]                    # 这棵树里逐个改过的名字
2. stored_relations 里那条的 label       # 关系清单里那条的名字
3. TREE_EDGE_LABELS / RELATION_LABELS    # 模板默认 / 中性叫法
4. kind 本身                             # 最后的兜底
```

**为什么需要这么多层**：用户在界面上把「军团长」改成别的名字，新连出来的线
也应该印新名字——不然改了等于没改。所以「改过的名字」优先级最高。

### 5.3 setup 标记：选过模板了吗

```python
# apps/graph/models.py —— TreeVariant.is_setup
return bool((self.settings or {}).get("setup"))
```

新建一棵关系树时它先是「没配过」的状态（关系清单、画布落点都还没有），
这时打开应该**先给模板选择**，而不是一片空画布。
选完（哪怕选的是「从空白开始」）就打上这个标记——用户明确要了空白，
就不该每次都再问一遍。

## 6. 为什么单独开一个全屏页

工作区里的关系树是「二十个工具之一」，塞在标签页 + 并排面板里，画布只占中间一条。
而画树这件事本身是**全屏的活**：一大片网格、右键就长人、从加号拖出去就连线。

所以先把这件事做成一个能独立跑通的页面 `/relationship`（`apps/world/relationship.py`），
再收进工作区当其中一个面板。页面支持嵌入：

| 查询参数 | 作用 |
| --- | --- |
| `?doc=<id>` | 直接进某棵树的编辑区；不带就停在模板选择那一步 |
| `?embed=1` | 被工作区面板 / 发布站点用 iframe 嵌进去：去掉外壳留白与圆角。**默认只读** |
| `?readonly=0` | 嵌入态下显式要求可编辑 |
| `?theme=paper\|light\|dark` | 指定明暗；不指定时跟随世界主题 |

明暗规则跟工作区统一（`world.theme.mode`，非 light 即 dark），
这样从工作区点「全屏编辑」跳过来不会有「闪一下换了皮肤」的割裂感。

另一个细节：请求里带的 `doc` id **原样保留**，即使文档打不开也**不悄悄归零**——
这样前端能说「这篇不在了」，而不是把人丢回模板选择（那看着像「我的树变成了新建向导」）。

## 7. 接口一览

工作区里那套（人物与关系的增删改）挂在 `/api/world/` 下：

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| `GET` | `/trees/<doc_id>` | 整棵树的完整状态（变体列表 + 当前变体的节点/关系） |
| `GET`/`POST` | `/trees/<doc_id>/variants` | 变体列表 / 新建变体（给 `fork_from` 就复制） |
| `GET`/`PUT`/`DELETE` | `/tree-variants/<id>` | 单个变体：读 / 改（改名、模板、关系叫法）/ 删 |
| `GET`/`POST` | `/tree-variants/<id>/nodes` | 人物节点列表 / 新建 |
| `GET`/`POST` | `/tree-variants/<id>/edges` | 关系列表 / 新建 |
| `GET`/`PUT`/`DELETE` | `/tree-nodes/<id>` | 单个节点 |
| `POST` | `/tree-nodes/<id>/card` | 把这个人物吸附到一张卡片 |
| `GET`/`PUT`/`DELETE` | `/tree-edges/<id>` | 单条关系 |

独立页自己那套（模板目录、新建、编辑区状态、关系清单）挂在 `/api/world/relationship/` 下：

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| `GET` | `/relationship/templates` | 模板目录（含示意图与网格参数） |
| `GET`/`POST` | `/relationship/trees` | 已有关系树列表 / 按模板新建一棵（可顺手放示例人物） |
| `GET` | `/relationship/trees/<doc_id>` | 编辑区完整状态 |
| `GET`/`PUT` | `/relationship/trees/<doc_id>/relations` | 关系清单的读取 / 整份替换 |
| `POST` | `/relationship/trees/<doc_id>/setup` | 给一棵已存在的空树选模板 |

> 人物与关系的增删改**复用**工作区那套 `tree-nodes` / `tree-edges` 接口——
> 同一个数据模型，没必要为独立页再抄一遍。

---

## 8. 一句话小结

- **变体**让同一批人有多套关系视角；**节点**可以是人物也可以是便签；**边**用中性的 `kind` 落库。
- **模板只改叫法不改数据**：换模板时 `kind` 不动，界面上的名字变。
- 卡片宽高取整数格，落点乘 `GRID` 就是像素，**边框因此天然贴网格**。
- 关系名字有四级优先级，**用户改过的名字优先级最高**。
- 画树是全屏的活，所以它**单独有一个页面**，再以只读/可编辑两种形态嵌回工作区与站点。
