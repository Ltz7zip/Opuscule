# 架构总览

> **文档版本：0.4.0-dev**
>
> 这份文档回答三个问题：**这个项目长什么样？它由哪些部分组成？一个请求进来后走了哪条路？**
> 它按"先看全貌、再拆零件"的顺序写，面向刚学会 Python、还没写过 Web 应用的人。
>
> 一句话概括：**同一个 Django 进程里，跑着两个界面——给作者的"工作区"和给读者的"只读站点"。**

如果你只想先跑起来，看 [README.md](../README.md) 的「快速开始」。

## 1. 这是什么项目

Opuscule（世界观共建工作台）把「写虚构世界设定」这件事变成**结构化的工作**：

- 把设定写成一张张**卡片**（人物、地点、组织……）；
- 把事件排进**时间线**，可以带自己的历法和纪元；
- 把人和人连成**关系树**（家谱、组织架构、军团编制）；
- 把地点标在**地图**上；
- 最后**一键发布**成一个只读的、能到处点进去的维基站点。

它的设计目标只有两条：

1. **作者在工作区不觉得工具挡路**——随手记，随手连，结构自己长出来。
2. **读者在站点里感觉在翻一本世界档案**——干净、有氛围、能顺着链接跳进去。

## 2. 两个面孔（工作区 / 只读站点）

程序是"一个后端、两张脸"。两张脸跑在**同一个进程**里，共用**同一份数据**，区别只在于**谁能看、能干什么**：

| 面孔 | 地址 | 谁能看 | 干什么 | 返回什么 |
| --- | --- | --- | --- | --- |
| **工作区** | `/world` | 作者（登录后可写） | 建卡、写正文、排时间线、画关系树、标地图、发布 | 页面外壳 + 一堆 JSON 接口 |
| **只读站点** | `/s/<短码>/` | 读者（公开 / 需密码） | 像翻维基一样浏览已经发布的内容 | 服务端渲染的 HTML |

它们的关系可以这样理解：

```
        ┌──────────────────────── 同一份数据（SQLite） ────────────────────────┐
        │                                                                      │
   工作区 /world  ──(写)──▶  Document / Card / TimelineEvent / …  ◀──(读)── 只读站点 /s/<短码>/
   （作者随手改）              数据库里唯一的一份真相                （读者只看已发布的）
```

> **比喻**：把工作区想成作者的**书房**——稿纸乱一点没关系，改起来要快；
> 把只读站点想成出版社印出来的**成书**——干净、固定、给外人看。
> 书房里可以随时改，改完点一次"发布"，成书才会更新。

工作区里几乎所有的"动作"都是通过 `/api/world/*` 下的 JSON 接口完成的，
页面本身只是一个空壳，靠前端 JavaScript 把数据填进去。
只读站点则相反：它由服务器**直接把 HTML 拼好**发给读者（渲染），不需要作者那一套编辑器。

## 3. 技术栈一览与取舍

| 层 | 选择 | 为什么这么选 |
| --- | --- | --- |
| 语言 | Python 3.12 或更高 | 生态成熟、代码可读性高 |
| Web 框架 | Django 6.1.1 | 自带 ORM、数据库迁移、admin 后台、CSRF 防护、会话——一个依赖顶起一整套后端骨架 |
| 数据库 | SQLite（单文件） | 零配置；一个人写设定的数据量，一个文件足够；**备份就是拷一个文件** |
| 前端 | 原生 HTML / CSS / JavaScript，**无构建** | 不引入 Node、npm、打包器；改一行刷新即见；降低上手门槛 |
| 生产服务器 | gunicorn | 与 Django 的标准搭配 |
| 依赖总数 | 只有 Django + gunicorn + django-otp | 依赖越少，能坏的地方越少 |

这套取舍用一句话表示：**用「Django 提供后端骨架 + 原生前端提供界面」，换掉一切构建链与微服务**，
让整个项目是一个**能被一个人读完并改懂**的整体。

三个"为什么"值得单独说清楚：

- **为什么用 SQLite 而不是 PostgreSQL？**
  SQLite 把整库存在一个文件里，不需要单独启动数据库服务。对"一个人、一台机器、写设定"这个场景，
  省掉的运维成本远大于它带来的限制。代价是并发写入较弱，但本项目的写入量根本不会触及这个上限。
- **为什么不用 React / Vue 这类框架？**
  它们通常需要一套构建工具链（`npm install`、打包、热更新）。无构建意味着新同学 clone 下来，
  不用装 Node 就能改前端，也不会遇到"构建产物和源码不一致"的经典困惑。
- **为什么只依赖 Django + gunicorn + django-otp？**
  每多一个第三方库，就多一处升级风险、多一处安全漏洞面。把依赖压到最小，
  等于把"能坏的地方"也压到最小。（`django-otp` 只用于账号的两步验证，是唯一的额外依赖。）

## 4. 为什么有六个 Django app

一个 Django 项目可以包含多个 **app**（应用）。每个 app 是一组相关的"模型 + 视图 + 路由"。

> **什么是 Django app？** 你可以把它想成一个"功能模块"或"插件"。项目配置（settings、总路由）
> 负责把多个 app 组装在一起，每个 app 自己管好自己那摊事。

Opuscule 有六个 app：

```
worldbuilding_timeline/      ← 项目配置（settings.py / urls.py）
├── apps/                    ← 本项目自己的应用都收在这个包里
│   ├── world/               ← 【主应用】世界 / 类型与属性 / 成员 / 治理 + 工作区与只读站点的视图
│   ├── documents/           ← 文档 / 卡片 / 时间线 / 日历 / 纪元 / 在线状态 / 版本
│   ├── graph/               ← 关系树（TreeVariant / TreeNode / TreeEdge）
│   ├── maps/                ← 经典地图（MapLayer / MapMarker）
│   ├── publishing/          ← 发布记录（PublishLog）
│   └── timeline/            ← 【次应用】一条经典横向时间轴
```

### 4.1 `world`（主应用）

承载产品的**骨架与治理概念**：世界、类型与属性、成员与邀请、治理（举报 / 封禁）；
同时它仍是工作区与只读站点的**实现**——`/world`、`/api/world/*`、`/s/<短码>/` 的视图都收在它的 `views/` 里。

### 4.2 `timeline`（次应用）

它只做一件事：提供那条**经典横向时间轴**——一个纯粹的"横向拖拽时间点 / 时间段"编辑器。
它有两个入口：

- `/legacy`：独立成一页访问；
- `/world/timeline/<doc_id>`：被工作区用**同源 iframe** 嵌进来使用（嵌在"时间线"文档里）。

它自己有一套很扁平的存储模型：所有条目都塞在一张 `TimelineItem` 表里，
时间直接用"浮点年"表示（比如 1642.5 表示第 1642 年的年中）。

### 4.3 `documents` / `graph` / `maps` / `publishing`（内容模型）

这四个 app 只装**模型**（视图与路由仍集中在 `world` / `timeline`），按主题各管一摊：

- `documents`：文档树上的内容——`Document`（树上唯一的节点类型）、`Card`、`Era`、`Calendar`、
  `TimelineEvent`，外加协作所需的 `Presence`（在线状态）与 `DocumentVersion`（版本历史）。
- `graph`：关系树——`TreeVariant` / `TreeNode` / `TreeEdge`。
- `maps`：经典地图——`MapLayer` / `MapMarker`。
- `publishing`：发布记录——`PublishLog`。

### 4.4 为什么分成六个 app

**`world` 和 `timeline` 为什么分开？** 因为这两块的**「时间模型」根本不一样**：

| | `world` 的时间 | `timeline` 的时间 |
| --- | --- | --- |
| 一个世界有几条时间轴 | 多世界、多历法、多纪元 | 一条固定横轴 |
| 时间怎么存 | 年 / 月 / 日 / 时四级精度，挂在事件上 | 一个浮点年（`start` / `end`） |
| 视野如何保存 | 存在时间线文档的 `settings` 里 | 一个叫 `TimelineView` 的单例 |

如果把它们塞进一个 app，"时间"这个概念就会长出**两套彼此打架的实现**，
以后每改一处都要担心碰坏另一处。分成两个 app，各自管好自己的时间模型，
再由一层很薄的**适配层**让工作区能内嵌经典时间轴，两边互不污染。

**`documents` / `graph` / `maps` / `publishing` 为什么从 `world` 里拆出来？**
它们原本全摊在一个 `world/models.py` 里。文件越长，模型之间的**导入依赖**越容易缠成环——
「文档」要用到「世界」，「图谱」「地图」「发布」又要用到「文档」，牵一发动全身。
按主题拆成独立 app 后，每个 app 的模型自成一体，跨 app 的引用方向变成**单向**的
（`world` 常量与世界模型在下，`documents` 居中，`graph` / `maps` / `publishing` 在上），
**依赖环被解开**；而且每个 app 只导出自己那摊模型，读代码时能更快定位。

> 拆 app 只动**代码组织**，不动**数据**：所有表名都用 `Meta.db_table` 钉在原处（仍是 `world_*`），
> 数据库里一行都不会搬；视图、接口、URL 也完全没变。

### 4.5 适配层 `apps/world/classic.py` 的作用

`apps/world/classic.py` 是一座**翻译桥**。当你在工作区打开一条"时间线"文档，
实际上打开的是经典编辑器本体，但经典编辑器"以为"自己在跟自己的接口说话。

适配层做两件事：

1. **骗过编辑器的请求**：经典编辑器写死了要调用 `/api/timeline`、`/api/items` 等地址。
   嵌进工作区时，页面会在编辑器脚本之前注入一小段 fetch 适配层，把这些地址
   指向 `world` 里的等价接口。
2. **翻译两种数据形态**：编辑器用"浮点年"，`world` 用"年/月/日/时四级精度"。
   两者之间靠一个换算公式来回转：

   ```
   浮点年 = 年 + (月-1)/12 + (日-1)/360 + 时/8640
   ```

   所以你在经典轴上把某个事件拖到哪一年，`world` 的库里就存哪一年。

| 经典编辑器里的东西 | 翻译成 `world` 里的东西 |
| --- | --- |
| `kind="event"` + 浮点年 | `TimelineEvent`（带四级精度） |
| `kind="era"` + 起止年 | `Era` + 文档 `settings` 里的时间跨度 |
| `cards: [{title, url, …}]` | 事件的 `linked_cards`（按名字对齐到卡片） |
| `view: {start, end}` | 文档 `settings` 里的视野起止 |

> **比喻**：适配层像一个**电源转换插头**。里面的电器（经典编辑器）没变，
> 外面墙上的插座（`world` 的数据）也没变，中间加一个插头，两边就能接上。

## 6. 一次请求发生了什么

这是理解整个后端**最重要的一段**。以工作区里**保存一张卡片**为例：

```
浏览器
  │  POST /api/world/documents/12          ← 带 session cookie 和 CSRF token
  ▼
Django 请求管道（中间件按 settings.MIDDLEWARE 的顺序从外到内穿过）
  │
  ├─ ① 内置中间件
  │     SecurityMiddleware → Session → Common → CSRF → Authentication → Messages → XFrameOptions
  │     （会话就绪、CSRF 校验、认出当前登录用户是谁）
  │
  ├─ ② ActiveWorldMiddleware              ← apps/world/middleware.py
  │     解析"当前世界"并写进 contextvar
  │     （优先级：会话里选定的 → 自己的第一个世界 → 兜底第一个世界）
  │
  ├─ ③ EditPermissionMiddleware           ← apps/world/middleware.py
  │     这是写操作吗（POST/PUT/PATCH/DELETE）？是 → 拦下来判权限
  │       没账号 → 403；没登录 → 401；登录了但没权限 → 403；通过 → 放行
  │
  ├─ ④ 维护模式 MaintenanceMiddleware      ← apps/world/maintenance.py
  │     只有在 OPUSCULE_MAINTENANCE=1 时才拦，平时等于不存在
  │
  ├─ ⑤ 路由 → worldbuilding_timeline/urls.py → apps/world/urls.py → apps/world/views/ 的某个函数
  │
  └─ ⑥ 视图里：用 current_world() 取当前世界 → 读写模型 → 返回 JSON
```

### 6.1 为什么把"当前世界"放进 contextvar

`current_world()` 在代码里有大量调用点（全站约 87 处）。如果每个视图都要
从 `request` 里把"当前世界"一路当参数传下去，函数签名会变得又长又啰嗦。

于是 `ActiveWorldMiddleware` 在请求一开始就把世界解析好，存进一个
**`contextvars.ContextVar`**——一个"当前请求内随处可读"的变量；请求结束时再复位。

> **什么是 contextvar？** 可以把它想成一个**贴在请求身上的便签**。
> 请求一进来，中间件在便签上写下"当前世界 = 世界 #3"；之后任何代码问"当前是哪个世界"，
> 读一下便签就知道；请求结束时把便签撕掉。

**为什么用 contextvar，而不是普通全局变量？**
因为 contextvar **对每个请求是隔离的**。假如服务器同时处理两个请求——
A 在"世界 3"、B 在"世界 7"——用全局变量会互相覆盖；用 contextvar，
A 读到的永远是 3、B 读到的永远是 7，互不干扰。

```python
# 中间件里的三行核心逻辑（简化示意）
world = permissions.resolve_active_world(request)   # 解析当前世界
token = permissions.set_active_world(world)         # 写进 contextvar
try:
    return self.get_response(request)
finally:
    permissions.reset_active_world(token)           # 无论如何都复位
```

### 6.2 为什么权限中间件要排在世界作用域之后

因为"**有没有编辑权限**"这件事，**依赖于"是哪个世界"**。

同一个人，在 A 世界里可能是作者（能改），在 B 世界里可能只是个访客（只能看）。
所以必须先知道"当前世界是谁"（②），才能判断"他能不能改这个世界"（③）。

**顺序不能颠倒**：如果先判权限、后解析世界，权限中间件就不知道该对着哪个世界判。

### 6.3 权限中间件里的三道判断

`EditPermissionMiddleware` 只对两件事同时成立的请求生效：

1. 是**写方法**（POST / PUT / PATCH / DELETE）；
2. 打在一个**受保护路径**上（`/api/world/`、`/api/items`、`/api/view`）。

满足后，它按顺序问三个问题：

| 顺序 | 问题 | 不通过时的反应 |
| --- | --- | --- |
| 1 | 数据库里一个用户都没有？ | 放行（首次安装例外，方便第一个注册的人把世界建起来） |
| 2 | 没登录？ | 返回 `401 {"need_login": true}`（前端据此弹登录框） |
| 3 | 登录了，但在这个世界不能编辑？ | 返回 `403` |

还有一批路径被列入**白名单**（`permissions.OPEN_WRITE_PREFIXES`），直接跳过守门：

| 白名单 | 为什么放行 |
| --- | --- |
| `/api/world/auth/` | 登录 / 注册发生在"还没有身份"的时候 |
| `/api/world/presence` | 在线心跳，只读成员也要能发，好显示"谁在线" |
| `/api/world/worlds` | 新建 / 切换世界发生在"还没有属于自己世界"的时候，先放行到视图里再校验 |

## 7. 分层规则

项目刻意保持**清晰的分层**，好处是"一个功能出问题"时，你能立刻知道该翻哪个文件：

| 层 | 代表文件 | 只做什么 | 不做什么 |
| --- | --- | --- | --- |
| **存储层** | `models.py` | 定义字段、负责存与取，附几个"最贴身的读取方法" | 不做业务编排 |
| **编排层** | `views.py` | 解析请求 → 调用模型与算法模块 → 返回 JSON | 不写复杂的纯计算 |
| **算法层** | `normalize.py` / `autolink.py` / `graph.py` / `geo.py` / `publish.py` … | **纯函数式工具**：给定输入，算出输出 | 不碰 `request`，方便单独测试 |
| **横切层** | `permissions.py` / `middleware.py` | 拦在**所有**请求前面，统一处理权限与作用域 | 不关心某个具体功能 |

> **比喻**：分层就像一家餐厅——**存储层**是仓库（只负责存取食材），
> **编排层**是前台（接单、调度），**算法层**是厨师（把食材做成菜），
> **横切层**是门口保安（每个进门的人都要先过他那关）。

这里"算法模块是纯函数"很关键：它只吃参数、吐结果，不碰网络请求，
所以你可以在命令行里直接调用它、也方便写单元测试。

## 8. 总路由表概览

项目总路由在 `worldbuilding_timeline/urls.py`，它决定"什么网址交给谁处理"。
按下表从上到下理解即可：

| 路由前缀 | 交给谁 | 干什么 |
| --- | --- | --- |
| `admin/` | Django 自带 admin | 数据库后台管理界面 |
| `api/world/` | `apps.world.urls` | 工作区的**全部 JSON 接口**（`/api/world/state`、`/api/world/documents` …） |
| `world` | `apps.world.views.workspace` | 工作区**页面外壳**（一个几乎空的 HTML，靠 JS 填内容） |
| `sw.js` | `apps.world.views.service_worker` | Service Worker 脚本（必须从根路径发，离线缓存才生效） |
| `relationship` | `apps.world.relationship.relationship_page` | 关系树**独立页**（模版选择 + 网格画布编辑器） |
| `map` | `apps.world.mapdoc` | 地图**独立页**（`/map` → `/map/2d`，共用同一份图层与标注数据） |
| `w`、`w/timeline/<id>` | `RedirectView` | 旧地址的**跳转**（保留是为了别让已发出去的链接失效） |
| `s/` | `apps.world.site_urls` | **只读站点**（`/s/<短码>/` 首页 / 文档页 / 纪元页 / 搜索 / RSS / 解锁） |
| ``（其余） | `apps.timeline.urls` | 经典横向时间轴：`/legacy` 页面 + `/api/timeline`、`/api/items` 等接口 |
| `login` / `register` / `logout` | `apps.world.views` | 账号的**表单式页面**（浏览器原生提交） |
| `maintenance` | `apps.world.maintenance` | 维护页 |
| ``（根路径） | `RedirectView` | 访问网站首页时 302 跳到 `/world` |

此外还有两个全局错误处理：

- `handler404` → `apps.timeline.views.page_not_found`（非 `/api/` 的 404 给一页"信号丢失"）；
- `handler500` → `apps.timeline.views.server_error`（给一页"重试"）。

> 更细的接口清单（每个 `/api/world/*` 的方法与参数）见 [12-接口参考.md](12-接口参考.md)。

## 9. 一张 ASCII 架构图

```
        ┌──────────────────────────── 浏览器 ─────────────────────────────┐
        │                                                                │
        │   /world             /s/<短码>/              /legacy            │
        │  （工作区）           （只读站点）            （经典横向时间轴）   │
        └──────┬───────────────────┬───────────────────────┬─────────────┘
               │                   │                       │
        JSON over /api/world   HTML（服务端渲染）      JSON over /api
               │                   │                       │
               ▼                   ▼                       ▼
   ┌──────────────────────────── Django 进程 ────────────────────────────┐
   │                                                                     │
   │  中间件链：                                                        │
   │    内置（会话 / CSRF / 认证） → ActiveWorldMiddleware（当前世界）    │
   │    → EditPermissionMiddleware（写守门人） → MaintenanceMiddleware   │
   │                                                                     │
   │  world 应用                                    timeline 应用         │
   │  ┌─────────────────────────┐                  ┌───────────────────┐  │
   │  │ views.py（编排请求）     │                  │ views.py          │  │
   │  │ algorithms：            │                  │ models.py         │  │
   │  │  normalize / autolink   │◀── classic.py ───│ TimelineItem      │  │
   │  │  graph / geo / publish  │    适配层（桥）   │ TimelineView      │  │
   │  │ models：World →         │                  └───────────────────┘  │
   │  │  Document → Card/…      │                                         │
   │  └───────────┬─────────────┘                                         │
   │              │ ORM                                                   │
   └──────────────┼──────────────────────────────────────────────────────┘
                  ▼
            SQLite（单文件 db.sqlite3）
```

**顺着箭头读一遍**：浏览器发出请求 → 穿过中间件链（先认身份、再定世界、再判权限）
→ 交给某个 app 的视图 → 视图调用模型和算法模块 → 通过 ORM 读写 SQLite → 返回 JSON 或 HTML。
