# 部署与运维

> **文档版本：0.4.0-dev**
>
> 这一篇讲**怎么把它放到一台服务器上，并让它长期稳定地跑**：
> 环境要求、每一个环境变量管什么、为什么某些配置必须那样写、上线步骤、
> 备份，以及出问题时怎么排查。
>
> 面向**第一次自己部署 Web 应用**的读者。凡是「为什么」的地方都会写清楚，
> 因为部署的坑大多不是「不会敲命令」，而是「不知道那条命令为什么要这么写」。

---

## 1. 环境要求与依赖

| 项 | 要求 |
| --- | --- |
| 操作系统 | 任意能跑 Python 的 Linux（示例按 Debian/Ubuntu 系写） |
| Python | **3.12 或更高** |
| 数据库 | SQLite（单文件，零配置，随项目走） |
| 依赖 | 只有两个：**Django 6.1.1** 与 **gunicorn 23.0.0** |
| 前端 | 原生 HTML/CSS/JS，**无需 Node、无需构建** |
| 反向代理 | nginx（处理静态资源与 TLS） |
| 进程守护 | systemd |

依赖清单（`requirements.txt`）：

```
Django==6.1.1
gunicorn==23.0.0
```

> 依赖越少，能坏的地方越少。没有 Node、没有打包器、没有消息队列，
> 整个系统就是「一个 Python 进程 + 一个 SQLite 文件 + 一堆静态文件」。

## 2. 目录约定

本文的示例路径沿用部署样例里的约定：

| 路径 | 含义 |
| --- | --- |
| `/srv/opuscule` | 项目根目录（`WorkingDirectory`） |
| `/srv/opuscule/.venv` | 虚拟环境 |
| `/srv/opuscule/db.sqlite3` | 数据库文件 |
| `/srv/opuscule/staticfiles` | `collectstatic` 收集出来的静态资源 |
| `/srv/opuscule/media` | 用户上传的媒体（地图底图等） |
| `/srv/opuscule/.cache` | 文件缓存（登录 / 注册限流计数，见 §4.8） |

这些名字都能改，但要**四处保持一致**：systemd 单元、nginx 配置、
备份脚本、环境变量文件。改的时候一起改。

## 3. 环境变量逐个讲

所有环境变量都由 [worldbuilding_timeline/settings.py](../worldbuilding_timeline/settings.py)
读取，样例见 [deploy/opuscule.env.example](../deploy/opuscule.env.example)。

| 变量 | 默认值 | 作用 |
| --- | --- | --- |
| `DJANGO_SECRET_KEY` | 本地兜底密钥 | **生产必须换成随机字符串** |
| `DJANGO_DEBUG` | `1`（开） | 是否调试模式；**对外服务必须为 `0`** |
| `DJANGO_ALLOWED_HOSTS` | `127.0.0.1,localhost,[::1]` | 允许访问的域名，逗号分隔 |
| `DJANGO_CSRF_TRUSTED_ORIGINS` | 空 | CSRF 信任来源，逗号分隔，带 `https://` |
| `OPUSCULE_MAINTENANCE` | 未设（关） | 置 `1` 全站进入维护模式 |
| `OPUSCULE_MAINTENANCE_ETA` | 空（显示「15 分钟后」） | 维护页上那句「预计多久恢复」 |
| `OPUSCULE_ADMIN_PATH` | `admin` | 后台路径；**对外服务应改成猜不到的一串** |
| `OPUSCULE_LOG_FILE` | 空（只打 stdout） | 另存一份应用日志到文件（按大小自动轮转） |
| `OPUSCULE_BUILD` | 空（不显示） | CI 注入的构建号，展示在 `/meta` 与页脚 |
| `OPUSCULE_OTP_ISSUER` | `Opuscule` | 认证器 App 里显示的组织名（后台两步验证） |

### 3.1 `DJANGO_SECRET_KEY`

Django 用它签名会话 cookie、CSRF token 等。**它是整套认证安全的地基：
泄露了，别人就能伪造登录状态。**

代码里有一个兜底值，是为了让本地开发「装上就能跑」。
**部署时必须覆盖它**，生成一串足够长的随机串：

```bash
python3 -c "import secrets; print(secrets.token_urlsafe(64))"
```

把输出填进 `/etc/opuscule.env` 的 `DJANGO_SECRET_KEY=`。

**兜底密钥会「拒绝启动」**：如果 `DJANGO_DEBUG=0`（对外服务）却还在用代码里
那个公开的兜底密钥，[settings.py](../worldbuilding_timeline/settings.py) 会在**启动那一刻
直接抛 `ImproperlyConfigured`、把进程拦下来**，而不是带着一个人人可伪造的密钥
悄悄上线。看到这个报错，说明 `DJANGO_SECRET_KEY` 没配好，按上面生成一串填进去即可。

### 3.2 `DJANGO_DEBUG`

```python
DEBUG = os.environ.get('DJANGO_DEBUG', '1') == '1'
```

默认是**开**（`'1'`），因为本地开发希望有调试页、有热加载。
但**对外服务必须设成 `0`**：调试模式出错时会显示源码片段、配置、SQL——
这是严重的信息泄露。

> 记法：**默认值是给开发用的，生产要显式覆盖**。凡是这类「默认宽松」的开关，
> 上线清单里都要核一遍。

### 3.3 `DJANGO_ALLOWED_HOSTS`

只填**域名**（不带协议、不带端口），逗号分隔：

```
DJANGO_ALLOWED_HOSTS=example.com,www.example.com
```

Django 用 `Host` 头跟这个列表比对，防止「Host 头攻击」（攻击者伪造 Host
骗过基于域名的安全判断）。填错会导致访问直接返回 400。

### 3.4 `DJANGO_CSRF_TRUSTED_ORIGINS`

**浏览器原生表单**（登录、注册页面）从 HTTPS 域名提交时，
Django 的 CSRF 校验需要你显式声明「信任这个来源」。写**带协议**的完整来源：

```
DJANGO_CSRF_TRUSTED_ORIGINS=https://example.com,https://www.example.com
```

漏了它的典型症状：**在页面上登录，怎么点都提示 CSRF 失败**。

### 3.5 `OPUSCULE_MAINTENANCE` 与 `OPUSCULE_MAINTENANCE_ETA`

见 [§5 维护模式](#5-维护模式)。

### 3.6 `OPUSCULE_ADMIN_PATH`

后台（Django admin）的地址前缀。默认 `admin`——**这只是方便本地开发与测试**，
对外服务**必须**改成一串猜不到的值：

```
OPUSCULE_ADMIN_PATH=ops-7f3a9c
```

改完后台就从 `/admin/` 挪到了 `/ops-7f3a9c/`。为什么这样做：`/admin/` 是
Django 的**出厂默认路径**，任何扫描器、自动化脚本第一件事就是去戳它。
路径改了，扫描器按默认地址敲门只会得到 404，**少一层被顺手发现的机会**。

> 这不是「保密依赖」式的安全——后台的真正门锁仍是 [§4.11](#411-后台入口改路径--超级管理员--两步验证)
> 那条「只有 `is_superuser` 才能进」。改路径只是**减少被发现面**，
> 两者叠加才稳妥。

配套改动（改路径后会自动跟随，无需另外配置）：

- **robots.txt** 会按这个值禁掉后台路径（见 [§4.12](#412-robotstxt)）；
- **维护模式白名单**也用这个值，维护期间运维照样进得去后台
  （见 [§5](#5-维护模式)）。

### 3.7 `OPUSCULE_LOG_FILE`

默认不设，应用日志只打 stdout/stderr，交给 systemd → journald（见 [§8.6](#86-日志与监控)）。
想让日志**同时**落一份到文件，设成某个可写路径：

```
OPUSCULE_LOG_FILE=/var/log/opuscule/app.log
```

这时会挂一个按大小轮转的文件处理器：**单文件 10 MB、最多留 5 份历史**，
文件轮转由程序自己管（**不需要**额外的 `logrotate`）。记得给运行用户该目录的写权限。
细节与告警方式见 [§8.6](#86-日志与监控)。

### 3.8 `OPUSCULE_BUILD`

CI 注入的**构建号**，同一个 `X.Y.Z` 下每次构建递增；不设则不显示。
仓库里的 [.github/workflows/ci.yml](../.github/workflows/ci.yml) 用
`OPUSCULE_BUILD=${{ github.run_number }}` 注入，把一次部署对应到唯一一次 CI 运行。

它只影响**展示**：`/meta` 接口与页脚会从 `Opuscule 0.5.0 · Dev` 变成
`Opuscule 0.5.0 · Dev · build 42`，机器可读的完整串变成 `0.5.0-dev+build.42`。
派生逻辑在 [apps/world/version.py](../apps/world/version.py)，**改号只改 `settings.py` 一处**。

### 3.9 `OPUSCULE_OTP_ISSUER`

后台两步验证（TOTP）里，认证器 App 显示的组织名——它写进 `otpauth://` 串的
issuer 标签（见 [§4.11](#411-后台入口改路径--超级管理员--两步验证)）。默认
`Opuscule`，上线建议改成站点自己的名字：

```
OPUSCULE_OTP_ISSUER=Opuscule
```

不设时认证器里只显示用户名，**容易跟别的站混在一起、认不出哪个码是哪个站**。
它只影响录入设备时的显示名，**改了不会让已录入的设备失效**（密钥没动）。

## 4. 关键设置逐个讲「为什么」

这些不是「随便填的」，每一条背后都有原因。

### 4.1 `SECURE_PROXY_SSL_HEADER`

```python
SECURE_PROXY_SSL_HEADER = ('HTTP_X_FORWARDED_PROTO', 'https')
```

请求到 Django 时，其实是 **nginx 转发过来的 HTTP**（gunicorn 只监听本机）。
告诉 Django：「如果代理在 `X-Forwarded-Proto` 头里写了 `https`，
就把这个请求当成 HTTPS」。

**为什么需要它？** 因为 Django 要据此判断 `request.is_secure()`、
要不要给 cookie 加 `Secure` 标记、CSRF 校验怎么走。如果它以为「这是 HTTP」，
而实际用户走的是 HTTPS，安全判断就会全错。

> **前提（很重要）**：gunicorn 只监听 `127.0.0.1`，外部请求一律经过代理。
> **千万别**把 8000 端口直接暴露到公网——否则攻击者可以自己伪造
> `X-Forwarded-Proto: https` 来骗 Django。

### 4.2 `X_FRAME_OPTIONS = 'SAMEORIGIN'`

```python
X_FRAME_OPTIONS = 'SAMEORIGIN'
```

Django 默认是 `DENY`：**任何页面都不许被 iframe 嵌**。
但这个系统里，工作区用**同源 iframe** 嵌了那条经典横向时间轴
（`/world/timeline/<doc_id>`）。

- `DENY` 会连自家页面都拦掉，iframe 里一片空白；
- `SAMEORIGIN` 只允许**同源**页面嵌，既能让自家 iframe 工作，
  又挡住了外部网站把本站嵌进它的页面里（防点击劫持）。

### 4.3 语言与时区

```python
LANGUAGE_CODE = 'zh-hans'
TIME_ZONE = 'Asia/Shanghai'
USE_I18N = True
USE_TZ = True
```

- `LANGUAGE_CODE`：界面语言（简体中文）。
- `TIME_ZONE`：显示与本地化用的时区（东八区）。
- `USE_TZ = True`：**数据库里存的是 UTC**，展示时按 `TIME_ZONE` 转换。
  这是推荐做法——不管服务器在哪个时区，数据始终一致。

### 4.4 静态与媒体

```python
STATIC_URL = '/static/'
STATICFILES_DIRS = [BASE_DIR / 'static']   # 开发时直接从这里读
STATIC_ROOT = BASE_DIR / 'staticfiles'     # collectstatic 的收集目录

MEDIA_URL = '/media/'
MEDIA_ROOT = BASE_DIR / 'media'            # 用户上传的文件
```

- **静态资源**（CSS/JS/SVG）打包在仓库里，开发时按目录直发，
  部署时用 `collectstatic` 汇总到 `STATIC_ROOT`，交给 nginx 直接发。
- **媒体文件**（上传的地图底图等）是运行时长出来的，放在 `MEDIA_ROOT`。

**上传上限：**

```python
FILE_UPLOAD_MAX_MEMORY_SIZE = 25 * 1024 * 1024    # 25 MB
DATA_UPLOAD_MAX_MEMORY_SIZE = 26 * 1024 * 1024    # 26 MB
```

单文件上限 **25 MB**（上传界面会提示「图片超过 25 MB，建议先压缩」），
整个请求体上限 26 MB（留 1 MB 余量给表单其它字段）。
nginx 侧对应地设了 `client_max_body_size 30m`（再多留一点给请求头等开销）。

> 三个数要**层层递增**：应用单文件 25 MB < 请求体 26 MB < nginx 30 MB。
> 如果 nginx 设得比应用小，请求会在代理层就被拒（返回 413），
> 用户看到的错误信息还不一定清楚。

### 4.5 会话

```python
SESSION_COOKIE_AGE = 60 * 60 * 24 * 14    # 14 天
SESSION_SAVE_EVERY_REQUEST = False
```

- 会话有效期 **14 天**；前端会在到期前提醒「续期」
  （调 `/api/world/auth/renew`）。
- `SESSION_SAVE_EVERY_REQUEST = False`：不给每个请求都重写会话表，
  减少无谓的数据库写入。

**非调试环境下加密 cookie：**

```python
if not DEBUG:
    SESSION_COOKIE_SECURE = True
    CSRF_COOKIE_SECURE = True
```

正式环境走 HTTPS，这两个 cookie 只允许加密传输，防止被中间人窃取。
用 `not DEBUG` 门控，所以本地 http 开发不受影响。
（同一个 `if not DEBUG:` 块里还有**强制 HTTPS 跳转**和 **HSTS**，见
[§4.9](#49-生产开关强制-https-与-hsts)。）

> ⚠️ **一个常见坑**：开启 `Secure` 后，**纯 HTTP 下登录会拿不到 cookie**
> （浏览器拒绝在明文连接上存 Secure cookie）。
> 所以「验证登录」这一步要放在**配好 HTTPS 之后**；签发证书前想自测，
> 可以临时 `DJANGO_DEBUG=1`。

### 4.6 `SW_ENABLED`（Service Worker）

```python
SW_ENABLED = not DEBUG
```

[static/sw.js](../static/sw.js) 是 PWA 的离线缓存脚本，它只做三件事：

| 请求类型 | 策略 | 为什么 |
| --- | --- | --- |
| 带 `?v=` 的静态资源 | **cache-first** | URL 天然版本化，内容永不改变，缓存最安全 |
| HTML 导航 | **network-first** | 模板是服务端渲染的，缓存的旧 HTML 配新 JS 会错位 |
| `/api/*` | **不碰** | 实时数据，缓存会让「看到的东西」不可信 |

升级时靠缓存名前缀里的版本号（`opus-static-v1`）在 `activate` 阶段清掉旧缓存。

**默认只在非调试环境注册**：开发机上开着它，你可能看到的是缓存里的旧代码，
调试会变得不可信。想临时试，加 `?sw=1`；想关，加 `?nosw=1`
（见 [apps/world/context.py](../apps/world/context.py) 的 `static_version`）。

### 4.7 模板加载器（一个容易踩的坑）

```python
'APP_DIRS': not DEBUG,
# DEBUG 时显式给出不带缓存的 loader：
'loaders': [...] if DEBUG else {}
```

Django 6.x 的模板引擎会**无条件**把 loader 套进带缓存的包装里。
后果是：**改完 `.html` 模板，不重启进程就永远看不到效果**（CSS/JS 是静态文件，
照常生效，只有模板被冻住）。

所以：**开发模式**走不带缓存的 loader，改模板刷新即见；
**部署模式**（`DEBUG=False`）仍走默认的带缓存路径——性能更好。
运维时记住：**生产环境改了模板必须重启服务。**

### 4.8 缓存（限流计数）

```python
CACHES = {
    'default': {
        'BACKEND': 'django.core.cache.backends.filebased.FileBasedCache',
        'LOCATION': BASE_DIR / '.cache',
    }
}
```

登录 / 注册的**频率限制**（[apps/world/views/accounts.py](../apps/world/views/accounts.py) 的 `_login_throttle` /
`_register_throttle`）把「试了多少次」记在缓存里。Django 默认的 `LocMemCache` 是
**每进程一份**，而生产是 gunicorn 多 worker（见 [§6.5](#65-起-gunicornsystemd)），
各进程各算各的，等于把阈值悄悄放大到 worker 数倍。换成**文件缓存**后，
同一台机器上的所有 worker 共享同一份计数。

- `.cache/` 是运行时产物，已进 `.gitignore`，**不要**纳入备份或版本控制；
- 目录会在首次写入时自动创建，确保运行用户（如 `opuscule`）对项目根目录有写权限；
- 缓存丢了不影响正确性——只是计数清零、限流窗口重新开始。

### 4.9 生产开关：强制 HTTPS 与 HSTS

`if not DEBUG:` 块里除了 `Secure` cookie，还有三条专门管「逼你走 HTTPS」的设置：

```python
SECURE_SSL_REDIRECT = True
SECURE_HSTS_SECONDS = 31536000          # 1 年
SECURE_HSTS_INCLUDE_SUBDOMAINS = True
SECURE_HSTS_PRELOAD = True
```

- **`SECURE_SSL_REDIRECT`**：任何 `http://` 请求一律 301 跳到 `https://`。
  它靠 [§4.1](#41-secure_proxy_ssl_header) 的 `SECURE_PROXY_SSL_HEADER`
  从 nginx 的 `X-Forwarded-Proto` 判出原始协议——**两者必须一起配**，
  否则 Django 在反代后只看得到 `http`，会「跳到自己」陷入死循环。
- **HSTS（`SECURE_HSTS_SECONDS`）**：在响应头里告诉浏览器「以后一年内，
  访问本站一律只用 https，别再试 http」。一旦浏览器记下，到期前用 http 访问
  会被它**自己拦下**——所以在**确认全站能上 https 之后**再开。
- `INCLUDE_SUBDOMAINS` 让 HSTS 也覆盖子域名。
- `PRELOAD` 只是往响应头里加一个 `preload` 指令，声明「本域名有资格进浏览器的
  预加载列表」；真正被写进 Chrome/Firefox 等厂商的内置列表，需要你**另外去
  [hstspreload.org](https://hstspreload.org/) 手动提交**，这一步本项目不做。

> ⚠️ **HSTS 是「一旦开启就很难回头」的开关**：浏览器记住之后，你就算把
> 设置关掉，用户那边在一年内仍会被强制 https。所以**先确保证书正常、https 全通**，
> 再让这套设置上线。

### 4.10 `manage.py check --deploy`（上线前自检）

Django 自带一个「上线体检」命令，会逐条检查上面这些安全开关配没配：

```bash
cd /srv/opuscule
DJANGO_DEBUG=0 DJANGO_SECRET_KEY=… .venv/bin/python manage.py check --deploy
```

干净通过时输出：

```
System check identified no issues (2 silenced).
```

- **两条 silenced** 是「故意如此」、已在 `SILENCED_SYSTEM_CHECKS` 里显式静音的：
  - `security.W019`：我们故意让 `X_FRAME_OPTIONS=SAMEORIGIN`（见
    [§4.2](#42-x_frame_options--sameorigin)），方便工作区同源 iframe 内嵌时间轴；
  - `mail.E001`：项目目前**不发送任何邮件**，控制台邮件后端只是占位；
    等做密码重置、接入真实邮件后端后，把这条从静音列表里删掉。
- 静音列表只关这两条，**别顺手多关**——静音一条检查，等于关掉一个提醒。

### 4.11 后台入口：改路径 + 超级管理员 + 两步验证

Django admin 是「直接操作数据库」的入口，**泄露即高危**。这里做了三层收口：

**第一层——改路径**（[§3.6](#36-opuscule_admin_path)）。默认 `/admin/` 是出厂地址，
扫描器必戳；部署时用 `OPUSCULE_ADMIN_PATH` 改成一串猜不到的值，
让默认地址直接 404。

**第二层——只认超级管理员**。后台站点的每个视图都过自定义站点
[apps/world/admin.py](../apps/world/admin.py) 的 `has_permission`：

```python
def has_permission(self, request):
    return bool(
        request.user.is_active
        and request.user.is_superuser
        and request.user.is_verified()   # 第三步，见下
    )
```

这意味着 **`is_staff=True` 也进不去**（Django 默认 `is_staff` 就能进 admin）。
本项目只需要「站长一个人」能用后台，普通成员、甚至被误勾了 `is_staff`
的账号都不该拿到这份权限。后台站点通过
[apps/world/adminconfig.py](../apps/world/adminconfig.py) 的 `OpusculeAdminConfig.default_site`
挂成默认站点，`python manage.py createsuperuser` 出来的账号天然满足条件。

**第三层——两步验证（口令 + TOTP）**。即便口令泄露，光有口令也进不去后台。
实现用的是第三方库 [`django-otp`](https://github.com/django-otp/django-otp)：
后台站点继承 `OTPAdminSite`，上面那句 `is_verified()` 就是「第二步过了没」的开关，
由中间件 `django_otp.middleware.OTPMiddleware` 按会话里的设备记录填上
（**必须紧跟在 `AuthenticationMiddleware` 之后**）。三个相关设置都在
[settings.py](../worldbuilding_timeline/settings.py)：
`INSTALLED_APPS` 里的 `django_otp` + `otp_totp` + `otp_static`、中间件、
以及认证器显示名 [`OTP_TOTP_ISSUER`](#39-opuscule_otp_issuer)。

> **为什么破例引第三方库**：本项目其余部分坚持「零第三方依赖」，但两因素
> 认证涉及时钟漂移、重放窗口、限流、密钥熵这些容易翻车的细节，自己搓不划算，
> 交给成熟的库更稳妥。这是**目前唯一的第三方依赖**（见
> [requirements.txt](../requirements.txt)）。

#### 录入设备：`manage.py otp_enroll`

后台要求「已通过两步验证」才能进，而新账号还没有任何设备——
「要进后台才能建设备、要建设备才能进后台」是个**死结**。所以设备录入走命令行
[apps/world/management/commands/otp_enroll.py](../apps/world/management/commands/otp_enroll.py)：

```bash
# 录入（或重新查看）TOTP 设备：把打印的 otpauth:// 串或密钥填进认证器 App
python manage.py otp_enroll root

# 换手机／密钥疑似泄露：丢掉旧设备、换一个全新密钥（旧密钥随之作废）
python manage.py otp_enroll root --reset

# 顺带打印 5 个一次性备用码（认证器丢了用它救急）
python manage.py otp_enroll root --backup-codes 5
```

命令会打印 `otpauth://` 串、Base32 密钥，以及（如果加了 `--backup-codes`）
若干个**一次性备用码**。录入后打开后台登录页，除口令外再填认证器 App 显示的
6 位验证码，即可进入。

> 打印出的密钥等同于登录凭据——**别贴进聊天记录 / 工单**，
> 用完即从屏幕和终端历史里清掉。

本项目**不安装二维码生成库**（`qrcode`/`segno`），所以 `otp_enroll` 只在终端
给文本串与密钥，用认证器 App 的「手动输入」录入；后台设备页里那个「显示二维码」
的链接在缺库时返回 503，属正常现象，不影响登录。

#### 备用码与恢复流程

- **认证器丢了、但记得备用码**：登录页的 `OTP Device` 下拉里选
  `Backup Code`（`otp_static` 设备），填任意一个**未用过**的备用码即可进后台；
  每个码**只能用一次**，用掉即作废。
- **认证器丢了、也没备用码**：用 `python manage.py otp_enroll root --reset`
  命令行重录一台新设备（旧密钥作废），再用新设备登录。
- **忘了这回事／换了机器**：`otp_enroll` 不带 `--reset` 会**复用并重新打印**
  已有设备的串，不必重置。

命令行 **`createsuperuser` 创建的账号仍需先 `otp_enroll` 录一次设备**，
否则进不了后台——这既是安全要求，也是这套流程唯一的「手工初始化」步骤。

### 4.12 `robots.txt`

项目从根路径发一份 [robots.txt](../apps/world/views/site.py)（视图 `robots_txt`，
路由在 [urls.py](../worldbuilding_timeline/urls.py)）。它的目标是
**约束「正规搜索引擎」**、把该藏的藏起来、该露的露出来：

```
User-agent: *
Disallow: /api/        # 全部 JSON 接口：登录后的私有空间
Disallow: /world       # 工作区页面
Disallow: /media/      # 上传文件（本就鉴权）
Disallow: /<后台路径>/  # 后台入口，跟随 OPUSCULE_ADMIN_PATH
Disallow: /login /register /reset …
Allow: /s/             # 公开发布出来的只读世界站点
Allow: /explore        # 公开世界展示页
```

**要说清楚的一点**：`robots.txt` 只对**守规矩的爬虫**有效——
它是一份「君子协定」。真正的恶意采集**根本不会读它**，拦这种靠的是
限流 + 登录墙（以及将来上 CDN）。所以这份文件的定位是：
让搜索引擎**好好收录公开世界**、**别去碰私有区域**，顺带少让自动化扫描器
顺着默认地址摸到后台。

## 5. 维护模式

维护模式实现在 [apps/world/maintenance.py](../apps/world/maintenance.py)，
由中间件 `MaintenanceMiddleware` 把关（挂在中间件链的最末尾）。

**怎么开启**：把环境变量设成 `1` 并**重启服务**（环境变量在进程启动时读取）。

```bash
# /etc/opuscule.env
OPUSCULE_MAINTENANCE=1
OPUSCULE_MAINTENANCE_ETA=预计 15 分钟后恢复
```

**生效逻辑**（`__call__`）：

```
开着维护开关，且请求路径不在白名单里？
  → 回维护页（HTTP 503 + Retry-After: 900）
否则
  → 正常处理
```

**白名单**（维护期间仍可访问），由 `allowed_prefixes()` 动态给出：

```python
def allowed_prefixes() -> tuple[str, ...]:
    return ("/static/", "/maintenance", f"/{settings.ADMIN_URL_PATH}/", "/media/")
```

**为什么要放行这几个？** 因为如果连静态资源都拦了，
维护页自己的 CSS/JS/图片都加载不出来，页面会变成一堆裸文字；
放行后台，是为了让运维还能进去处理事情——**它跟着
`OPUSCULE_ADMIN_PATH` 走**（[§3.6](#36-opuscule_admin_path)），
所以改了后台路径，维护期间也照样进得去，不会被硬编码的 `/admin/` 挡在门外。
`/media/` 只是"不拦在维护门前"，进来后仍要走 [§6.6](#66-配-nginx-反代) 说的
鉴权视图——维护期并不会让未公开的图变成可直链。

**为什么用 503 而不是 500？** 503（Service Unavailable）语义就是
「服务暂时不可用，稍后重试」。配合 `Retry-After: 900`（900 秒），
搜索引擎和客户端就知道这是**临时**状态，不会把页面从索引里删掉。

维护页 `/maintenance` 也可以直接访问查看效果（它本身不需要开关）。

## 6. 上线步骤

下面是「从零到能访问」的顺序。每一步都给出**为什么在这个位置**。

### 6.1 准备代码与环境

```bash
# 1. 建一个专用的系统用户（不要用 root 跑服务）
sudo useradd --system --group --home /srv/opuscule opuscule

# 2. 代码放到 /srv/opuscule，建虚拟环境装依赖
cd /srv/opuscule
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
```

### 6.2 配环境变量

```bash
sudo cp deploy/opuscule.env.example /etc/opuscule.env
sudo chmod 600 /etc/opuscule.env     # 里面有密钥，别让别人读到
```

逐项改成真实值（重点是 `DJANGO_SECRET_KEY`、`DJANGO_DEBUG=0`、
`DJANGO_ALLOWED_HOSTS`、`DJANGO_CSRF_TRUSTED_ORIGINS`）。

### 6.3 建库（跑迁移）

```bash
.venv/bin/python manage.py migrate
```

**迁移 = 把模型定义同步到数据库表结构**。第一次是建表；以后每次改了模型，
也要重跑一次。**跳过它的典型症状：接口报「no such table」或字段不存在。**

### 6.4 收集静态资源

```bash
.venv/bin/python manage.py collectstatic --noinput
```

它把各处的静态文件拷到 `STATIC_ROOT`（`/srv/opuscule/staticfiles`）。
之所以要这一步：**开发时 Django 能自己发静态文件，生产时不该让它发**
（慢、且不该由应用进程处理），而是交给 nginx 直接读磁盘。

### 6.5 起 gunicorn（systemd）

安装服务单元（[deploy/opuscule.service](../deploy/opuscule.service)）：

```bash
sudo cp deploy/opuscule.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now opuscule
systemctl status opuscule          # 看状态
journalctl -u opuscule -f          # 看日志
```

单元里最关键的一行：

```ini
ExecStart=/srv/opuscule/.venv/bin/gunicorn worldbuilding_timeline.wsgi \
  --bind 127.0.0.1:8000 --workers 2 --threads 4 --timeout 60
```

逐个参数：

| 参数 | 含义 | 为什么这样 |
| --- | --- | --- |
| `worldbuilding_timeline.wsgi` | WSGI 入口 | gunicorn 靠它加载 Django 应用 |
| `--bind 127.0.0.1:8000` | 监听本机 8000 | **只让 nginx 访问**，不暴露公网 |
| `--workers 2` | 2 个工作进程 | SQLite 写并发有限，进程别开太多 |
| `--threads 4` | 每进程 4 线程 | 用多线程提升并发，适合 I/O 等待多的场景 |
| `--timeout 60` | 单个请求 60 秒超时 | 给慢请求留余量，又不会挂死 |

单元里还配了 `EnvironmentFile=/etc/opuscule.env`（读环境变量）、
`Restart=always`（崩了自动重启）、`User/Group=opuscule`（以专用用户运行）。

### 6.6 配 nginx 反代

把 [deploy/nginx-opuscule.conf](../deploy/nginx-opuscule.conf) 放到
`/etc/nginx/conf.d/`，改域名，检查并重载：

```bash
sudo sed -i 's/example.com/你的域名/g' /etc/nginx/conf.d/opuscule.conf
sudo nginx -t && sudo systemctl reload nginx
```

nginx 的分工是**两处**：

```nginx
location /static/ { alias /srv/opuscule/staticfiles/; expires 7d; }  # 直发磁盘
location / {
    proxy_pass http://127.0.0.1:8000;         # 其余（含 /media/）转给 gunicorn
    proxy_set_header X-Forwarded-Proto $scheme;   # 让 Django 认出 HTTPS
    ...
}
```

要点：

- `/static/` 交给 nginx 直接读文件，**gunicorn 不碰静态资源**；
- **`/media/` 不能直发**：上传的地图底图 / 语音 / 图片要鉴权（按「所属文档是否公开」
  放行，见 `apps.world.views.media_file`），必须落到 `location /` 转发给 gunicorn。若在这里
  加 `alias /srv/opuscule/media/`，等于绕过鉴权——知道路径就能下载未公开的图；
- 其余请求转发给 `127.0.0.1:8000`；
- 必须带 `X-Forwarded-Proto`，配合 [§4.1](#41-secure_proxy_ssl_header) 的判断；
- `/sw.js` 由 Django 提供（自带正确的响应头），无需特殊配置。

### 6.7 上 HTTPS（certbot）

样例里 nginx 只配了 HTTP（80）。等 `http://你的域名` 能访问后：

```bash
sudo certbot --nginx -d 你的域名 -d www.你的域名
```

certbot 会自动插入 443 段、证书路径和 80→443 跳转，**证书不用手写**。

> 记住顺序提醒：因为非调试环境 cookie 带 `Secure`，
> **「验证登录」要放在签发证书之后**（见 [§4.5](#45-会话)）。

## 7. 备份

备份脚本：[deploy/backup.sh](../deploy/backup.sh)。它做四件事：

1. **快照数据库**——用 `sqlite3` 的 `.backup` 做**在线一致快照**；
2. **打包媒体**——把 `media/` 目录 `tar -czf` 成压缩包；
3. **加密落盘**——用 [age](https://age-encryption.org/) 把上面两个产物**加密**，
   本机只留 `.age` 密文；
4. **推到异地**——用 [rclone](https://rclone.org/) 把密文同步到异地目标。

```bash
WORK=$(mktemp -d); trap 'rm -rf "$WORK"' EXIT    # 明文只在临时目录短暂停留
sqlite3 "$APP_DIR/db.sqlite3" ".backup '$WORK/db.sqlite3'"
tar -czf "$WORK/media.tar.gz" -C "$APP_DIR" media
age -r "$AGE_RECIPIENT" -o "$BACKUP_DIR/db-$STAMP.sqlite3.age"   "$WORK/db.sqlite3"
age -r "$AGE_RECIPIENT" -o "$BACKUP_DIR/media-$STAMP.tar.gz.age" "$WORK/media.tar.gz"
rclone copy "$BACKUP_DIR" "$RCLONE_REMOTE" --include '*.age'
```

> 依赖：`apt install age rclone`。脚本**强制要求加密**——没配公钥就直接退出，
> 绝不产出「明文备份躺在磁盘上」这种假安全感。

### 7.1 为什么用 `.backup` 而不是直接拷文件？

**直接 `cp db.sqlite3` 是不安全的。** 原因：SQLite 在写入时，
内存里的改动会先落到日志（journal/WAL）文件，磁盘上的主文件可能处于
「改了一半」的状态。你 `cp` 到的可能是**不一致的库**，恢复时才发现坏了。

`sqlite3 ... ".backup"` 会**跟数据库协作**，产出一个**事务一致的快照**，
不管此刻有没有人在写。这是 SQLite 官方推荐的在线备份方式。

> 类比：数据库就像一本正在被编辑的账本。`cp` 是趁人不注意抢过来拍张照，
> 可能拍到只改了一半的一页；`.backup` 是让编辑「先在这一页划条线、我拍完你再继续」，
> 拿到的每一页都是完整的。

### 7.2 先配好「加密公钥」与「异地目标」

备份的两个关键变量写在 `/etc/opuscule.env`（脚本会自动加载它）：

```bash
# 必填：age 公钥。只放公钥，私钥离线保管。
BACKUP_AGE_RECIPIENT=age1…

# 异地目标（rclone 远端）。不填就只留本机——机器挂了备份也没了。
BACKUP_RCLONE_REMOTE=oss:opuscule-backup/
```

**为什么是「公钥加密」？** 这用的是非对称加密：**公钥**只能加密、不能解密，
放在服务器上；**私钥**只能解密，**离线保存**（比如存在你自己的电脑、离线介质里）。
好处是——**就算服务器被入侵/被偷，攻击者拿不到私钥，也解不开备份**
（而如果用密码加密，密码必然得存在服务器上，一被入侵就形同虚设）。

生成密钥对（**在一台安全、离线的机器上做**）：

```bash
age-keygen -o backup.key
# 打印出的 "public key: age1…" 填进 BACKUP_AGE_RECIPIENT
# 生成的 backup.key 是私钥——离线保管，丢了备份就永远解不开了
```

异地目标用 `rclone` 配置（`rclone config` 交互式选一个后端：S3 / 阿里云 OSS /
Backblaze B2 / SFTP / WebDAV …），配好后用 `rclone lsd <远端名>:` 验证能连通。
**加密过的密文**才推上去，所以哪怕云端存储被别人看到，也只是一堆 `.age` 二进制。

### 7.3 放进定时任务

```cron
0 4 * * * /srv/opuscule/deploy/backup.sh >> /var/log/opuscule-backup.log 2>&1
```

每天凌晨 4 点跑一次，日志追加到 `/var/log/opuscule-backup.log`。

> cron 不加载登录环境，所以脚本**自己** `source /etc/opuscule.env`——
> 这也是把 `BACKUP_*` 变量写进这个文件而不是别的脚本里的原因。

### 7.4 恢复怎么做

1. 停服务：`sudo systemctl stop opuscule`；
2. 解密数据库（用**离线保管的私钥**）：
   ```bash
   age -d -i backup.key db-20260101-040000.sqlite3.age > db.sqlite3
   ```
3. 需要的话恢复媒体：
   ```bash
   age -d -i backup.key media-20260101-040000.tar.gz.age | tar -xzf - -C "$APP_DIR"
   ```
4. 起服务：`sudo systemctl start opuscule`。

> **恢复演练别省**：备份的价值不在「有没有跑」，而在「**能不能解开、能不能恢复**」。
> 定期（比如每季度）拿一份密文在别的机器上按上面步骤走一遍，确认私钥可用、
> 库能起来。恢复前先留一份当前库的副本，别把现场也覆盖了。

## 8. 运维与常见故障排查

### 8.1 看日志

```bash
journalctl -u opuscule -f          # 应用实时日志（gunicorn 的输出）
journalctl -u opuscule --since "1 hour ago"
tail -f /var/log/nginx/error.log   # nginx 错误
tail -f /var/log/opuscule-backup.log
```

Django 的错误页（调试模式下）和 gunicorn 的堆栈都会进 `journalctl`，
排查时最先看这里。

### 8.2 一张排查表

| 症状 | 大概率原因 | 怎么做 |
| --- | --- | --- |
| 改了 CSS/JS，用户还是旧样子 | 浏览器缓存了旧资源（URL 版本号没变） | 见 [§8.3](#83-静态资源没更新) |
| 改了模板没反应 | 生产环境模板是**带缓存**加载的 | **重启服务** |
| 接口报 `no such table` / 字段不存在 | 迁移没跑 | `manage.py migrate` |
| 写操作返回 **403** | 你在这个世界里**没有编辑权限** | 查成员角色（§8.4） |
| 写操作返回 **401 / `need_login`** | 没登录 | 登录；或会话过期 |
| 页面样式全丢、裸 HTML | nginx 的 `/static/` 路径不对 | 核对 `alias` 与 `collectstatic` 产物 |
| 登录时提示 CSRF 失败 | 没配 `DJANGO_CSRF_TRUSTED_ORIGINS` | 见 [§3.4](#34-django_csrf_trusted_origins) |
| 访问返回 **400 Bad Request** | `DJANGO_ALLOWED_HOSTS` 没含这个域名 | 见 [§3.3](#33-django_allowed_hosts) |
| 上传图片失败 | 超过 25 MB，或 nginx 的 `client_max_body_size` 太小 | 见 [§4.4](#44-静态与媒体) |
| 全站返回 503 + 维护页 | 维护开关被打开了 | 见 [§5](#5-维护模式) |
| 登录后立刻掉线、拿不到 cookie | 站点是 HTTP 但 cookie 要求 `Secure` | 先上 HTTPS，或临时 `DEBUG=1` |
| 端口 8000 从公网能直接访问 | gunicorn 没锁在本机 | 必须 `--bind 127.0.0.1`，见 [§6.5](#65-起-gunicornsystemd) |

### 8.3 静态资源没更新

现象：代码明明改了，刷新还是老的。

前端资源 URL 后面会拼一个版本号（`?v=…`），这个号来自
[apps/world/context.py](../apps/world/context.py)：它扫描 `static/` 目录里所有
`.js/.css/.webmanifest/.svg`，取**最新的修改时间**当版本号。

- **开发环境**：版本号有 2 秒短缓存，改完文件 2 秒内 URL 就变，刷新即见。
  如果没变，检查是不是改的文件不在扫描范围内。
- **生产环境**：先 `collectstatic` 把新文件收集到 `STATIC_ROOT`，
  再刷新；必要时强刷（绕过浏览器缓存）确认。

> 这个机制解决的正是一个经典问题：无构建的前端，浏览器会**启发式缓存**静态文件
> （通常十分钟到几小时）。「文件改了 URL 没变」是缓存问题的根因；
> 「文件改了 URL 也变」浏览器才必然会去拉新的。

### 8.4 返回 403：检查成员角色

写请求被拒时，多半是**权限**问题（不是 bug）。权限规则是：

| 规则 | 说明 |
| --- | --- |
| 读永远公开 | 游客也能浏览 |
| 写需登录 + 在世界里有权限 | 必须是该世界的 `owner` / `editor` |
| 首次安装例外 | 数据库里一个用户都没有时，允许任何人写 |
| 超级管理员无视限制 | 仅 `is_superuser` 通行；`is_staff` 不再穿透 |

排查顺序：你登录了吗 → 你是**当前这个世界**的成员吗 → 你的角色是
`owner`/`editor` 吗（`viewer` 只能读）。改角色在「协作」面板里做
（对应 `PUT /api/world/collaborators/<member_id>`）。

### 8.5 日常检查清单

- [ ] `DJANGO_DEBUG=0`（对外服务必须关）
- [ ] `DJANGO_SECRET_KEY` 是随机串，不是兜底值（用了兜底值会直接**拒绝启动**）
- [ ] `DJANGO_ALLOWED_HOSTS` / `DJANGO_CSRF_TRUSTED_ORIGINS` 与实际域名一致
- [ ] `/etc/opuscule.env` 权限是 `600`
- [ ] gunicorn 只监听 `127.0.0.1`
- [ ] https 全站可用后，强制跳转与 HSTS 已生效（见 [§4.9](#49-生产开关强制-https-与-hsts)）
- [ ] `manage.py check --deploy` 干净通过（见 [§4.10](#410-managepy-check---deploy上线前自检)）
- [ ] 备份能跑通，且产物是**加密**的、**有异地副本**（见 [§7](#7-备份)）
- [ ] （可选但推荐）系统盘/数据盘已用 LUKS 整盘加密，并配好开机解锁（见 [§8.7](#87-静态加密服务器整盘加密luks可选但推荐)）
- [ ] 需要停机维护时，用维护模式（503）而不是直接关进程
- [ ] uptime 监控已挂在 `/healthz` 上，异常能真正送达人（见 [§8.6](#86-日志与监控)）

### 8.6 日志与监控

**日志去哪了**：应用默认把日志打到 stdout/stderr，由 systemd 收进 journald，
所以 `journalctl -u opuscule -f` 就能看（见 [§8.1](#81-看日志)）。journald 自己按大小/
时间轮转，**不需要额外的 `logrotate`**；保留量由 `/etc/systemd/journald.conf` 的
`SystemMaxUse` / `MaxRetentionSec` 决定。

**另存一份文件日志（可选）**：想让日志同时落到某个文件（比如交给外部采集），
设 [§3.7](#37-opuscule_log_file) 的 `OPUSCULE_LOG_FILE` 即可——会挂一个
**单文件 10 MB、最多 5 份**的按大小轮转处理器，文件轮转由程序自己管。记得给运行用户写权限：

```bash
sudo mkdir -p /var/log/opuscule && sudo chown www-data:www-data /var/log/opuscule
```

**健康检查 `/healthz`**：进程存活 + 数据库连通时返回 `200 {"status":"ok"}`；
数据库不通时返回 `503 {"status":"error","database":"down"}`。它**刻意很轻**
（只跑一句 `SELECT 1`），适合给外部 uptime 监控高频调用——**别拿它当业务接口**。

```bash
curl -fsS https://example.com/healthz   # 正常输出 {"status": "ok"}
```

**怎么被告警**：项目本身不发告警，靠外部。两种够用的做法：

- **外部 uptime 服务**（Uptime Kuma、BetterStack 等）：定时 GET `/healthz`，
  非 200 或超时就发邮件 / 短信 / webhook。
- **systemd 失败即通知**：给 [deploy/opuscule.service](../deploy/opuscule.service)
  加 `OnFailure=` 指向一个触发通知的单元；服务崩了（`systemctl status` 显示 failed）能马上知道。

> 注意：**维护模式下 `/healthz` 会返回 503**——`MaintenanceMiddleware` 的放行白名单
> 只含 `/static/`、后台、`/media/` 与维护页，不含 `/healthz`（见 [§5](#5-维护模式)）。
> 这是有意为之：维护期间本就该「看起来不可用」。不想在维护时被误报，就在告警规则里
> 识别维护页或临时静音。

### 8.7 静态加密：服务器整盘加密（LUKS，可选但推荐）

第 [§7](#7-备份) 节的 age 加密保护的是**备份**；这里补上**运行中的磁盘**那一环。

**它防什么、不防什么**（务必先认清，别被「加密」二字给假安全感）：

- ✅ **防**：服务器/磁盘被**物理拿走**（机房失窃、旧硬盘退役后被翻数据）、云厂商整盘快照被拖走。
  拿走的人拿到的是密文，**没有解锁口令就什么都没有**。
- ❌ **不防**：**服务器被攻破**。系统一旦启动、盘一解开，密钥就在内存里、文件就是明文——
  被入侵后照样能被读走。所以整盘加密**替代不了**访问控制与备份加密，只是**多一层**。

**为什么这件事通常只能"重装时做"**：LUKS 是对**块设备**加密，得落在分区/格式化之前。
已经跑着业务、装了系统盘再去加，等于要重做分区——所以**在 §6 的上线步骤之前就要决定**。
数据库是 SQLite、`media/` 是普通目录，落在加密卷上**应用侧零改动**。

**做法（以 Debian / Ubuntu 为例）**：

1. **系统盘**：安装系统时在分区步骤选 **「Guided - use entire disk and set up encrypted LVM」**，
   installer 会自动建好 LUKS + LVM，开机输口令解锁。这是最省事、最彻底的方式。
2. **另挂的数据盘**（代码/库/媒体放这块时）：

   ```bash
   # 1. 加密格式化（会清空该盘，务必确认设备名）
   sudo cryptsetup luksFormat /dev/sdX
   # 2. 打开映射，得到一个可用的 /dev/mapper/cryptdata
   sudo cryptsetup luksOpen /dev/sdX cryptdata
   # 3. 在映射设备上建文件系统并挂载
   sudo mkfs.ext4 /dev/mapper/cryptdata
   sudo mount /dev/mapper/cryptdata /srv/opuscule
   ```

   开机自动解锁写进 `/etc/crypttab` + `/etc/fstab`；**解锁用的 keyfile 必须放在另一块盘上**
   （跟着同一块盘走的话，等于把钥匙和锁一起交出去，毫无意义）。

3. **无人值守重启的取舍**：无头服务器开机要人输口令不现实，两条常见路子——
   - **dropbear-initramfs**：开机起一个极小的 SSH，远程敲一次口令就能解锁（推荐）。
   - **TPM2 绑定**（`systemd-cryptenroll --tpm2-device=auto`）：免口令自动解锁，但安全性
     取决于主机的 TPM——适合能物理守住机器的场景。
   - ⚠️ **别用**「明文 keyfile 放在系统盘里自动解锁」这种做法：等于没加密。

**什么时候值得做**：把服务放到**共享主机 / 托管机房 / 云主机**（磁盘不在自己手上）时，
这一步性价比很高——**一次配置，长期受益**；代价是运维上多一个「开机解锁」的环节。
本地/自己家里守着机器的部署，可以往后放。

## 9. 小结

- **两条铁律**：生产 `DEBUG=0`、`SECRET_KEY` 换随机串（留着兜底值会直接拒绝启动）。
- **环境变量**是唯一配置入口：密钥、调试、域名、CSRF、维护开关都在这里。
- **`SECURE_PROXY_SSL_HEADER` + nginx 的 `X-Forwarded-Proto`** 一起，
  才能让 Django 在反代后正确判断 HTTPS；
  `SECURE_SSL_REDIRECT` 强制跳转、HSTS 让浏览器记住「只用 https」。
- **`X_FRAME_OPTIONS=SAMEORIGIN`** 是为了让工作区能同源 iframe 内嵌经典时间轴。
- **上线顺序**：装环境 → 配变量 → `migrate` → `collectstatic` → 起 gunicorn →
  配 nginx → 上 HTTPS。
- **上线前跑 `manage.py check --deploy`**，干净通过才算数（两条静音是「故意如此」）。
- **备份用 `sqlite3 .backup`**，别直接拷文件；再**加密（age）**、**推异地（rclone）**，
  并定期演练恢复。
- **整盘加密（LUKS）**保护「磁盘被物理拿走」那一环，须在装系统/分区时决定；
  它**不防**运行中的服务器被攻破（见 [§8.7](#87-静态加密服务器整盘加密luks可选但推荐)）。
- **改模板要重启、改静态文件要 `collectstatic`、接口 403 先查角色。**
