# 工作区与文档树

> **文档版本：0.5.0-dev**
>
> 这篇讲「作者每天面对的那块屏幕」：顶栏、左侧的文档树、中间的主编辑区，
> 以及把这一切串起来的数据结构——**文档（Document）**。
> 读完你应该能回答：树是怎么长出来的、拖拽移动背后发生了什么、
> 删掉的文档去了哪里、地址栏里的短码（slug）是怎么来的。

---

## 1. 工作区长什么样

工作区是登录后的主界面，地址是 `/world`。它的 HTML 骨架在
`templates/workspace.html` 里，样式与逻辑由 `static/workspace.js`（配 `icons.js`、
`experience.js`）驱动。整块屏幕分成五个区域：

| 区域 | 位置 | 里面有什么 | 干什么用 |
| --- | --- | --- | --- |
| **顶栏** | 最上方一条 | 面包屑、侧栏开关、撤销/重做、命令面板（⌘K）、保存状态、纪元切换、在线头像、用户菜单 | 全局操作与状态显示 |
| **左侧文档树** | 左侧竖栏 | 世界切换、搜索框、视图药丸（世界 / 维基）、上手进度、文档树、底部「＋新建文档」 | 导航：找到并打开任意文档 |
| **主编辑区** | 中间大块 | 一个或多个「面板」，每个面板顶部是一排标签页 | 真正看内容、改内容的地方 |
| **多标签页** | 每个面板的顶部 | 一排 `.tab`，每张对应一份打开的文档 | 像浏览器一样同时开很多篇来回切 |
| **右侧 / 并排面板** | 主编辑区可再加一格 | 第二个面板（并排显示） | 一边看 A 一边对照 B |

一句话概括**布局原则**：左边负责「去哪儿」，中间负责「看什么」，
顶栏负责「现在是什么状态」。三者互不遮挡。

### 1.1 顶栏的组成

顶栏（`.topbar`）从左到右依次是：

- **面包屑 `tbCrumb`**：当前文档在世界里的路径，例如「资料 / 人物 / 亚瑟」。
- **侧栏开关 `sidebarBtn`**：窄屏时折叠 / 展开左侧树。
- **撤销 / 重做**：编辑正文时的历史操作。
- **命令面板 ⌘K**：一个输入框搜索并跳转到任意文档或执行动作。
- **保存状态 `save-state`**：显示「正在保存 / 已保存」。
- **纪元槽 `era-slot`**：切换当前「世界版本（纪元）」。
- **在线头像 `presence`**：谁正在这个世界里。
- **用户菜单 `userChip`**：账号、退出等。

### 1.2 左侧文档树的组成

侧栏（`aside.sidebar#sidebar`）自上而下：

| 元素 | id / 类 | 作用 |
| --- | --- | --- |
| 世界切换器 | `#sb-world` | 在「我的世界」之间切换（一个账号可以有多个世界） |
| 搜索框 | `#sb-search` | 在文档树里按名字过滤 |
| 视图药丸 | `.sb-pills` | 切换「世界 / 维基」两种视角 |
| 上手进度卡 | `.sb-setup` | 引导新手完成的几件事 |
| **文档树** | `#sbTree` | 真正的树本体，可展开、可拖拽 |
| 底部动作条 | `.sb-dock` | 「＋新建文档」和「更多」菜单 |

## 2. 一切内容都是「文档」：Document 与文档树

### 2.1 为什么只有一张表

传统做法里，「文件夹」「文章」「时间线」「地图」往往各建一张表。
Opuscule 反过来：**所有东西都是同一种记录——`Document`**，再用一个字段
`document_type` 区分它是什么类型。

这样设计有三个好处：

1. **树只需要一种节点**。文件夹和卡片能装在同一个 `parent` 下，无需考虑"这一层允许放什么"。
2. **移动、复制、删除、权限等通用逻辑写一次就够**，对所有类型都生效。
3. **新工具随时能加**，只是多一个 `document_type` 取值，树的结构不变。

`apps/world/models/constants.py` 里定义了全部文档类型：

| 值 | 含义 | 值 | 含义 |
| --- | --- | --- | --- |
| `folder` | 文件夹 | `dictionary` | 词典 |
| `card` | 卡片 | `todo` | 待办清单 |
| `timeline` | 时间线 | `voice` | 语音备忘 |
| `map` | 地图 | `dice` | 骰子 |
| `canvas` | 画布 | `soundscape` | 环境音 |
| `board` | 看板 | `radar` | 雷达图 |
| `note` | 笔记 | `chapter` | 章节 |
| `table` | 表格 | `media` | 媒体库 |
| `familyTree` | 关系树 | `embed` | 链接嵌入 |
| `graph` | 世界图谱 | | |

### 2.2 树是靠「自引用外键」长出来的

`Document` 里有一个指向**自己**的外键：

```python
class Document(models.Model):
    ...
    parent = models.ForeignKey(
        "self", null=True, blank=True, on_delete=models.CASCADE, related_name="children"
    )
    position = models.PositiveIntegerField("排序", default=0)
```

- `parent` 为空（`null`）→ 这份文档是**根节点**（树的最外层）。
- `parent` 指向另一份文档 → 它是那份文档的**子节点**。
- `related_name="children"` 让我们可以写 `doc.children.all()` 拿到直接子节点。

因为没有层级数量限制，`parent` 一层套一层，就能表达**无限深的嵌套**。
一个典型的树：

```text
世界（根文档们）
├── 资料（folder）
│   ├── 人物（folder）
│   │   ├── 亚瑟（card）
│   │   └── 梅林（card）
│   └── 地理（folder）
│       └── 卡美洛（card）
└── 世界时间线（timeline）
```

对应的 `parent` 关系表：

| 文档 | document_type | parent |
| --- | --- | --- |
| 资料 | folder | （空，根） |
| 人物 | folder | 资料 |
| 亚瑟 | card | 人物 |
| 梅林 | card | 人物 |
| 地理 | folder | 资料 |
| 卡美洛 | card | 地理 |
| 世界时间线 | timeline | （空，根） |

### 2.3 模型上提供的树工具

`Document` 自带几个方便操作树的方法：

| 方法 | 做什么 |
| --- | --- |
| `is_folder` | 是不是文件夹（`document_type == "folder"`） |
| `root_doc` | 顺着 `parent` 往上走，返回最顶层的根 |
| `descendants(include_self=False)` | 用**宽度优先**（BFS）遍历，返回整棵子树的所有节点 |
| `is_descendant_of(other)` | 判断自己是不是 `other` 的后代（用于防止把节点拖到自己的子孙下面） |

`descendants()` 用队列实现，一层一层往外扩：

```python
def descendants(self, include_self=False):
    found = [self] if include_self else []
    queue = list(self.children.all())
    while queue:
        node = queue.pop(0)          # 从队首取出
        found.append(node)
        queue.extend(node.children.all())   # 子节点排到队尾
    return found
```

这种「一圈一圈扩散」的写法叫**广度优先搜索**，特点是离根越近越早被访问到。

## 3. 树的读取、排序与前端渲染

### 3.1 后端：先取根，再递归拼整棵

进入工作区时，前端第一件事就是请求 `/api/world/state`。后端在
`apps/world/views/site.py` 的 `state()` 里这样组装树：

```python
roots = world.documents.filter(
    parent__isnull=True, deleted_at__isnull=True
).order_by("position", "id")
documents = [document.to_payload(with_children=True) for document in roots]
```

两步走：

1. **只查根节点**：`parent__isnull=True`（是根）且 `deleted_at__isnull=True`（没被删）。
2. **交给 `to_payload` 递归**：每个节点在 `with_children=True` 时自动带上自己的子节点。

`to_payload` 的递归部分：

```python
if with_children:
    payload["children"] = [
        child.to_payload(with_children=True)
        for child in self.children.filter(deleted_at__isnull=True).order_by("position", "id")
    ]
```

注意两点：

- 子节点查询里再次过滤了 `deleted_at__isnull=True`——**回收站里的文档不出现在树上**，
  否则点进去只会得到 404。
- 每一层都按 `("position", "id")` 排序，保证顺序稳定。

### 3.2 排序：position 决定先后

每个 `Document` 有一个 `position`（正整数）。同一个 `parent` 下的兄弟节点，
按 `position` 从小到大排列；`position` 相同时用 `id` 兜底，保证顺序不会随机跳。

`Document` 的默认排序也写死了这一点：

```python
class Meta:
    ordering = ["position", "id"]
```

### 3.3 前端：renderTree 把 JSON 画成树

前端拿到 `state.documents` 后存进 `S.tree`，由 `renderTree()` 渲染。它做几件事：

| 行为 | 说明 |
| --- | --- |
| **截断** | 默认只显示前 `CAP = 26` 个根节点，其余折叠成「⋯ 查看全部」 |
| **置顶分组** | `pinned=True` 的节点单独排到一组 |
| **过滤** | 顶部搜索框输入的关键字会过滤匹配的节点 |
| **递归建行** | `treeRow(node, depth)` 为每个节点建一行，深度越大缩进越多 |

`treeRow` 会为每一行判断：是不是文件夹（决定图标是「打开的文件夹」还是「合上的」）、
有没有子节点（决定是否画展开三角 `▾/▸`）、是否属于当前纪元（不属于就标灰）、是否被隐藏等。

## 4. 文档的增删改查（CRUD）流程

这里说的「CRUD」是 Create（新建）、Read（读取）、Update（修改）、Delete（删除）
四个基本操作。下面逐个讲它们在 Opuscule 里怎么走。

### 4.1 新建：不同 document_type 有不同动作

新建走 `POST /api/world/documents`，请求体里带 `type`、`name`、可选的 `parent`。
后端先校验类型合法，然后**按类型做不同的初始化**：

```python
if doc_type == DOC_CARD:
    # 新卡片给一块空白"概览"，属性值按类型预填
    Card.objects.create(
        document=document,
        entity_type=entity_type,
        values=default_values_for(entity_type) if entity_type is not None else {},
        blocks=normalize_blocks([{"id": "b1", "type": "text", "title": "", "text": ""}]),
    )
elif doc_type == DOC_TIMELINE:
    calendar_id = as_int(payload.get("calendar"), 0)
    if not calendar_id:
        calendar = world.calendars.order_by("id").first()
        calendar_id = calendar.id if calendar is not None else 0
    if calendar_id:
        save_document_settings(document, {"calendar": calendar_id})
elif doc_type == DOC_TREE:
    kind = as_text(payload.get("kind"), 40) or TREE_KINDS[0][0]
    TreeVariant.objects.create(document=document, kind=kind)
```

用表格总结：

| 新建的类型 | 额外动作 |
| --- | --- |
| **卡片 `card`** | 建一张 `Card`，预填类型默认属性值，并给一块空白「概览」区块 |
| **时间线 `timeline`** | 在 `settings` 里绑定一个日历（没指定就用世界的第一本） |
| **关系树 `familyTree`** | 建一个 `TreeVariant`（关系树的变体） |
| **其它类型** | 只建 Document，没有额外动作 |

前端在 `createDoc(type, parent)` 里先弹框问名字，再发请求，成功后刷新树并打开这篇新文档。
不同类型的默认名不一样：文件夹叫「新文件夹」、时间线叫「世界时间线」、其它叫「未命名」；
关系树不问名字（下一步会跟着模板走）。

### 4.2 读取：单篇文档

`GET /api/world/documents/<id>` 返回一份文档。查询参数 `?children=1` 会把子节点也带上
（文件夹展开时用）。返回体里还会附一个 `revision` 修订号，用于防冲突：

```python
payload["revision"] = as_int((document.settings or {}).get("revision"), 0)
```

### 4.3 修改：改名、移动、置顶、隐藏……

`PUT /api/world/documents/<id>` 是**同一个接口处理很多种修改**：请求体里出现哪个字段，
就改哪个字段。

| 请求体字段 | 效果 |
| --- | --- |
| `name` | 改名 |
| `parent` | 移动到新父节点（会做**环检测**，见下） |
| `pinned` | 置顶 / 取消置顶 |
| `hidden` | 在维基中隐藏 / 显示 |
| `cover` / `icon` | 封面 / 图标 |
| `document_type` | 改文档类型（必须是合法类型） |
| `era` / `era_ids` | 归属哪个纪元 |
| `entity_type` | 卡片类型 |
| `settings` | 与现有设置**合并**（不是覆盖） |
| `position` | 排序号 |
| `blocks` / `values` / `aliases` / … | 卡片正文相关，转交 `apply_card_payload` |

**环检测**是移动时最要紧的一步——不能把一份文档塞到它自己的子孙下面，
否则树会首尾相连变成环，递归渲染会死循环：

```python
if parent is not None:
    walker = parent
    while walker is not None:
        if walker.id == document.id:
            return error("不能把文档移动到它自己的子文件夹里")
        walker = walker.parent
```

`settings` 的合并逻辑也值得注意：

```python
if "settings" in payload and isinstance(payload.get("settings"), dict):
    merged = dict(document.settings or {})
    merged.update(payload["settings"])   # 只覆盖传进来的键
    document.settings = merged
```

这样做是为了**不动其它键**：比如地图页面传一个新设置进来，不会把时间线绑定的日历弄丢。

### 4.4 复制：duplicate

`POST /api/world/documents/<id>/duplicate` 复制一篇文档。后端会：

1. 新建一个 Document，名字加后缀「（副本）」，`parent` / `position` / `era` 等一并复制。
2. 如果原文档是卡片，把它的 `Card`（类型、别名、属性值、区块、正文）也复制一份。
3. 如果原文档有时间线事件，逐个复制事件。

```python
clone = Document.objects.create(
    world=world,
    document_type=document.document_type,
    name=f"{document.name}（副本）",
    parent=document.parent,
    ...
)
```

### 4.5 删除：先软删，再彻底删

删除走 `DELETE /api/world/documents/<id>`，分两种：

| 请求 | 行为 | 能否恢复 |
| --- | --- | --- |
| 普通删除 `DELETE /documents/<id>` | **软删**：只是把 `deleted_at` 设为当前时间 | 能，见下一节 |
| 彻底删除 `DELETE /documents/<id>?hard=1` | **硬删**：调用 `document.delete()` 从库里抹掉 | 不能 |

软删的实现很短：

```python
if permanent:                 # ?hard=1
    document.delete()
else:
    document.deleted_at = timezone.now()
    document.save(update_fields=["deleted_at"])
```

关键点：软删只是"打个标记"，所以从数据库里仍然查得到，只是所有正常查询都带
`deleted_at__isnull=True` 把它排除掉——这就是"回收站"的实现原理。

### 4.6 回收站与恢复

回收站列出所有被软删的文档（`GET /api/world/trash`）：

```python
documents = world.documents.filter(deleted_at__isnull=False).order_by("-deleted_at", "id")
```

恢复走 `POST /api/world/documents/<id>/restore`：

```python
document.deleted_at = None
if document.parent is not None and document.parent.deleted_at is not None:
    document.parent = None      # 父文件夹还在回收站里 -> 提到顶层
document.save(update_fields=["deleted_at", "parent"])
```

这里处理了一个容易忽略的情况：**如果父文件夹也还在回收站里**，
恢复出来的这篇文档挂上去也看不见（父节点不在树上），所以直接把它提到顶层。

前端的 `showTrash()` 弹窗里，每一行都有「恢复」和「彻底删除」两个按钮：

```javascript
await api(`/api/world/documents/${doc.id}/restore`, { method: 'POST' });
// 彻底删除
await api(`/api/world/documents/${doc.id}?hard=1`, { method: 'DELETE' });
```

## 5. 多标签页与面板：前端怎么维护

### 5.1 状态都存在一个 S 对象里

前端所有的界面状态集中在一个全局对象 `S`（`static/workspace.js`）里，与面板相关的部分：

```javascript
const S = {
  ...
  tree: [],            // 根文档（含 children）
  docs: new Map(),     // docId -> 详情（document + card / timeline 状态）
  panels: [{ tabs: [], active: -1 }],
  collapsed: new Set(),
  ...
};
```

| 字段 | 含义 |
| --- | --- |
| `S.tree` | 后端返回的整棵树（JSON 数组） |
| `S.docs` | 已经加载过的文档详情，`Map` 的键是文档 id；打开同一篇不用再请求 |
| `S.panels` | 面板数组。第一个是主面板，可再 push 一个做并排 |
| `S.panels[i].tabs` | 这个面板里打开的文档 id 列表（就是标签页的次序） |
| `S.panels[i].active` | 当前激活的是第几个标签页 |
| `S.collapsed` | 被折叠的树节点 id 集合 |

### 5.2 打开一篇文档：openDoc

`openDoc(id, panelIndex, …)` 的流程可以概括为：

```javascript
const panel = S.panels[panelIndex];
if (!panel.tabs.includes(id)) panel.tabs.push(id);   // 没开过就加一个标签
if (focus) panel.active = panel.tabs.indexOf(id);    // 激活它
if (!S.docs.has(id)) {                                // 没加载过才请求
    panel.loading = { id, type: ... };                // 先画骨架屏
    const entry = await fetchEntry(id);
    S.docs.set(id, entry);
}
renderPanels();
renderTree();
```

其中 `fetchEntry(id)` 会**并行**取详情与（卡片 / 时间线）数据——它们之间没有依赖，
排队等就是白等：

```javascript
const detail = await api(`/api/world/documents/${id}${wantChildren}`);
const jobs = [];
if (detail.type === 'timeline') jobs.push(api(`/api/world/timelines/${id}`)...);
if (detail.type === 'card')     jobs.push(api(`/api/world/cards/${id}`)...);
await Promise.all(jobs);
```

### 5.3 关闭标签页：closeTab

`closeTab(panelIndex, id)` 先从 `tabs` 里删掉 id，再修正 `active` 下标，
最后重画面板。它还记录到 `S.closedTabs`（上限 20 个），配合动画做"关闭折叠"的效果。
被关掉的文档**不会**从 `S.docs` 里删除——下次再打开就直接用缓存。

### 5.4 整体重画：renderPanels

`renderPanels()` 的做法很直接：**每次把面板区域整块清空，从头重建 DOM**。

```javascript
const host = $('#panels');
host.innerHTML = '';          // 清空
S.panels.forEach((panel, index) => { ... });  // 按状态重画每个面板
```

这样做牺牲了一点性能，换来的是**状态和界面的强一致**：只要改 `S`，调一次
`renderPanels()`，屏幕就一定对得上数据，不用担心"漏更新了某个角落"。

画的时候会按文档类型分发到不同的渲染函数：卡片走 `renderCard`、时间线走
`renderTimeline`、表格走 `renderTableTool`……没有打开任何标签页时，就显示
一个空状态提示（`#emptyHint`）。

### 5.5 别丢掉"上次看到哪一篇"

地址栏（URL 的 `#` 后面）会记录当前打开的文档，格式类似
`#doc=12`，并排时还有 `&doc2=34`。它带来三个好处：

- **可分享**：把链接发给别人，打开的就是同一篇。
- **前进 / 后退可用**：浏览器原生返回键能回到上一篇。
- **刷新不迷路**：启动时 `boot()` 读取 hash，直接打开那一篇。

```javascript
let hash = `#doc=${id}`;
['panel', 'tl', 'doc2', 'event'].forEach((key) => { ... });
```

## 6. slug 是什么、怎么生成、有什么用

项目里「slug」这个词出现在**两个不同的对象**上，含义不同，要分清楚。

### 6.1 Document.slug：给人看的、可读的短名

`Document.slug` 由名称算出，用途是让 URL、链接等有一个"能读懂的稳定标识"。
它由 `slugify_name()` 生成（`apps/world/models/constants.py`）：

```python
def slugify_name(name: str, fallback: str = "untitled") -> str:
    """把名称变成 slug：去音标、去符号、转小写、截断 50 字符。"""
    import unicodedata
    normalized = unicodedata.normalize("NFKD", name or "")
    normalized = "".join(ch for ch in normalized if not unicodedata.combining(ch))
    normalized = re.sub(r"[^\w\s-]", "", normalized, flags=re.UNICODE).strip().lower()
    normalized = re.sub(r"[\s_]+", "-", normalized)
    normalized = normalized[:50].strip("-")
    return normalized or fallback
```

逐步拆解它做了什么：

| 步骤 | 代码 | 例子 |
| --- | --- | --- |
| 1. 去音标（NFKD 分解 + 去掉组合字符） | `normalize("NFKD", ...)` + 去 `combining` | `Café` → `Cafe` |
| 2. 去掉非 `[\w\s-]` 的符号 | `re.sub(r"[^\w\s-]", "", ...)` | `亚瑟王!` → `亚瑟王` |
| 3. 转小写、去首尾空白 | `.strip().lower()` | `Arthur` → `arthur` |
| 4. 空白与下划线转连字符 | `re.sub(r"[\s_]+", "-", ...)` | `dark age` → `dark-age` |
| 5. 截断 50 字符、去掉首尾连字符 | `[:50].strip("-")` | — |
| 6. 结果为空就用兜底名 | `or fallback` | `` → `untitled` |

它在 `Document.save()` 里被自动调用：**只在 slug 还是空的时候生成一次**，
之后改名不会自动覆盖，保证地址稳定：

```python
def save(self, *args, **kwargs):
    if not self.slug:
        self.slug = slugify_name(self.name)
    super().save(*args, **kwargs)
```

### 6.2 World.slug：6 位十六进制短码

世界（`World`）的 slug 是另一种风格——**随机短码**，由 `make_slug()` 生成：

```python
def make_slug(*seeds: str) -> str:
    """生成 6 位十六进制短码。"""
    import hashlib
    raw = "|".join(str(s) for s in seeds if s) or str(timezone.now().timestamp())
    return hashlib.sha1(raw.encode("utf-8")).hexdigest()[:6]
```

做法是：把几个"种子"字符串用 `|` 拼起来 → 算一次 SHA-1（一种散列函数）→
取前 6 个十六进制字符。结果形如 `a045ca`。

为什么要短码？因为世界的访问地址需要**又短又不易撞车**。`World.slug` 字段是
`unique=True`，全局唯一；发布成站点后还会再生成一个 `published_slug`：

```python
if self.is_published and not self.published_slug:
    self.published_slug = make_slug("site", self.name, self.slug)
```

### 6.3 两种 slug 对比

| | `Document.slug` | `World.slug` |
| --- | --- | --- |
| 生成函数 | `slugify_name()` | `make_slug()` |
| 形态 | 可读的词，如 `dark-age` | 6 位十六进制，如 `a045ca` |
| 是否唯一 | 否（只要求是空串时才生成） | 是（`unique=True`） |
| 目的 | 给人看的稳定短名 | 给系统用的、不撞车的短码 |

## 7. 相关接口逐个讲

所有接口都挂在 `/api/world/` 下，且**路径结尾不带斜杠**。与本篇相关的是下面这几个：

| 方法 | 路径 | 视图 | 用途 |
| --- | --- | --- | --- |
| GET | `/api/world/state` | `state` | 启动数据：世界、类型、纪元、日历、**整棵文档树** |
| GET | `/api/world/documents` | `document_collection` | 列文档（支持 `type` / `parent` / `q` 过滤） |
| POST | `/api/world/documents` | `document_collection` | 新建文档 |
| GET | `/api/world/documents/<id>` | `document_detail` | 读一篇文档 |
| PUT | `/api/world/documents/<id>` | `document_detail` | 改名 / 移动 / 置顶 / 隐藏… |
| DELETE | `/api/world/documents/<id>` | `document_detail` | 删除（`?hard=1` 彻底删） |
| POST | `/api/world/documents/<id>/duplicate` | `document_duplicate` | 复制 |
| POST | `/api/world/documents/<id>/restore` | `document_restore` | 从回收站恢复 |
| GET | `/api/world/trash` | `trash_collection` | 回收站列表 |

### 7.1 GET /api/world/state

**用途**：首屏一次性把工作区需要的东西全给前端。返回结构（节选）：

```json
{
  "world": { "id": 1, "name": "亚瑟的世界", "slug": "a045ca", "theme": { ... }, "publish": { ... } },
  "viewer": { "name": "...", "role": "..." },
  "online": [ { "name": "..." } ],
  "types": [ { "id": 1, "name": "人物", "properties": [ ... ] } ],
  "eras": [ ... ],
  "calendars": [ ... ],
  "documents": [
    { "id": 1, "type": "folder", "name": "资料", "children": [ ... ] }
  ],
  "doc_types": [ { "value": "card", "label": "卡片" } ],
  "trash_count": 0,
  "worlds": [ { "id": 1, "name": "亚瑟的世界", "is_current": true } ],
  "session_expires_at": "2026-10-14T12:00:00+08:00",
  "publish": { "published": false, "url": "", "counts": { ... } }
}
```

关键点：`documents` 里每个节点都通过 `to_payload(with_children=True)` 递归带上了
`children`，所以前端一次请求就拿到整棵树，无需逐层再请求。

### 7.2 GET /api/world/documents

**用途**：按条件列文档。支持的查询参数：

| 参数 | 作用 |
| --- | --- |
| `type` | 只列某一种文档类型，如 `?type=card` |
| `parent` | 只列某个父节点下的直接子节点；`root` 表示根层 |
| `q` | 按名称模糊搜索（`name__icontains`） |

```python
query = world.documents.filter(deleted_at__isnull=True)
doc_type = request.GET.get("type")
if doc_type:
    query = query.filter(document_type=doc_type)
parent = request.GET.get("parent")
if parent not in (None, "", "root"):
    query = query.filter(parent_id=as_int(parent))
```

返回的每条都带卡片正文（`with_card=True`）。

### 7.3 POST /api/world/documents

**用途**：新建文档。请求体示例：

```json
{ "type": "card", "name": "亚瑟", "parent": 3, "entity_type": 2 }
```

后端的处理顺序：校验 `type` 合法 → 解析 `parent` 与 `entity_type` → 建 `Document`
→ 按类型做初始化（卡片建 Card、时间线绑日历、关系树建变体）→ `touch_document`
更新修订号与版本快照 → 返回新文档的 payload。

响应示例：

```json
{ "id": 42, "type": "card", "name": "亚瑟", "parent": 3, "slug": "ya-se", "card": { ... } }
```

### 7.4 GET / PUT / DELETE /api/world/documents/<id>

- **GET**：返回文档；`?children=1` 带上子节点；始终带 `revision`。
- **PUT**：局部更新（见上文 4.3 的字段表），支持移动与环检测。
- **DELETE**：默认软删（写 `deleted_at`）；加 `?hard=1` 则彻底删除。

删除响应：

```json
{ "success": true, "removed": false }
```

`removed` 说明这次是"彻底删掉"（true）还是"移进回收站"（false）。

### 7.5 POST /api/world/documents/<id>/duplicate

**用途**：复制文档（含卡片的属性值 / 区块、以及时间线的事件），
新文档名字后缀「（副本）」，父节点与原文档相同。返回新文档 payload。

### 7.6 POST /api/world/documents/<id>/restore

**用途**：把回收站里的文档恢复出来。若其父节点也还在回收站里，则把这篇提到顶层。

### 7.7 GET /api/world/trash

**用途**：回收站列表。返回：

```json
{
  "documents": [ { "id": 9, "type": "card", "name": "废弃的草稿" } ],
  "count": 1
}
```

## 8. 把这条链路串起来

走一遍「从点开工作区到删掉一篇文档」的完整过程，你能看到各个部件如何配合：

```text
1. 打开 /world
   → workspace.js: boot()
     → GET /api/world/state（拿世界 + 整棵树）
     → renderTree() / renderPanels()

2. 点左侧树里的「亚瑟」
   → treeRow 的 click → openDocFromTree
     → openDoc(id)
       → 没加载过：fetchEntry → GET /api/world/documents/<id> + /cards/<id>
       → S.docs.set(id, entry)
       → renderPanels() 画卡片、renderTree() 更新高亮

3. 拖动「亚瑟」到「人物」文件夹里
   → dragstart 写入 id → drop 时
     → PUT /api/world/documents/<id> { parent: 人物.id }
     → reloadTree() 重新拉 state

4. 右键「亚瑟」→ 移到回收站
   → DELETE /api/world/documents/<id>（软删）
     → 从 S.panels / S.docs 里移除
     → reloadTree()

5. 打开回收站 → 恢复
   → GET /api/world/trash → POST /api/world/documents/<id>/restore
```

记住一句话：**树是数据，不是目录**——`folder` 只是恰好被当成分组用的文档，
真正的层级来自每份文档的 `parent` 字段。
