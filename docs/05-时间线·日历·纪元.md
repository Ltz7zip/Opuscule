## 1. 三个概念，先分清

「时间」这件事在本项目里被拆成了三层，它们**互相独立**，混在一起看最容易糊涂：

| 概念 | 数据表 | 回答的问题 | 类比 |
| --- | --- | --- | --- |
| **事件**（TimelineEvent） | `world_timelineevent` | 「什么时候发生了什么事」 | 日历上圈出来的一个日子 |
| **日历**（Calendar） | `world_calendar` | 「这个世界怎么数日子」 | 一年几个月、一天几小时、天上有几颗月亮 |
| **纪元**（Era） | `world_era` | 「这段时间属于哪个时代」 | 书里的一「章」：元年以前 / 元年以后 |

- **事件**回答「是什么时候」；
- **日历**提供「读日期」的规则（同一串数字，在自定义历法里可能是「Month 3, Year -14」）；
- **纪元**给时间**分段**，而且每个纪元**从 0 年重新起算**——这是理解它的关键（见 §4）。

一份**时间线文档**（`Document` 里 `document_type = "timeline"`）是装着这些事件的容器。

## 2. 事件：四级精度

### 2.1 「精度」是什么，为什么要它

写小说的人经常只知道「大概是第三纪」而不知道具体哪天。如果强制填年月日，
作者就会被工具逼着编一个假日期。所以这里让**每个事件自己声明精确到哪一级**：

```python
# apps/world/models/constants.py
PRECISION_YEAR  = "year"    # 只知道某一年
PRECISION_MONTH = "month"   # 精确到月
PRECISION_DAY   = "day"     # 精确到日
PRECISION_TIME  = "time"    # 精确到小时
PRECISION_ORDER = {PRECISION_YEAR: 0, PRECISION_MONTH: 1, PRECISION_DAY: 2, PRECISION_TIME: 3}
```

精度不到的位**仍然会被存下来**（比如一个「year」精度的事件，month 默认是 1），
但它们**不参与排序**——这正是 `sort_key` 在做的事。

### 2.2 排序键：让粗精度事件排在靠前

```python
# apps/documents/models/document.py —— TimelineEvent.sort_key
depth = PRECISION_ORDER.get(self.precision, 0)
return (
    self.year,
    self.month if depth >= 1 else 1,   # 精度不到「月」，无论存了什么，都当 1 月
    self.day   if depth >= 2 else 1,   # 同理
    self.hour  if depth >= 3 else 0,
    self.position,                     # 同一天里的手动顺序
    self.id or 0,
)
```

**为什么这样写**：假设有两件事都发生在「Year 300」——一件只精确到年，另一件精确到月。
如果不做处理，第二件的 month 会是 5，排序时它会被塞到「1 月 1 日」那件之后。
把「精度不到的位」一律归零/归一，就等于说：**「Year 300」代表这一年的开始**，
于是它稳定地排在年内所有更精确的事件之前。心情上很符合直觉：越模糊越靠前。

### 2.3 日期怎么显示给人看

事件自己不知道历法，它把日期渲染交给所属文档的日历：

```python
# apps/documents/models/document.py —— TimelineEvent.date_label
calendar = self.document.settings.get("calendar")      # 文档 settings 里指定的日历 id
cal = Calendar.objects.filter(pk=calendar).first()     # 找不到就……
cal = cal or Calendar.objects.filter(world_id=...).first()   # ……退回本世界第一本日历
return cal.format_date(self.year, self.month, self.day, self.hour, self.precision)
```

规则：**文档指定优先 → 世界默认日历兜底 → 都没有就输出 `Year 300`**。
这样即使世界还没配日历，界面也不会报错。

## 3. 日历：自定义历法

### 3.1 日历里存了什么

```python
# apps/documents/models/document.py —— Calendar
hours_per_day = models.PositiveIntegerField("每天小时数", default=24)
months        = models.JSONField("月份", default=list)   # [{"name": "Frost", "days": 31}, ...]
moons         = models.JSONField("卫星", default=list)   # [{"name": "Luna", "cycle_days": 28, ...}]
open_past     = models.BooleanField("开放过去", default=False)
default_precision = models.CharField("默认精度", ..., default=PRECISION_YEAR)
```

一个世界可以有**多本日历**（不同地区用不同的历法），每本日历自己的月份长度、
每天小时数、天上卫星都可以自定义。

### 3.2 月份表：坏数据也要能读

用户填的 JSON 未必干净，所以 `month_list()` 会把各种形态统统收成统一的 `{name, days}`：

```python
# apps/documents/models/document.py —— Calendar.month_list
for i, m in enumerate(months, start=1):
    if isinstance(m, dict):
        clean.append({"name": str(m.get("name") or f"Month {i}"), "days": int(m.get("days") or 30)})
    elif isinstance(m, str):
        clean.append({"name": m, "days": 30})       # 只给名字，天数按 30 算
return clean or [dict(m) for m in EARTH_MONTHS]      # 一个都没配好 → 退回 12×30
```

**它做两件事**：
1. **容错**：缺名字补 `Month 5`，缺天数补 30；
2. **兜底**：全空时退回通用的 12 个月 × 30 天，保证下游算法（网格、月相）永远有数据可用。

### 3.3 收拢越界值

自定义历法里各月天数不同，用户可能传一个「13 月 40 日」给一个只有 12 个月、每月 28 天的历法。
`clamp()` 负责把这种输入夹回合法范围：

```python
# apps/documents/models/document.py —— Calendar.clamp
month = min(max(month, 1), len(months))       # 月份夹在 [1, 月份数]
max_day = months[month - 1]["days"]
day = min(max(int(day or 1), 1), max_day)     # 日期夹在 [1, 该月天数]
hour = min(max(int(hour or 0), 0), max(0, self.hours_per_day - 1))
```

**为什么要在服务端夹、而不是只在前端校验**：接口是可以被直接调用的（导入脚本、
其它客户端），把校验放在数据进库的最后一道关口，才挡得住所有入口。

### 3.4 日期格式化

```python
# apps/documents/models/document.py —— Calendar.format_date
if precision == PRECISION_YEAR:   return f"Year {year}"
if precision == PRECISION_MONTH:  return f"{self.month_name(month)}, Year {year}"
stamp = f"{day} {self.month_name(month)}, Year {year}"
if precision == PRECISION_TIME:   stamp += f" · {hour:02d}:00"
return stamp
```

格式里的 `Year -14` 这种「负数年」是刻意的：世界观的「元年之前」天然是负数，
不必额外发明一套「公元前」说法。

## 4. 纪元：世界的「版本」

### 4.1 每个纪元从 0 年重新起算

```python
# apps/documents/models/document.py —— Era
length_years = models.FloatField("长度（年）", default=0.0)   # 0 = 开放式（没有终点）

@property
def start_year(self) -> float:
    return 0.0     # 永远从 0 开始

@property
def end_year(self) -> float | None:
    return self.length_years or None
```

这是整个纪元设计里**最需要解释的一个决定**。

在真实历史里，「公元前 / 公元后」是两套编号打在同一根轴上。但虚构世界常常是
**断裂**的：上一个纪元被大灾变终结，新的纪元重新纪元——两段之间没有可比的刻度。
所以这里不去拼一根连续的绝对时间轴，而是让**每个纪元有自己独立的年份坐标系**，
都从自己的 0 年开始。

好处是：作者可以放心地在「第二纪元 500 年」记事件，不必担心它和「第一纪元 500 年」
冲突；纪元之间靠**排列顺序**（`position`）而不是年号连起来。

### 4.2 纪元在轴上的位置是「排出来的」

纪元的长度可以留空（开放纪元）。要在一条横向时间轴上把它们摆出来，就需要给每个
纪元算一个起止位置。`apps/world/classic.py` 里的 `spans_for()` 负责这件事：

```python
# apps/world/classic.py —— spans_for
cursor = 0.0
for index, era in enumerate(world.eras.all()):
    if era.id in saved:                 # 1. 文档里存过位置 → 用它
        spans[era.id] = saved[era.id]
        cursor = max(cursor, saved[era.id][1])
        continue
    length = float(era.length_years or 0) or 50.0    # 2. 没存过 → 按长度顺次铺开
    spans[era.id] = (cursor, cursor + length)
    cursor += length                                 # 长度为空按 50 年占位
```

**优先级**：文档里存过的摆放（用户手动拖过）> 按 `length_years` 依次铺开。
「用户拖过就听用户的」是所有画布类交互的通用原则。

### 4.3 摆放位置存在哪

纪元的**起止位置**存在**时间线文档**的 `settings["era_spans"]` 里，形如
`{"3": [0, 120], "7": [120, 400]}`（键是纪元 id 的字符串）——因为同一个纪元在
不同时间线文档里可以摆在不同的地方。而纪元**本身**（名字、描述、配色）存在
`world_era` 表，全世界共享。

## 5. 日历计算：月视图与月相

`apps/world/calendarview.py` 是一个纯粹的**计算模块**（不碰数据库，只做数学），
它把一本日历渲染成一个月的网格。

### 5.1 月相：从「第几天」反推

卫星（月亮）只需要用户给两个数：**周期多少天**、**第几天是满月**。

```python
# apps/world/calendarview.py —— phase_of
cycle   = max(1.0, float(moon.get("cycle_days") or 28))
full_on = float(moon.get("full_on") or 1)
new_on  = full_on - cycle / 2.0                    # 满月往回推半个周期 = 新月
offset  = ((day_number - new_on) % cycle + cycle) % cycle   # 保证落在 [0, cycle)
ratio   = offset / cycle                           # 0 = 新月，0.5 = 满月
index   = int((ratio * 8 + 0.5)) % 8               # 八分之一格 → 八个相名
illumination = (1 - math.cos(ratio * 2 * math.pi)) / 2      # 亮度 0..1
```

**算法要点**：
- 用户给「满月在第几天」比给「新月在第几天」更直观（肉眼更容易认满月），所以先由满月反推新月。
- `((x % n) + n) % n` 是 Python 里把取模结果强行拉回非负的惯用写法（`%` 对负数会返回负值）。
- 相位比例 `ratio` 直接映射到 8 个相名（新月→娥眉月→上弦月→盈凸月→满月→亏凸月→下弦月→残月）。
- 亮度用余弦曲线算：新月 0、满月 1，中间平滑过渡，比线性更接近真实。

### 5.2 展示策略：不是每晚都要画月亮

```python
# apps/world/calendarview.py —— moon_phases
shown = moon.get("shown") or "quarters"
if shown == "full_only" and info["phase_index"] != 4:                 continue  # 只画满月
if shown == "quarters"  and info["phase_index"] not in (0, 2, 4, 6):  continue  # 只画四相
```

三档策略：`every_night`（每晚都画）/ `quarters`（只画上弦、满月、下弦、新月）/
`full_only`（只画满月）。默认 `quarters`——月视图上密密麻麻全是月亮反而看不清日期。

### 5.3 「第几天」：跨年连续

月相必须能跨年连续（否则每年 1 月 1 日月亮都会重置）。`day_of_year()` 从「历法原点」
算起一个绝对天数：

```python
# apps/world/calendarview.py —— day_of_year
before = sum(m["days"] for m in months[: month - 1])       # 这个月之前已经过了多少天
return year * calendar.days_per_year + before + (int(day or 1) - 1)
```

**负数年也成立**：`year` 是负数时结果仍是连续递减的整数，月相因此可以一路往回算。

### 5.4 月视图网格

```python
# apps/world/calendarview.py —— month_grid
offset = int(year * calendar.days_per_year) % 7   # 该月第一天落在星期几
```

用「当年已过天数对 7 取模」决定首日列位，保证**同一历法下每一年都自洽**——
不会出现「某年的 1 月 1 日突然从周三跳到周六」。

网格搭好后，`place_events()` 把事件按「年 / 月 / 日」塞进对应的格子：

```python
# apps/world/calendarview.py —— place_events
if grid["month"] == month and getattr(event, "year", 0) == grid["year"]:
    day = min(max(int(getattr(event, "day", 1) or 1), 1), grid["days"])   # 越界日夹回
```

**粗精度事件怎么落格**：只精确到月的事件，会被放到该月第 1 天（month 有了、day 默认 1）；
这符合「越模糊越靠前」的一贯原则。

## 6. 经典时间线：把老编辑器整个嵌进来

### 6.1 为什么会有「两套时间线」

工作区里的时间线文档用 `TimelineEvent`（四级精度、纪元、关联卡片）这套新模型；
但项目里还有一套**独立开发的横向时间线编辑器**（`timeline` 应用，页面在 `/legacy`），
它的拖拽、缩放、分屏等交互更完整。

与其重写一遍，不如**把它嵌进工作区复用**：`apps/world/classic.py` 就是两者之间的**适配层**。

### 6.2 嵌入的做法

`timeline` 页面的脚本原先写死请求 `/api/timeline`、`/api/items*`、`/api/view`。
嵌入时模板在脚本之前**注入一段 fetch 适配层**，把这些地址改写到当前时间线文档上：

```
/api/timeline        →  /api/world/timelines/<doc_id>/classic
/api/items           →  /api/world/timelines/<doc_id>/classic/items
/api/items/<id>      →  /api/world/timelines/<doc_id>/classic/items/<id>
/api/view            →  /api/world/timelines/<doc_id>/classic/view
```

编辑器**一行都不用改**——这是「适配层」这个模式的价值：让两个本来不认识彼此的
系统通过一层转换对话，各自保持干净。

### 6.3 两种数据形态怎么互转

| 经典编辑器 | world 时间线文档 |
| --- | --- |
| `kind="event"` + 浮点年 | `TimelineEvent`（四级精度） |
| `kind="era"` + 起止年 | `Era` + 文档 `settings["era_spans"]` |
| `cards: [{title, url, …}]` | 事件的 `linked_cards`（按名字匹配卡片） |
| `view: {start, end}` | 文档 `settings` 的 `view_start` / `view_end` |

**桥梁是「浮点年」**。经典编辑器把时间当成一根连续的数轴（3.5 = 第 3 年过半），
而 `TimelineEvent` 存的是离散的年月日时。两者靠一对函数互转：

```python
# apps/world/classic.py —— event_to_float：四级精度 → 浮点年
value = float(event.year or 0)
if event.precision in ("month", "day", "time"):
    value += (max(1, event.month or 1) - 1) / 12
if event.precision in ("day", "time"):
    value += (max(1, event.day or 1) - 1) / (12 * 30)
if event.precision == "time":
    value += (event.hour or 0) / (12 * 30 * 24)
```

```python
# apps/world/classic.py —— float_to_parts：浮点年 → 四级精度（只拆到精度允许的位）
year = int(value // 1)
fraction = value - year + 1e-9          # epsilon 见下
...
```

**为什么有 `+ 1e-9`**：浮点数没法精确表示 `1/360` 这类小数。一个「第 5 天」的值
换算回来可能变成 `4.999999…`，`int()` 一截就成了「第 4 天」。
加一个极小的 epsilon 把「理论上正好落在边界」的值推进下一格，就稳定了。
这是**浮点比较**里非常常见的技巧。

### 6.4 用偏移量避开 id 撞车

经典编辑器要在一个数组里同时装事件和纪元，两者的 id 都得是数字。而 `Era` 和
`TimelineEvent` 是两张不同的表，id 会重复。解决办法是给纪元的 id 加一个大偏移：

```python
# apps/world/classic.py
ERA_ID_BASE = 1_000_000        # 纪元 id = 1_000_000 + 真实 id
```

任何 `>= ERA_ID_BASE` 的 id 都当纪元处理，其余当事件处理：

```python
# apps/world/classic.py —— delete_item
if item_id >= ERA_ID_BASE:
    era_id = item_id - ERA_ID_BASE
    ...   # 纪元只「解除摆放」，纪元本身保留
event = document.events.filter(pk=item_id).first()   # 事件才真正删除
```

**为什么删纪元不删纪元本身**：纪元是全世界的资产（描述、配色、封面），
在这个文档里「删掉」只意味着「不摆在这条轴上了」，不该连累别的时间线。

### 6.5 新建事件的默认精度

```python
# apps/world/classic.py —— apply_item
fallback = settings_.get("default_precision") or calendar.default_precision or "month"
# 经典编辑器按月走，兜底精度至少是「月」，否则年内新建的事件会被丢成 1 月
event.precision = (fallback if PRECISION_ORDER[fallback] >= PRECISION_ORDER["month"]
                   else "month")
```

编辑器在轴上以「月」为最小格，所以新建事件的默认精度**下限就是月**；
但如果调用方（工作区的事件面板）显式传了精度，就照它办。

## 8. 一句话小结

- **事件**声明自己精确到哪一级，**精度不到的位不参与排序**，越模糊越靠前。
- **日历**是读日期的规则；服务端负责容错与收拢越界值。
- **纪元**是**世界自己的坐标系**，每个纪元从 0 年起算，靠顺序而非年号相连。
- 工作区的时间线**复用了**那套独立的经典横向编辑器，靠一个 fetch 适配层 +
  浮点年桥接，让两套数据模型对话。
