# 导入导出与工具

> **文档版本：Dev 1.0**
>
> 这一篇讲两件事：
>
> 1. **怎么把内容搬进搬出**——把 Markdown 变成卡片、把整个世界打包成 zip、把旧数据导回来。
> 2. **工作区里的内置小工具**——表格、媒体库、骰子、语音、词典、看板、画布……
>
> 目标读者是**刚学会 Python、还没写过 Web 应用**的人。所有算法都会配例子与「为什么」，
> 读完之后你应该能自己写一个导入脚本。

---

## 1. 总览：搬进搬出的四种方式

工作区把「交换」拆成四类动作，每一类对应一个入口：

| 动作 | 格式 | 粒度 | 用什么 |
| --- | --- | --- | --- |
| **导出整个世界** | zip（Markdown + JSON 备份）或纯 JSON | 整个世界 | `GET /api/world/export` |
| **导出单份文档** | Markdown（默认）或 JSON | 一份文档 | `GET /api/world/documents/<doc_id>/export` |
| **导入文件** | Markdown / zip / world.json | 若干文档 | `POST /api/world/import` |
| **导入旧数据** | 旧格式 JSON | 经典时间轴条目 | 管理命令 `import_legacy_json` |

设计上有一个明确取舍，先说清楚，后面就好懂了：

> **导出以 Markdown 为主、JSON 为备份。**
> Markdown 是给「人」和「别的工具」看的，拿去 Obsidian、Typora 都能打开；
> JSON 是给「工作区自己」看的，能原样导回来、保住层级与属性。

一句类比：Markdown 是**打印稿**，JSON 是**施工图**。打印稿好看但丢了结构，
施工图丑但能把房子一模一样再盖一遍。

## 2. Markdown 导入

### 2.1 一次导入要走的路

当你在工作区里选了一堆 `.md` 文件点「导入」，前端把文件发给 `POST /api/world/import`，
后端（[world/services/exchange.py](../world/services/exchange.py)）大致做这几步：

```
收到文件
  │
  ├─ ① 拆包：zip 递归展开成一个个文本文件；普通 .md 直接收下
  │
  ├─ ② 判断是不是备份：文件名以 .json 结尾且内容里有 "documents" → 走"备份还原"
  │
  ├─ ③ 逐个处理 Markdown：
  │      ├─ 按文件名/目录名决定放到哪个文件夹（文件夹不存在就建）
  │      ├─ 取 "# 标题" 当文档名（没有就用文件名）
  │      ├─ 把正文段落解析成"区块"
  │      └─ 建一个 Document(type=card) + 一张 Card，写入区块
  │
  └─ ④ 返回统计：{created, folders, documents}
```

### 2.2 文件名、标题、层级：谁决定文档名

导入时文档名的取值优先级是这样：

1. 正文里第一个 `# 一级标题` 的内容；
2. 没有一级标题，就用文件名去掉扩展名（`.md` / `.markdown` / `.txt`）。

**一级标题不会被当成正文**（`markdown_to_blocks` 里遇到 `# ` 直接跳过），
因为它已经升级成了文档名，留着会重复。

**目录决定层级。** 传入的文件名可能自带路径，比如：

```
世界设定/人物/Isarra.md
世界设定/人物/Sera.md
世界设定/地点/Harrowdeep.md
```

导入算法（`import_markdown_files` 里的 `folder_for`）会：

- 把路径按 `/` 切开，去掉文件名本身；
- 从最外层开始逐级找文件夹，**没有就新建一个 `Document(type=folder)`**；
- 把文件挂到最后一层文件夹下。

于是上面三份文件会得到这样一棵树：

```
世界设定/
├── 人物/
│   ├── Isarra
│   └── Sera
└── 地点/
    └── Harrowdeep
```

它用了一个「**路径 → 文件夹对象**」的缓存（`folders` 字典），
保证同一个目录只建一次，不会因为文件多就重复建文件夹。

> 这个「按 `name="/".join(已走过的层级)"` 当 key」的做法值得记一下：
> 它是处理树形路径的通用套路——**先把路径规范化成字符串 key，再查缓存**。

### 2.3 标题层级 → 区块

一份文档在数据库里不是一整块 HTML，而是一串**区块（block）**。每个区块长这样：

```python
{"id": "b1", "type": "text", "title": "概览", "text": "……"}
```

导入时 `markdown_to_blocks` 把 Markdown 的标记映射成区块类型：

| Markdown 写法 | 变成什么 | 说明 |
| --- | --- | --- |
| `## 标题` | `type="heading"`，`title` 是标题文字 | 二级标题 = 一个标题区块 |
| `### 标题` | `type="text"`，`title` 是标题文字 | 三级标题 = 带小标题的正文块 |
| `> 引用` | `type="quote"` | 连续多行 `>` 合成一个引用块 |
| `> [!info]` | `type="callout"` | 提示框 |
| `---` / `***` / `___` | `type="divider"` | 分隔线 |
| 普通段落 | `type="text"` | 默认类型 |

解析用的是**逐行扫描 + 缓冲**的状态机，核心思路是：

```
遇到"开新块"的标记（##、>、---）
  → 先把缓冲区里攒的正文 flush 成一个区块
  → 再开一个新当前块
遇到普通行
  → 往缓冲区里追加
文件结束
  → 最后再 flush 一次（别忘了收尾）
```

`flush()` 里还会做两件变形：

- **行内排版保留一点**：`**粗体**` → `<b>`，`*斜体*` → `<i>`，`` `代码` `` → `<code>`，
  行首的 `- ` 列表符 → `• `。这样导入后正文不至于全变成白开水。
- **`[[双链]]` 变提及**：见下一节。

### 2.4 `[[双链]]` 与别名：把文字变成可点的链接

Markdown 里常见的 `[[卡片名]]` 会在导入时被**尽量接成指向卡片的链接**：

```python
WIKI_LINK = re.compile(r"\[\[([^\]|]+)(?:\|([^\]]+))?\]\]")
```

它认两种写法：

- `[[Harrowdeep]]`：只写卡片名；
- `[[Harrowdeep|深港]]`：竖线后面是**显示文字**（链接仍指向 Harrowdeep）。

替换逻辑（`_link_mentions`）：

1. 拿卡片名去当前世界里找同名文档（忽略大小写）；
2. 找不到，再拿它去比对各张卡片的**别名**；
3. 还找不到——**保持纯文本**（宁可不变，也不硬造一个死链）。

找到后输出一段带标记的 HTML，前端据此渲染成可点、可悬浮预览的链接：

```html
<span class="mentions-inline" data-target="42">深港</span>
```

> **为什么用 `data-target` 而不是直接写死 URL？**
> 因为卡片的 URL 在重建世界、导入导出后可能变化。只存一个「目标文档 id」，
> 前端渲染时再拼链接，链接就不会失效。

### 2.5 导入后的正文为什么一定干净

解析出的区块最后会过一遍 `normalize_blocks`，写库前 HTML 还要过**白名单净化**
（[world/services/sanitize.py](../world/services/sanitize.py)）。卡片正文是可编辑的富文本，
浏览器（尤其是粘贴时）会塞进各种标签，甚至 `script`。

净化器的规则：

| 类别 | 处理 |
| --- | --- |
| 允许的标签 | `p br b strong i em u s strike del code mark ul ol li blockquote span a h1 h2 h3` |
| 允许的属性 | 只有 `<a>` 的 `href`、`<span>` 的 `data-target` 与 `class` |
| 允许的 class | `<span>` 只留 `mentions-inline` |
| 危险标签 | `script style iframe object embed template svg` **连内容一起丢掉** |
| 链接协议 | 只放行 `http:// https:// mailto: / #`，`javascript:` 之类一律删掉 |

它不是「过滤字符串」，而是用 Python 的 `HTMLParser` **重新拼一棵合法的标签树**：
能保留的标签按原样输出，属性逐条审查，没闭合的标签自动补上 `</…>`。
解析一旦出错，**退化成纯文本**（`escape` 转义），绝不把没洗过的原文存进库。

> 一句话记住：**「什么值算合法」归 `normalize.py`，「哪段 HTML 能存」归 `sanitize.py`。**

## 3. Markdown 导出

导出做的事，正好是导入的**逆过程**：把一棵文档树拍平成文本文件。

### 3.1 一份文档怎么变成 Markdown

`document_markdown(document)` 负责单份文档。成品长这样：

```markdown
# Isarra Thornveil

- 类型：卡片
- 别名：The Untreated
- 卡片类型：角色
<!-- 由世界工作区导出 -->

| 属性 | 值 |
| --- | --- |
| 角色定位 | 外交官 |
| 阵营 | The Balri Accords |
| 年龄 | 41 |

## 概览

Isarra Thornveil 是记载中最具分量的外交官之一……

## 早年

关于她的早年记载很少……
```

拆解一下：

- **第一行 `# 文档名`**——对齐导入时「一级标题当文档名」的规则，导入导出能来回。
- **元信息列表**——类型（用中文标签）、别名、是否隐藏、卡片类型。
- **属性表**（`property_lines`）——遍历卡片的**有效类型**（含继承来的）全部属性，
  有值的才写一行；值是数组时用 `、` 连接。
  表格里的 `|` 和换行会被转义（`_escape_cell`），免得把表格撑破。
- **区块正文**（`block_lines`）——按区块类型分别序列化：

| 区块类型 | 导出成 |
| --- | --- |
| `heading` | `## 标题` |
| 其它带 `title` 的块 | `### 标题` + 正文 |
| `quote` | 每行前加 `> ` |
| `callout` | `> [!info]` + 每行 `> ` |
| `divider` | `---` |
| 带评论的块 | 追加一行 `<!-- 评论（未解决）作者：内容 -->` |

隐藏的区块（`hidden=True`）直接跳过不导出。

### 3.2 特殊文档类型

不是所有文档都是卡片。导出时针对不同 `document_type` 走不同分支：

| 文档类型 | 导出内容 |
| --- | --- |
| `timeline` | `## 事件` 下逐条列出事件（按年/月/日/时排序），带关联卡片 |
| `familyTree` | `## 成员`（节点）+ `## 关系`（`A → B（关系）`） |
| `map` | `## 标注` 下逐条列出地图标记及其关联卡片 |
| 其它（卡片/笔记/看板…） | 属性表 + 区块正文 |

### 3.3 整树导出成 zip

`world_zip(world)` 把整个世界打成一个 zip：

```
world.json            ← 完整备份（下一节讲）
README.md             ← 说明这个包里有啥
documents/
├── 人物与势力/
│   ├── Isarra Thornveil.md
│   └── Sera Thornveil.md
└── 地点/
    └── Harrowdeep.md
media/index.md        ← 媒体清单（图片本身仍在原地址）
```

**文件名去重**是个小细节：不同文件夹下可能有同名文档，同一个 zip 里如果重名会冲突。
`unique()` 会把名字里的非法字符换成 `-`，重名时追加 `-2`、`-3`……

> **为什么用 BFS（广度优先）遍历而不是递归？**
> 导出时要给每份文档算出它在 zip 里的**目录前缀**（如 `人物与势力/`）。
> 用显式队列（`stack.pop(0)`）一层层往下走，前缀随手拼就好，
> 不用担心递归深度，也不会因为目录太深而爆栈。

## 4. JSON 导入导出

### 4.1 备份结构（`world_backup`）

`world_backup(world)` 生成整世界的 JSON。顶层字段如下：

```json
{
  "format": "worldbuilding-timeline/backup",
  "version": 1,
  "exported_at": "2026-10-14T12:00:00+08:00",
  "world": { "...世界自身的属性与主题设置..." },
  "types": [ "...类型定义（含属性定义 with_properties=true）..." ],
  "eras": [ "...纪元..." ],
  "calendars": [ "...日历..." ],
  "documents": [ "...文档树（递归，每份文档带 children）..." ]
}
```

`world` 那份文档树是**递归**的，每份文档的结构（来自 `document_payload`）：

| 字段 | 含义 |
| --- | --- |
| `type` | 文档类型（`card` / `timeline` / `map` / `familyTree` …） |
| `name` | 名称 |
| `settings` | 该文档的工具设置（各类型自己解释） |
| `cover` | 封面地址 |
| `card` | 若是卡片：`aliases`（别名）、`blocks`（区块）、`values`（属性值，键是属性 id） |
| `events` | 若是时间线：事件数组 |
| `variants` | 若是关系树：`{id, name, nodes[], edges[]}` |
| `layers` / `markers` | 若是地图：图层与标记 |
| `children` | 子文档数组（递归） |

导出时只带**未删除**的文档与子节点（`deleted_at` 为空），回收站里的东西不打包。

### 4.2 导出接口

```bash
# 整个世界 zip（默认）
curl -O -J http://127.0.0.1:8000/api/world/export

# 只要 JSON 备份
curl -O -J "http://127.0.0.1:8000/api/world/export?format=json"

# 单份文档：默认 Markdown
curl -O -J http://127.0.0.1:8000/api/world/documents/12/export

# 单份文档：要 JSON
curl -O -J "http://127.0.0.1:8000/api/world/documents/12/export?format=json"
```

下载文件名会带上世界/文档名与时间戳（形如 `我的世界-20261014-1200.zip`），
非法字符会被替换，保证能存到磁盘。

### 4.3 导入备份

导回来的入口还是 `POST /api/world/import`，它靠**内容特征**来判断这是不是备份：

```
文件名以 .json 结尾，且内容里有 "documents" → 认为是 world.json 备份
```

也可以用 JSON 请求体显式指定：

```json
{ "mode": "backup", "content": { "format": "...", "documents": [ ... ] } }
```

还原逻辑（`import_backup`）尽量**保住原来的层级**：

- 从 `documents` 的顶层开始，逐个建 `Document`；
- 有 `card` 字段就补建 `Card`（别名、区块、属性值都还原）；
- 递归处理每份文档的 `children`。

导入的文档挂在**当前世界**下。所以「把 A 世界的备份导进 B 世界」是允许的——
这正是迁移、合并的用法。

## 5. 导入旧的时间轴数据：`import_legacy_json`

经典的横向时间轴由 `timeline` 应用单独提供，它历史上把数据存成一份 JSON 文件，
格式是：

```json
{
  "view": { "start": 1500, "end": 1900 },
  "items": [ { "kind": "era", "title": "..." }, { "kind": "event", "start": 1602, ... } ]
}
```

（早期版本只存一个数组，命令也认。）

要把这种文件灌进数据库：

```bash
# 同 id 覆盖，没有 id 的当新记录
.venv/bin/python manage.py import_legacy_json 备份.json

# 先清空条目表再导入（视野设置不受影响）
.venv/bin/python manage.py import_legacy_json 备份.json --replace
```

命令（[timeline/management/commands/import_legacy_json.py](../timeline/management/commands/import_legacy_json.py)）
其实只做了一层薄封装：把文件交给 `timeline.legacy.import_legacy_file` 去读、去写。

两个注意点：

- **必须显式给出文件路径**。项目里不再自带示例数据文件；路径读不到会直接报错，
  **绝不会偷偷往库里写示例数据**——这是故意的，免得生产环境被塞进一份演示内容。
- `--replace` 只清空**时间轴条目表**，不动视野（view）那一条设置。

> 如果只是想「把经典时间轴里的内容搬进世界工作区」（变成世界里的时间线文档、
> 纪元、卡片），那是另一条命令 `import_timeline` 的活，它做的是**模型之间的转换**，
> 不是文件导入。两者不要混。

## 6. 工作区的内置小工具

工作区里除了卡片、时间线、关系树、地图这些「大件」，还有一批轻量工具。
它们的共同点是：**本质上都是一份 `Document`，只是 `document_type` 不同**。
可在 [world/models/constants.py](../world/models/constants.py) 的 `DOC_TYPES` 里看到全表：

| `document_type` | 中文名 | 一句话 |
| --- | --- | --- |
| `folder` | 文件夹 | 树节点，只用来装东西 |
| `card` | 卡片 | 世界的原子：属性 + 区块正文 |
| `timeline` | 时间线 | 挂在世界上的事件流 |
| `map` | 地图 | 图层 + 图钉/区域/标注 |
| `canvas` | 画布 | 自由排布的便签画布 |
| `board` | 看板 | 分栏的卡片墙 |
| `note` | 笔记 | 纯文本记录 |
| `table` | 表格 | 把某一类卡片摊成一张表（见下） |
| `familyTree` | 关系树 | 家谱 / 组织架构 |
| `graph` | 世界图谱 | 世界关系的可视化 |
| `dictionary` | 词典 | 造语词条 |
| `todo` | 待办清单 | 勾选事项 |
| `voice` | 语音备忘 | 浏览器录音 |
| `dice` | 骰子 | 可存档的骰组 |
| `soundscape` | 环境音 | 分层、WebAudio 合成 |
| `radar` | 雷达图 | 多维对比 |
| `chapter` | 章节 | 写作分章 |
| `media` | 媒体库 | 图片 / 文件收藏 |
| `embed` | 链接嵌入 | 外链卡片 |

### 6.1 工具怎么存数据：一个统一入口

绝大多数工具**不需要专属后端接口**。它们的私货全部塞进文档的 `settings.data`，
由前端自己解释结构。读写走同一个入口：

```
GET  /api/world/documents/<doc_id>/data   → 取 {document, data, media, revision}
PUT  /api/world/documents/<doc_id>/data   → 覆盖 data（必须是对象，约 400 KB 上限）
```

设计意图很清楚：**新加一个工具，只要前端定一份数据 spec，后端一行都不用改**。

- 数据是「整体覆盖」式保存（不是逐字段 patch），简单可预期；
- 超限会返回错误，避免有人把大文件塞进 JSON 把库撑爆（文件另走媒体接口）。

### 6.2 媒体库与语音：`document_media`

图片、语音这类**二进制文件**不走 JSON，走媒体接口
（[world/views/content.py](../world/views/content.py) 的 `document_media`）：

```
POST   /api/world/documents/<doc_id>/media   ← 上传（multipart，字段名 file）
DELETE /api/world/documents/<doc_id>/media?id=<媒体 id>   ← 删除
```

上传时后端的动作：

1. 检查大小（超过 **25 MB** 拒绝）；
2. **检查内容类型**——只放行白名单里的类型（位图 / 音视频 / PDF / 纯文本）；
3. 把文件名里的非法字符替换掉，存到 `docs/<doc_id>/<文件名>` 下（`default_storage`）；
4. 生成一条媒体记录，写进 `settings.media`：

```json
{
  "id": "AbC123xy",
  "name": "portrait.png",
  "title": "角色立绘",
  "kind": "image",
  "path": "docs/12/portrait.png",
  "size": 204800,
  "content_type": "image/png",
  "url": "/media/docs/12/portrait.png",
  "created_at": "2026-10-14T12:00:00+08:00"
}
```

删除时**先把文件从磁盘删掉，再把记录从列表里去掉**（找不到文件也不报错，
保证记录能清干净）。

> **为什么「文件落盘、元数据进 `settings`」？**
> 因为 JSON 字段不适合存大二进制。把「文件在哪」和「文件本身」分开，
> 备份、迁移、删库都简单：JSON 里只有一份清单，真正的图在 `media/` 目录。

> **为什么内容类型要卡白名单？**
> 上传文件经 `/media/…` 是**按响应类型渲染**的：`image/svg+xml`、`text/html`
> 能被塞进脚本，直链打开就跑在本站源下——存储型 XSS。所以白名单刻意不含 SVG / HTML，
> 且响应带 `X-Content-Type-Options: nosniff`。校验只放行位图、音视频与 PDF / 纯文本。
> 统一走 [world/views/common.py](../world/views/common.py) 的 `_upload_problem`（媒体库与地图底图共用）。

### 6.3 表格引擎：最复杂的那个工具

表格不是「一张独立的表」，而是一个**视图**——它把世界里的**某一类卡片**摊平成表格：

- 列 = 该类型的属性（`PropertyDef`）；
- 行 = 该类的一张张卡片。

所以「在表格里改一个单元格」= 「改那张卡片的属性值」，这就是**双向绑定**。

#### 读表格（`GET /api/world/tables/<doc_id>`）

`table_payload` 的流程：

1. 取表格文档配置里的 `entity_type`（盯着哪一类卡片）；
2. 拿出该类型的全部属性当候补列；
3. 取世界里未删除、类型匹配的卡片当行（**上限 400 行**）；
4. 应用**筛选** → **排序** → **分组**：
   - 筛选支持 `contains / is / is_not / gt / lt / empty / not_empty`；
   - 排序按属性值；
   - 分组把行按某个属性的取值分桶；
5. 算 `aggregates`（求和、计数之类）；
6. 给一个 `schema` 指纹（类型 + 属性的特征串），前端据此判断「表结构是否变过」。

视图设置（筛选/排序/分组/隐藏列/列宽）统一收在 `settings.table.view` 里，
`_table_view()` 负责把它归一化——**读旧数据时若缺字段，一律当「没设」**，
行为跟一张新表一致。

#### 改一个单元格（`PUT /api/world/tables/<doc_id>/cell`）

```
请求体：{ "row": <卡片文档 id>, "column": <属性 id>, "value": ... }
```

后端找到那一行对应的卡片，调用 `coerce_property_value` 把值**按属性类型清洗**，
写回 `card.values`，然后**只返回这一行**（+ 结构指纹）。

> **为什么要「只回一行」？** 因为前端会先做**乐观更新**（不等服务器就先改界面），
> 拿到返回值后再校正。整表重载既慢又会让光标/滚动位置乱跳。

传 `"name"` 而不是列时，改的是那一行卡片的**名字**。

#### 加行 / 删行（`POST` / `DELETE /api/world/tables/<doc_id>/rows`）

- `POST`：**新建一张卡片**（自动带上该类型的默认值）当新行；
- `DELETE`：把那一行对应的卡片**软删除**（`deleted_at` 打时间戳）——
  所以删掉的行还能在回收站里找回。

#### CSV 进出（`GET` / `POST /api/world/tables/<doc_id>/csv`）

- `GET`：按**当前视图**（已筛选/排序/分组后的样子）导出 CSV，
  表头是 `名称` + 各列名，用 UTF-8，方便 Excel 直接打开；
- `POST`：导入 CSV。**按「名称」列匹配已有行**：
  - 名称对得上 → 更新那张卡片的属性；
  - 对不上 → 新建一张卡片。

匹配用「名称」而不是 id，是为了让你能在 Excel 里随便改、随便加行，再导回来。

> **CSV 导入的一个注意点**：列是按**属性名**（表头文字）去匹配属性定义的，
> 表头名字和属性名对不上时那一列会被跳过（不报错）。导出再原样导入最稳。

## 8. 小结

- **导出**：整世界打包成 zip（Markdown + JSON 备份 + 媒体清单），或单独导一份文档。
- **导入**：文件靠内容特征分流——有 `"documents"` 的 `.json` 走备份还原，
  其余当 Markdown 逐份解析成卡片；目录名建文件夹，`#` 标题当文档名。
- **Markdown 是打印稿，JSON 是施工图**：前者给人看，后者用来原样重建。
- **正文入库前过白名单净化**，只留排版标签，危险标签连内容一起丢。
- **小工具共用一个数据入口**（`settings.data`）与一个媒体入口（`document_media`）；
  **表格本质是「某一类卡片的视图」**，改格子就是改卡片。
