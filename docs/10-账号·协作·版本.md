# 账号·协作·版本

> **文档版本：0.4.0-dev**
>
> 这份文档讲清楚三件相关的事：**谁可以进这个世界、谁可以动手改、改过之后怎么找回旧版。**
> 依次覆盖：权限模型的五条规则与角色取值、判定权限的那几个函数、系统怎么知道"现在在做哪个世界"、
> 注册与登录的流程、邀请码与协作成员的管理、谁在线的判定，以及文档版本历史与回滚。
> 读之前你只需要知道：整个世界是"读永远公开、写要登录且有权限"，其余规则都是从这一条长出来的。

---

## 1. 一句话理解这三件事

把世界想象成一间共用的画室：

- **账号**决定"谁有门禁卡"——能进门，才有机会提笔。
- **协作**决定"谁的卡能开哪间房、能干什么"——有人只能看，有人能画，有人能换锁（管成员）。
- **版本**是"每一步都留底稿"——画错了、改砸了，能对着某一版说"就回到这里"。

三者共用一套"我是谁、我在哪个世界、我能干什么"的判断，这套判断就是权限模型。

## 2. 权限模型：五条规则

全部权限逻辑收在 `apps/world/permissions.py` 里，规则只有五条：

| 规则 | 内容 | 为什么这样定 |
| --- | --- | --- |
| 1. 读永远公开 | 任何人不登录都能读：发布出来的站点对读者开放，工作区也允许游客浏览 | 只读站点本来就是给外人看的，不该拦 |
| 2. 写要身份 | 想改内容必须登录，**并且**在这个世界里是 `owner` 或 `editor` | 写作是协作行为，得知道是谁改的、有没有资格 |
| 3. 一人一世界 | 注册就得到一个属于自己的世界，之后还能再建更多；受邀注册则加入邀请码指向的那个世界 | 每个人有自己的地盘，避免都挤进同一个演示世界 |
| 4. 首次安装例外 | 数据库里一个用户都没有时，**允许任何人写** | 好让第一个注册的人先把世界建起来（这也是"第一个注册者成为所有者"的实现） |
| 5. 超管无视限制 | 只有超级管理员（`is_superuser`）不受上面任何限制；工作人员（`is_staff`）不再穿透，只能进自己拥有 / 受邀加入的世界 | 留一个能救火的最高权限，但"能登录 admin 后台"不等于"能读改所有人的私有世界"（S7） |

> "读"和"写"的分界线很关键：**能不能读到**和**能不能改到**是两回事。
> 一个未登录的游客可以读，但一旦发出写请求，就会被中间件拦下来（详见第 4 节）。

### 2.1 角色取值

角色定义在 [apps/world/models/membership.py](../apps/world/models/membership.py) 的 `Membership` 上，一共三个：

| 常量 | 取值 | 中文标签 | 能做什么 |
| --- | --- | --- | --- |
| `ROLE_OWNER` | `owner` | 所有者 | 编辑 + 管成员 + 发邀请码 + 发布 |
| `ROLE_EDITOR` | `editor` | 可编辑 | 编辑内容；不能管成员 |
| `ROLE_VIEWER` | `viewer` | 只读 | 只能看，改不动 |

`Membership.can_edit()` 就是一句话：`role in (owner, editor)`。

除了上面三个"世界内角色"，还有两个"身份"要分清：

| 身份 | 何时出现 | `role_of()` 返回 |
| --- | --- | --- |
| 未登录访客 | 匿名请求 | `"guest"` |
| 已登录但不是这个世界的成员 | 登录了，却没加入当前世界 | `ROLE_VIEWER`（只能读） |
| 超级管理员 | `is_superuser` | `ROLE_OWNER`（按所有者对待） |
| 工作人员（非超管） | `is_staff` 但非 `is_superuser` | 与普通用户同权：只进自己拥有 / 受邀加入的世界 |

> 也就是说：**登录本身不等于有编辑权**。登录了却不在这个世界里，依然只是只读。

### 2.2 平台身份 vs 世界角色

上面那套是**世界内角色**（在某个世界里你是 `owner` / `editor` / `viewer`）。与之正交的是**平台身份**——
你站在"整个站点"这一层算什么人。两者不是一回事：平台身份决定"能不能治理站点"，
世界角色决定"能不能改某个世界里的内容"。

平台身份规划成四层，分三批落地（进度 = A 安全 → B 骨架 → C 功能）：

| 平台身份 | 判据 | 能做什么 | 落地状态 |
| --- | --- | --- | --- |
| 站长（`superuser`） | `is_superuser` | 全部权限：无视世界边界、能进 `/admin/`、任命管理员 | 已有 |
| 管理员（`moderator`） | 属于"管理员"用户组 | 由站长任命；封禁 / 解封公开 wiki（3–7 日，到期自动解封） | 批次 B / C 已落地 |
| 工作人员（`staff`） | `is_staff` | 与普通用户同权（S7 起不再穿透） | 已有 |
| 普通用户（`user`） | 其余登录用户 | 只在自己拥有 / 受邀加入的世界里按角色行事 | 已有 |

> **后台只对站长开放（批次 A）。** `/admin/` 用自定义站点 `OpusculeAdminSite`
> （`apps/world/admin.py`，经 `apps/world/adminconfig.py` 的 `default_site` 接管）：它的 `has_permission`
> 只认 `is_superuser`。Django 默认是 `is_active and is_staff`——任何 staff 都能进后台给自己
> 或别人点权限，这正是要堵的"借超管的浏览器自设 staff"。收紧后 staff 依旧只是普通用户，
> 后台的门只给站长开（用户与用户组的后台管理也随之对站长开放，任命管理员靠的就是用户组）。

> **治理留痕落在 `ModerationEvent`（批次 A）。** 任命 / 撤销管理员、封禁 / 解封这类**跨世界**的
> 平台级动作，记进 `ModerationEvent`（只增不改，仿世界内的成员审计 `MemberEvent`；写入助手
> `views._log_moderation_event()`，取值见 `models.MODERATION_ACTIONS`）。两者的作用域刻意分开：
> `MemberEvent` 记"某个世界里谁改了谁的角色"，`ModerationEvent` 记"站点这一层谁对谁做了什么"。
> 后台里对它是**只读**的（能看能筛，不能改不能删）。

> **任命管理员靠用户组（批次 B）。** 管理员身份**不新增模型 / 迁移**，直接落在 Django 内置的
> `Group`（组名 `permissions.MODERATOR_GROUP = "moderator"`）：任命 = 把人加进组，撤销 = 移出。
> 判定集中在 `apps/world/permissions.py`——`is_moderator()` 严格看组（站长不算组内身份）、
> `platform_role_of()` 按"站长 > 管理员 > 工作人员 > 普通用户"返回唯一标签、`can_moderate()`
> 表达"能不能治理站点"（站长或管理员）、`set_moderator(user, on)` 幂等地加 / 减组。
> 站长在 **`/api/world/moderators`** 上管理名单（`GET` 列出、`POST {user_id}` 任命、
> `DELETE /api/world/moderators/<user_id>` 撤销），只有 `is_privileged` 能碰，每次实质性变更
> 都写一笔 `ModerationEvent`（`appoint` / `dismiss`）。

> **封禁与举报（批次 C）。** 封禁是**世界级**动作：封的是一个已发布的公开 wiki。`World` 上
> 加 `banned_until` / `ban_reason` 两个字段，`World.is_banned` 是**惰性判断**（`banned_until > now`）——
> 到期即自动恢复，**不需要任何定时任务**。拒绝入口只有一处：`site_views._get_world()` 对被封
> 站点直接 `Http404`，因此首页 / 搜索 / 纪元 / 文档页 / feed / og 一并失效。执法面在
> `/api/world/moderation`（`GET` 看状态、`POST …/ban`、`POST …/unban`），守门 `can_moderate`
> （站长**或**管理员），时长夹在 3–7 日；每次封 / 解封写一笔 `ModerationEvent`（`ban` / `unban`）。
> 举报则相反——**只有站长**（`is_privileged`）能看与处置：读者在只读站点上匿名提交
> （`POST /s/<slug>/report`，落 `Report` 模型，顺带记来源 IP），站长在 `/api/world/reports`
> 上查看与流转（`open` / `handled` / `dismissed`）；管理员**不在举报流转里**。

## 3. 判定权限的几个函数

权限不是散落在各个视图里现算的，而是集中在几个函数里。看懂它们，就懂了整个账号体系。

### 3.1 你是谁的成员、能进哪些世界

```python
def worlds_for(user):
    """这个用户能进的世界：自己拥有的 + 有成员身份的。超级管理员看全部。"""
    if not user or not user.is_authenticated:
        return World.objects.none()              # 游客：一个都进不了
    if is_privileged(user):
        return World.objects.order_by("id")      # 超管：全部
    return (
        World.objects.filter(Q(owner=user) | Q(memberships__user=user))
        .distinct().order_by("id")               # 自己拥有的 + 加入过的
    )
```

一个世界的"能进"有两种来源：**你是它的 `owner`**，或者**你在它的成员表（`Membership`）里**。

### 3.2 能不能进这个世界

| 函数 | 判定 | 游客（未登录） | 已登录成员 | 超管 |
| --- | --- | --- | --- | --- |
| `can_access(user, world)` | 能否进入该世界的工作区 | 对兜底世界返回真 | 在自己的世界返回真 | 永远真 |
| `can_edit(user, world)` | 能否改内容 | 假（除非还没账号） | `owner`/`editor` 为真 | 永远真 |
| `can_admin(user, world)` | 能否管成员与邀请码 | 假 | 只有 `owner` 为真 | 永远真 |

三个函数都共享同一条"首次安装例外"：

```python
def can_edit(user, world):
    if not users_exist():
        return True                     # 首次安装：先让人把世界建起来
    if not user or not user.is_authenticated:
        return False
    if is_privileged(user):
        return True
    membership = membership_for(user, world)
    return bool(membership and membership.can_edit())
```

`can_admin` 与它几乎一样，只是最后一行换成了 `membership.role == ROLE_OWNER`。

### 3.3 给前端的"我是谁"

前端需要一个统一的口径来渲染界面（比如"要不要显示编辑按钮""要不要显示成员管理"）。这个口径由 `viewer_payload()` 产出：

| 字段 | 含义 |
| --- | --- |
| `authenticated` | 是否已登录 |
| `needs_setup` | 是否还没任何账号（前端据此跳"创建所有者账号"） |
| `username` / `handle` / `initial` | 显示名 / 用户名 / 头像首字母 |
| `role` / `role_label` | 角色取值与中文标签 |
| `can_edit` / `can_admin` | 上面两个判定的结果 |
| `joined` | 你是否这个世界的成员 |
| `platform_role` / `platform_role_label` | 平台身份取值与中文标签（站长 / 管理员 / 工作人员 / 普通用户） |
| `is_moderator` / `can_moderate` | 是否管理员组成员 / 能否治理站点 |

> 前端只认这一份数据，**不在浏览器里自己重算权限**——真正的裁决永远在服务端。

## 4. 写操作守门人与"当前世界"

### 4.1 中间件的作用与顺序

`worldbuilding_timeline/settings.py` 里紧挨着装了三个自定义中间件，顺序不能乱：

```python
MIDDLEWARE = [
    # …Django 自带：Security / Session / Common / Csrf / Auth / Messages / XFrame…
    'apps.world.middleware.ActiveWorldMiddleware',      # 1. 先解析"当前世界"
    'apps.world.middleware.EditPermissionMiddleware',   # 2. 再对着这个世界判"能不能写"
    'apps.world.maintenance.MaintenanceMiddleware',     # 3. 维护模式（平时形同不存在）
]
```

为什么"解析世界"必须排在"判权限"前面？因为判权限要回答的是**"你在**这个世界**里是不是编辑"**，不先确定是哪个世界，问题本身就问不清楚。

### 4.2 `ActiveWorldMiddleware`：把"当前世界"放进上下文

每个请求进来，第一层中间件先算出"当前世界"，写进一个 `contextvars.ContextVar`，请求结束再复位：

```python
class ActiveWorldMiddleware:
    def __call__(self, request):
        world = permissions.resolve_active_world(request)
        token = permissions.set_active_world(world)   # 存进 contextvar
        try:
            return self.get_response(request)
        finally:
            permissions.reset_active_world(token)     # 请求结束复位
```

`contextvar` 是 Python 提供的"请求内全局变量"：同一时间多个请求各跑各的，互不串扰。全站所有取"当前世界"的代码都读这一个值，**所以加多世界不需要去改一堆取世界的地方**。

取当前世界的入口是 `current_world_or_none()`：如果这次请求解析过了就用解析出来的；没解析过（比如命令行、单元测试直接调用）就退回"全场第一个世界"。

### 4.3 `resolve_active_world`：当前世界怎么判

优先级是"会话里选定的 → 自己的第一个世界 → 兜底世界"：

```text
已登录用户：
  1. 会话里存了 world_id，而且是你能进的世界  → 用它
  2. 否则用 "你能进的第一个世界"（worlds_for 的第一个）
  3. 一个都没有 → 退回全场第一个世界

游客 / 未登录：
  1. 会话里存了 world_id，且这个世界存在      → 用它
  2. 否则退回全场第一个世界
```

注意两个细节：

- **会话里选的也要过一遍"你还能不能进"**。万一你被移出某个世界，旧的 `world_id` 不会硬把你带进去。
- **游客没有"自己的世界"**，所以统一落到兜底世界——因为读永远公开，写另有守门人拦着。

### 4.4 `EditPermissionMiddleware`：写请求的守门人

第二层中间件只在"写方法 + 受保护路径 + 不在白名单"三个条件都满足时才拦：

```python
PROTECTED_PREFIXES = ("/api/world/", "/api/items", "/api/view")
WRITE_METHODS = {"POST", "PUT", "PATCH", "DELETE"}
```

拦下来的三种结果，状态码和文案都不一样，前端据此决定是弹登录框还是提示权限不足：

| 情况 | 响应 | 含义 |
| --- | --- | --- |
| 还没有任何账号 | `403 {"error": "还没有账号，先完成初始化"}` | 先创建第一个账号 |
| 未登录 | `401 {"error": "请先登录再编辑", "need_login": true}` | 弹登录 |
| 登录了但无编辑权 | `403 {"error": "你在这个世界里是只读权限"}` | 只能看 |

### 4.5 写接口白名单

有些写接口**不能**要求编辑权限，否则会死锁。它们被列进 `OPEN_WRITE_PREFIXES`：

```python
OPEN_WRITE_PREFIXES = (
    "/api/world/auth/",       # 登录/注册：发生在"还没有身份"的时候
    "/api/world/presence",    # 在线心跳：只读成员也要能上报"我在线"
    "/api/world/worlds",      # 新建/切换世界：还没有自己世界的人要用
)
```

这三类请求即便未登录也会放行到视图，由视图自己再校验登录状态（比如"登录后才能新建世界"）。

## 5. 注册状态机

注册的逻辑收在 `_register_user()` 里，它返回 `(user, 错误信息, 是否成为所有者, world)`。按"数据库里有没有用户"分岔：

```text
输入：用户名、密码、（可选）邀请码、显示名
  │
  ├─ 用户名不足 3 个字符        → 报错退出
  ├─ 用户名已被占用            → 报错退出
  ├─ 密码没通过强度校验         → 报错退出
  │
  ├─ first_user = 数据库里一个用户都没有？
  │
  ├─ 不是首次 且 填了邀请码：
  │     邀请码查不到 / 已用完    → 报错退出（填错就报错，绝不因此另建世界）
  │     有效                     → 记住这个邀请码
  │
  ├─ 创建用户
  │
  ├─ 有邀请码  → 加入邀请码指向的世界，角色由邀请码决定；邀请码已用次数 +1
  ├─ 是首次安装 → 接管（或创建）第一个世界，成为 owner
  └─ 其余情况  → 自助注册：新建一个属于自己的空世界，自己当 owner
  │
  └─ 若带着 request：顺手登录，并把会话的当前世界切到这个新世界
```

用一张表概括三种典型路径：

| 情况 | 触发条件 | 结果 |
| --- | --- | --- |
| 全新安装 | 数据库无任何用户 | 第一个注册者接管第一个世界，成为所有者 |
| 受邀注册 | 已初始化 + 提供了**有效**邀请码 | 加入邀请码指向的那个世界，角色由邀请码定 |
| 自助注册 | 已初始化 + 没有邀请码 | 新建一个属于自己的空世界，成为所有者 |

> **邀请码是可选的。** 已经初始化之后，不填邀请码也能注册——系统会给你开一个属于你自己的新世界；
> 但如果你**填了**邀请码，它就必须有效，填错会直接报错，而不是悄悄给你另建一个世界。

`auth_me` 在 `POST` 时会复用同一段逻辑完成注册，`GET` 时用来回答"我是谁、要不要初始化"。

## 6. 邀请码：生成、校验与限流

邀请码存在 `InviteCode` 表里，一张邀请码描述"进哪个世界、进去是什么角色、能用几次、什么时候过期"：

| 字段 | 含义 |
| --- | --- |
| `code` | 邀请码本体（唯一） |
| `world` | 用它注册后会加入的世界 |
| `role` | 加入后的角色（`owner` / `editor` / `viewer`） |
| `max_uses` / `uses` | 最多可用次数 / 已用次数 |
| `expires_at` | 过期时间（可空 = 永不过期） |
| `created_by` / `note` | 谁建的 / 备注（便于自己记） |

有效性就一句 `is_valid()`：

```python
def is_valid(self) -> bool:
    if self.uses >= self.max_uses:                       # 次数用完
        return False
    if self.expires_at and timezone.now() > self.expires_at:  # 已过期
        return False
    return True
```

### 6.1 生成（`invite_create`）

只有 `can_admin`（所有者或超管）能发。要点：

- 角色必须是三个合法值之一，否则回退成 `editor`。
- 不指定码就随机生成：`secrets.token_urlsafe(12)[:12]`；也允许自己填（会去掉 `-` 和 `_`）。
- `max_uses` 被收进 `1..100` 之间。
- 返回里直接带一条可分享的注册链接：`/register?invite=<code>`。

### 6.2 探测限流（`auth_invite_check`）

注册页"边输边查"用的是只读接口 `auth/invite`。邀请码是**有限集合**，如果不限速，等于把码库交给别人枚举。所以设了两道闸：

| 常量 | 值 | 含义 |
| --- | --- | --- |
| `INVITE_PROBE_WINDOW` | 60 秒 | 统计窗口 |
| `INVITE_PROBE_LIMIT` | 20 次 | 每窗口、每"IP + 会话"最多探这么多次 |

限速键是 `ip + session_key`（`X-Forwarded-For` 优先，取第一个 IP）。超限返回 `429` 和 `reason: "rate_limited"`。

更重要的是**它刻意不回任何可用于枚举的信息**——只回 `valid` 与一个机器可读的 `reason`，绝不透露角色、剩余次数、是否已存在同名用户：

| `reason` | 含义 |
| --- | --- |
| `empty` | 还没填 |
| `owner_setup` | 还没有任何账号，首次注册不需要邀请码 |
| `not_found` | 这个码不存在 |
| `exhausted` | 码存在但已用完或过期 |
| `ok` | 有效 |
| `rate_limited` | 探测太频繁 |

中文文案由前端按 `reason` 映射；**真正的裁决永远是提交注册时的 `_register_user()`**，探测只是给个即时提示。

## 7. 登录、会话与 CSRF

系统里有**两套并存的入口**，各有各的用途：

| 入口 | 形式 | CSRF | 用途 |
| --- | --- | --- | --- |
| 页面路由（`/login` `/register` `/logout`） | HTML 表单 | 用 `{% csrf_token %}` | 给人直接访问的登录/注册页 |
| JSON 接口（`/api/world/auth/*` 等**写**接口） | JSON | 写方法上标 `@csrf_exempt` | 前端脚本调用 |

> JSON **写**接口（POST/PUT/PATCH/DELETE）普遍 `@csrf_exempt`：它们靠 `SameSite` Cookie 来防护，
> 不需要逐个带 CSRF token；豁免所依赖的 `SameSite=Lax` 已在 `settings.py` 里**显式**写出
> （见 7.1），不再依赖框架默认值。
>
> 只读接口（`@require_safe` 的 GET/HEAD）**不**标豁免——CSRF 中间件本就只检查不安全方法，
> 在只读视图上标 `@csrf_exempt` 纯属空转，反而误导，已全部去掉。
>
> 而**页面表单**（登录、注册、站点密码解锁）都用 Django 原生的 `{% csrf_token %}` 保护。

### 7.1 会话（Session）

登录成功后，Django 用签名的 Cookie 记住"你是谁"，关键设置：

| 设置 | 值 | 含义 |
| --- | --- | --- |
| `SESSION_COOKIE_AGE` | `60*60*24*14`（14 天） | 会话最长有效期 |
| `SESSION_SAVE_EVERY_REQUEST` | `False` | 不在每个请求都刷新到期时间（省写库） |
| `SESSION_COOKIE_SECURE` | 正式环境 `True` | 只在 HTTPS 下传输会话 Cookie |
| `CSRF_COOKIE_SECURE` | 正式环境 `True` | 同上，针对 CSRF Cookie |
| `SESSION_COOKIE_SAMESITE` | `Lax` | 只随同站请求发会话 Cookie——`@csrf_exempt` 所依赖的主防线 |
| `CSRF_COOKIE_SAMESITE` | `Lax` | 同上，针对 CSRF Cookie |

因为到期时间不会每次自动顺延，所以另有**显式续期**接口：

- `GET /api/world/auth/me` 会返回 `session_expires_at`，前端据此在快过期时提醒"续期"，而不是让人敲到一半被踢回登录页。
- `POST /api/world/auth/renew` 把到期时间往后推一轮（内部 `set_expiry(SESSION_COOKIE_AGE)`）。

会话里还存着一个关键键 `world_id`——**用户选定的当前世界**，第 4.3 节的解析逻辑就靠它。

### 7.2 登录/注册/登出接口

| 接口 | 方法 | 说明 |
| --- | --- | --- |
| `auth/me` | `GET` | 我是谁、要不要初始化、会话何时到期 |
| `auth/me` | `POST` | 注册（与 `auth/register` 同一套逻辑） |
| `auth/register` | `POST` | 注册（JSON） |
| `auth/login` | `POST` | 登录，成功后切到"属于自己的世界" |
| `auth/logout` | `POST` | 登出 |
| `auth/renew` | `POST` | 续期 |
| `auth/invite` | `GET` | 邀请码探测（带限流） |

登录后调用 `_activate_default_world()`：把会话的当前世界切成"这个用户自己的第一个世界"，
一个世界都没有才退回兜底世界。

## 8. 协作：成员与邀请码管理

协作的入口是"成员列表"，由 `collaborators` 接口产出：

```python
data = {"members": members, "viewer": viewer, "invites": []}
if viewer.get("can_admin"):
    data["invites"] = [ … ]        # 邀请码只给管理员看
```

注意最后一段：**没权限的人拿到的是"空列表"，而不是"没有这个键"**——这样前端不用写分支，
永远按"有 invites 字段"来处理。

成员管理的三个写操作，全部要求 `can_admin`：

| 操作 | 接口 | 规则 |
| --- | --- | --- |
| 发邀请码 | `POST /api/world/collaborators/invites` | 只有所有者/超管能发 |
| 作废邀请码 | `DELETE /api/world/collaborators/invites/<id>` | 只能删本世界的邀请码 |
| 改角色 / 移除成员 | `PUT`/`DELETE /api/world/collaborators/<member_id>` | 只有所有者/超管能动 |

其中有一条**关键的防呆规则**——"至少要留一个所有者"：

```python
if membership.role == ROLE_OWNER and world.memberships.filter(role=ROLE_OWNER).count() <= 1:
    return error("至少要留一个所有者")
```

无论是"把最后一个所有者降级"还是"删掉最后一个所有者"，都会被这句拦下。
没有它，一个世界就可能变成"谁也管不了"的孤儿。

## 9. 在线状态（Presence）

"谁在线"用的是**心跳**，不是长连接——前端每隔一会儿就发一次心跳，服务端记下"他最后一次露面的时间"。

判定在线的时间窗是一个类常量：

```python
class Presence(models.Model):
    ONLINE_WINDOW = 60      # 秒：60 秒内有过心跳，就算在线

    @classmethod
    def online(cls, world):
        since = timezone.now() - timedelta(seconds=cls.ONLINE_WINDOW)
        return cls.objects.filter(world=world, updated_at__gte=since)…
```

接口是 `presence`（`GET` 看谁在 / `POST` 打心跳）：

- `POST` 时若带着 `{"leaving": true}`，直接**销号**（删掉这条记录）。
  这个"我走了"由浏览器的 `navigator.sendBeacon()` 在页面隐藏时发出，
  比等 60 秒窗口自然过期要快得多。
- 否则正常心跳，顺便记录"他正在看哪份文档"（`Presence.touch(world, user, document)`）。
- 每个（世界，用户）只有一条记录（`unique_together`），心跳就是不断刷新它的 `updated_at`。

## 10. 文档版本历史与回滚

这是"改错了能找回"的那一层。核心模型是 `DocumentVersion`（一份文档的一版快照）：

| 字段 | 含义 |
| --- | --- |
| `index` | 第几版（同一文档内递增，`(document, index)` 唯一） |
| `author` / `author_name` | 作者（用户被删后仍留名字） |
| `label` | "这一版做了什么"（如"内容改动""回滚前的自动备份"） |
| `payload` | **内容快照**（文档主体、卡片正文等） |
| `summary` | 人类可读摘要（"3 个区块：…"） |
| `created_at` | 保存时间 |

### 10.1 快照什么时候产生

每次内容变化走 `touch_document()`，它做三件事：修订号 +1、刷新 `updated_at`、留一版快照：

```python
def touch_document(document, label="", author=None):
    settings_["revision"] = … + 1        # 编辑冲突保护：修订号 +1
    document.save(update_fields=["updated_at", "settings"])
    snapshot_document(document, label=label or "内容改动", author=author)
```

> 注意最后一句外面裹着 `try/except`：**版本只是"有更好"，绝不能因为它报错而挡了正文的保存。**

### 10.2 90 秒同作者合并

如果人每敲一下键盘都存一版，历史会被瞬间刷屏。所以 `snapshot_document()` 有一条合并规则：

```text
看最新的一版：
  如果  它的作者 == 当前作者
  且    距它创建不到 90 秒
  那么  不新增版本，直接「改写」这一版（更新内容、标签、摘要）

否则  新开一版：index = 上一版 index + 1
```

于是"连续打字"会合并成同一版，只有隔得够久的改动才算新的一版。

### 10.3 只留最近 30 版（MAX_VERSIONS）

```python
MAX_VERSIONS = 30

extra = document.versions.order_by("-index").values_list("id", flat=True)[MAX_VERSIONS:]
if extra:
    DocumentVersion.objects.filter(id__in=list(extra)).delete()
```

新建版本后，把排在 `MAX_VERSIONS`（30）之外的旧版一次性删掉——版本无限增长会吃满数据库。

### 10.4 摘要怎么生成

版本列表里那句"改了什么"由 `_summarize()` 按文档类型给出：

| 文档类型 | 摘要内容 |
| --- | --- |
| 卡片 | "N 个区块"，并带上前三个区块标题 |
| 时间线 | "N 个事件" |
| 地图 | "N 个标注" |
| 关系树 | "关系树" |

### 10.5 回滚

接口 `documents/<id>/versions/<index>` 的 `POST` 就是回滚，顺序很讲究：

```text
1. 先给「现在」留一版（label = "回滚前的自动备份"）   ← 关键：回滚本身也可回退
2. 取出目标版本的 payload
3. 把快照写回文档：
     · 卡片：别名 / 区块 / 正文 / 属性值 / 纪元可见性
     · 文档：名称、设置
4. 再 touch_document(label = "回滚到 vN")，把这次回滚本身也记进历史
```

> 第 1 步是这套设计里最重要的一步：**回滚之前先备份当前状态**，
> 所以"手滑回滚错了"还有救——回滚前的样子也在版本列表里。

版本历史的两个接口：

| 接口 | 方法 | 作用 |
| --- | --- | --- |
| `documents/<id>/versions` | `GET` | 列出该文档所有版本（新的在前） |
| `documents/<id>/versions/<index>` | `GET` | 看某一版的完整内容（用于预览） |
| `documents/<id>/versions/<index>` | `POST` | 回滚到这一版 |

## 12. 小结

把三件事串起来看：

1. **账号**：注册即得一个属于自己的世界（首个账号接管第一个世界）；登录用会话记住身份，会话里还记着"当前世界"。
2. **协作**：权限由五条规则决定，`can_edit`/`can_admin` 是统一的判据；写请求由中间件守门，
   作者与邀请码由所有者管理，且始终保留"至少一个所有者"。
3. **版本**：每次改动留快照，同作者 90 秒内合并，只留最近 30 版；回滚前先自动备份，所以回滚也可回退。

而"当前世界"这个贯穿全局的概念，由 `ActiveWorldMiddleware` 在请求进入时解析、存进 `contextvar`、
请求结束复位——这就是为什么加上多世界之后，取世界的代码不需要到处改。
