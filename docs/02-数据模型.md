# 数据模型

> **文档版本：Dev 1.0**
>
> 这份文档回答一个问题：**数据库里到底存了什么，它们之间是什么关系？**
> 所有字段定义都来自各 app 的模型代码（`world/models/`、`documents/models/`、`graph/models.py`、
> `maps/models.py`、`publishing/models.py` 与 `timeline/models.py`），是唯一的"真相来源"。
>
> 面向零基础读者：每个模型先给"这是什么"，字段表里每个字段再给"存什么"。
> 读完之后，你应该能对着字段名说出它的用途。

如果你还没看整体架构，先读 [01-架构总览.md](01-架构总览.md)。

## 0. 先理解两个词

在看具体的表之前，先弄懂两个基础概念：

- **模型（Model）**：用 Python 类描述的一张数据库表。类里的每个属性就是表里的一列（字段）。
  Django 的 **ORM（对象关系映射）** 负责把"操作对象"翻译成"操作数据库"，
  所以你写 Python、不写 SQL。
- **外键（ForeignKey）**：一条记录"指向"另一张表的某条记录。例如一张卡片有一个
  `world` 外键，就表示"这张卡属于那个世界"。外键就是表与表之间的"线"。

本项目把世界拆成了几十张表，但核心结构只有一条主线：
**世界（World）→ 文档（Document）→ 各种内容（卡片 / 事件 / 图层 / 关系树……）**。

## 1. 一张全局关系图

```
World（世界 = 一部作品，顶层容器）
│   owner ────────────────→ Auth.User（所有者）
│
├── memberships ──────────→ Membership（user + role）  ← 谁能进这个世界
├── invites ──────────────→ InviteCode                 ← 邀请码
│
├── types ────────────────→ EntityType ─→ PropertyDef  ← 卡片类型与它的属性定义（类型可继承）
│                              └─ parent（自引用）构成"类型族谱"
│
├── eras ─────────────────→ Era                        ← 纪元（一张世界版本）
├── calendars ────────────→ Calendar ─→ 月份 / 卫星     ← 自定义历法
│
├── documents ────────────→ Document（一棵无限嵌套的文档树）
│   │   parent ──（自引用）──→ Document                 ← 树的父子关系
│   │
│   │   当 document_type 不同，它会"长出"不同的附属内容：
│   │
│   ├──【type = card】────→ Card（一对一）             ← 卡片的别名 / 属性值 / 区块正文
│   │                         values ──引用──→ 其它 Document（引用属性、正文提及）
│   │
│   ├──【type = timeline】→ TimelineEvent（一对多）    ← 事件（年/月/日/时四级精度）
│   │                         ├─ linked_cards（多对多）→ Document
│   │                         └─ featured_card（外键）→ Document
│   │
│   ├──【type = map】─────→ MapLayer ─→ MapMarker       ← 图层与标注
│   │                         └─ card（外键）→ Document（标注指向的卡片）
│   │
│   ├──【type = familyTree】→ TreeVariant ─→ TreeNode / TreeEdge
│   │                         ├─ TreeNode.card（外键）→ Document
│   │                         └─ TreeEdge.source/target（自引用到 TreeNode）构成关系
│   │
│   ├── versions ─────────→ DocumentVersion             ← 历史快照（可预览 / 回滚）
│   └── presence ─────────→ Presence（谁正打开这份文档）
│
├── publish_logs ─────────→ PublishLog                 ← 每次发布的记录
└── presence ─────────────→ Presence                   ← 谁在线（心跳）

────────────────── 次应用 timeline（经典横向时间轴）──────────────────
TimelineItem（事件 / 纪元，扁平结构，时间 = 浮点年）
TimelineView（单例：记住最后浏览到的时间范围）
```

> **怎么读这张图**：箭头方向是"谁指向谁"。`World → Document` 表示每份文档都属于一个世界，
> 而 `Document.parent → Document` 这种"指向自己"的箭头，就是下面第 6 节要讲的**树形结构**。

## 2. 逐模型字段表

> 说明：`related_name` 是"从对面反向查我时用的名字"；`choices`（取值只能从这个列表里挑）
> 会在对应字段的"说明"里点出。

### 2.1 World（世界）

**这是什么**：最顶层的容器，一个世界就是一部作品，可以整体发布成一个维基站点。

| 字段名 | 类型 | 说明 |
| --- | --- | --- |
| `owner` | ForeignKey → User | 所有者；可空（`null`），删除用户时置空（`SET_NULL`） |
| `name` | CharField(120) | 名称，默认"新世界" |
| `slug` | CharField(16) | 短链，唯一（`unique`）；保存时若为空自动生成 |
| `description` | TextField | 简介 |
| `theme_config` | JSONField | 世界主题（模式 / 颗粒 / 字体 / 主色 / 背景） |
| `ai_enabled` | BooleanField | 是否开启 AI 功能，默认开 |
| `auto_link_enabled` | BooleanField | 是否开启名字自动识别，默认开 |
| `link_entrance_enabled` | BooleanField | 是否开启链接入口，默认开 |
| `genres` | JSONField | 题材标签（列表） |
| `is_published` | BooleanField | 站点是否已发布 |
| `published_slug` | CharField(40) | 站点短码；发布且为空时自动生成 |
| `audience` | CharField(10) | 访问范围，取值见 `AUDIENCES`，默认 `public` |
| `publish_password` | CharField(60) | 访问密码（当 `audience = password` 时用） |
| `publish_version` | PositiveIntegerField | 发布版本号，每次发布 +1 |
| `published_at` | DateTimeField | 发布于（可空） |
| `created_at` / `updated_at` | DateTimeField | 创建时间 / 更新时间（自动维护） |

### 2.2 EntityType（卡片类型）

**这是什么**：卡片的"分类"，例如"人物""地点""组织"。类型可以**指定父类型**，形成继承关系。

| 字段名 | 类型 | 说明 |
| --- | --- | --- |
| `world` | ForeignKey → World | 属于哪个世界（`related_name="types"`） |
| `name` | CharField(60) | 类型名；（世界, 类型名）联合唯一 |
| `parent` | ForeignKey → EntityType（自引用） | 父类型，可空；构成类型的"族谱" |
| `icon` | CharField(40) | 图标名 |
| `color` | CharField(24) | 颜色 |
| `position` | PositiveIntegerField | 排序用 |
| `hidden` | BooleanField | 是否从类型选择器里隐藏 |
| `created_at` | DateTimeField | 创建时间 |

### 2.3 PropertyDef（属性定义）

**这是什么**：挂在某个**类型**上的一条属性，比如"人物"类型上的"生卒年"。
值类型有七种（见第 3 节）。

| 字段名 | 类型 | 说明 |
| --- | --- | --- |
| `entity_type` | ForeignKey → EntityType | 属于哪个类型（`related_name="properties"`） |
| `name` | CharField(60) | 属性名；（类型, 属性名）联合唯一 |
| `value_type` | CharField(16) | 值类型，取值见 `VALUE_TYPES`，默认 `text` |
| `options` | JSONField | 单选 / 多选的候选（形如 `[{"label", "color"}]`） |
| `required` | BooleanField | 是否必填 |
| `default_value` | JSONField | 默认值（可空） |
| `formula` | CharField(200) | 公式（当 `value_type = formula` 时用），形如 `@[attack] * 2` |
| `description` | CharField(200) | 属性说明 |
| `position` | PositiveIntegerField | 排序用 |
| `show_on_existing` | BooleanField | 是否同步到已存在的卡片 |
| `reference_type` | ForeignKey → EntityType | 引用属性允许指向的类型（可空） |

### 2.4 Era（纪元）

**这是什么**：世界的"版本分支"或"时代"。每个纪元都从 **0 年**起算自己的一套时间。

| 字段名 | 类型 | 说明 |
| --- | --- | --- |
| `world` | ForeignKey → World | 属于哪个世界（`related_name="eras"`） |
| `name` | CharField(80) | 名称，默认"新纪元" |
| `position` | PositiveIntegerField | 顺序 |
| `length_years` | FloatField | 长度（年）；`0` 表示开放式（没有结束点） |
| `theme` | CharField(16) | 配色，取值见 `ERA_THEMES`，默认 `blue` |
| `theme_config` | JSONField | 纪元主题 |
| `icon` | CharField(40) | 图标 |
| `description` | TextField | 描述 |
| `cover` | TextField | 封面（图片 URL 或 data URL） |

### 2.5 Calendar（日历）

**这是什么**：世界的历法。可以是一年 12 个月的地球历，也可以是完全自定义的（比如 8 个月、每月 40 天）。

| 字段名 | 类型 | 说明 |
| --- | --- | --- |
| `world` | ForeignKey → World | 属于哪个世界（`related_name="calendars"`） |
| `name` | CharField(80) | 名称，默认"地球历" |
| `mode` | CharField(8) | 模式：`earth`（地球历）/ `custom`（自定义） |
| `hours_per_day` | PositiveIntegerField | 一天几小时，默认 24 |
| `months` | JSONField | 月份表，形如 `[{"name", "days"}]` |
| `moons` | JSONField | 卫星（月亮）列表 |
| `open_past` | BooleanField | 是否开放"过去"（无尽的历史） |
| `default_precision` | CharField(8) | 默认精度，取值见 `PRECISIONS`，默认 `year` |
| `is_preset` | BooleanField | 是否是预设日历 |
| `created_at` | DateTimeField | 创建时间 |

### 2.6 Document（文档）

**这是什么**：**整棵树上的一个节点**。文件夹、卡片、时间线、地图、看板、笔记……
全部都是 Document，靠 `document_type` 字段区分类型。

| 字段名 | 类型 | 说明 |
| --- | --- | --- |
| `world` | ForeignKey → World | 属于哪个世界（`related_name="documents"`） |
| `document_type` | CharField(16) | 文档类型，取值见 `DOC_TYPES`，默认 `card` |
| `name` | CharField(160) | 名称，默认"未命名" |
| `slug` | CharField(80) | 文档短链；保存时若为空自动由名称生成 |
| `parent` | ForeignKey → Document（自引用） | 父文档，可空；决定它在树里的位置 |
| `position` | PositiveIntegerField | 同级排序 |
| `era` | ForeignKey → Era | 所属纪元（可空） |
| `era_ids` | JSONField | 所属纪元 id 列表 |
| `entity_type` | ForeignKey → EntityType | 卡片类型（可空） |
| `settings` | JSONField | 各工具文档自己的状态（时间线视野、地图图层等） |
| `map_data` | TextField | 地图的整包数据，原样存取、不拆字段 |
| `preview` | JSONField | 预览用的轻量数据 |
| `cover` | TextField | 封面 |
| `icon` | CharField(40) | 页面图标 |
| `pinned` | BooleanField | 是否置顶 |
| `hidden` | BooleanField | 是否在维基中隐藏 |
| `is_published` | BooleanField | 是否包含在站点里，默认 True |
| `published_slug` | CharField(120) | 发布地址 |
| `published_version` | PositiveIntegerField | 发布版本号 |
| `published_at` | DateTimeField | 发布于（可空） |
| `listed` | BooleanField | 是否可被搜索，默认 True |
| `reveal_condition` | CharField(200) | 揭示条件（满足条件才显示） |
| `forked_from` | ForeignKey → Document（自引用） | 从哪份文档派生而来（可空） |
| `created_at` / `updated_at` | DateTimeField | 创建 / 更新时间（自动维护） |
| `deleted_at` | DateTimeField | 删除时间（可空）；非空表示在回收站里 |

### 2.7 Card（卡片）

**这是什么**：卡片文档的**正文内容**，与 Document 一对一。它存别名、属性值、区块正文。
注意：卡片类型其实在 `Document.entity_type` 和 `Card.entity_type` 上都可能存，
取值时用 `Card.effective_type()` 决定用哪个。

| 字段名 | 类型 | 说明 |
| --- | --- | --- |
| `document` | OneToOneField → Document | 与哪份文档绑定（`related_name="card"`） |
| `entity_type` | ForeignKey → EntityType | 卡片类型（可空） |
| `aliases` | JSONField | 别名列表，例如 `["The Untreated"]` |
| `values` | JSONField | 属性值，形如 `{属性id: 原始值}` |
| `blocks` | JSONField | 区块正文（富文本按块存） |
| `comments` | JSONField | 页面级评论（挂在卡片上，不在块里） |
| `body` | TextField | 正文纯文本，供搜索与自动识别用 |
| `era_mode` | CharField(10) | 纪元可见性，取值见 `ERA_MODES`，默认 `universal` |
| `era_ids` | JSONField | 生效的纪元 id 列表 |

### 2.8 TimelineEvent（时间线事件）

**这是什么**：挂在时间线文档上的一个事件，带**年/月/日/时**四级精度，可以关联若干张卡片。

| 字段名 | 类型 | 说明 |
| --- | --- | --- |
| `document` | ForeignKey → Document | 属于哪条时间线文档（`related_name="events"`） |
| `title` | CharField(160) | 名称，默认"未命名事件" |
| `precision` | CharField(8) | 精度，取值见 `PRECISIONS`，默认 `year` |
| `year` | IntegerField | 年（可以为负，表示纪元前） |
| `month` | PositiveIntegerField | 月，默认 1 |
| `day` | PositiveIntegerField | 日，默认 1 |
| `hour` | PositiveIntegerField | 时，默认 0 |
| `era` | ForeignKey → Era | 所属纪元（可空） |
| `description` | TextField | 描述 |
| `cover` | TextField | 封面 |
| `row` | PositiveIntegerField | 在第几行（横向时间轴的分道） |
| `position` | PositiveIntegerField | 排序 |
| `settings` | JSONField | 事件的零碎设置（标记、颜色等） |
| `linked_cards` | ManyToManyField → Document | 关联的卡片（多对多，`related_name="linked_events"`） |
| `featured_card` | ForeignKey → Document | "特色卡片"（可空，`related_name="featured_in_events"`） |
| `created_at` / `updated_at` | DateTimeField | 创建 / 更新时间 |

### 2.9 TreeVariant（关系树，一棵）

**这是什么**：一块关系树画布。同一批人可以有**多棵**树（不同世界线 / 不同分支视角）。

| 字段名 | 类型 | 说明 |
| --- | --- | --- |
| `document` | ForeignKey → Document | 属于哪份关系树文档（`related_name="tree_variants"`） |
| `name` | CharField(60) | 名称，默认"Main" |
| `kind` | CharField(12) | 模板，取值见 `TREE_KINDS`（family/corporate/military/royal/blank），默认 `family` |
| `position` | PositiveIntegerField | 排序，默认 1 |
| `edge_labels` | JSONField | 逐个改过关系名的覆盖表 |
| `settings` | JSONField | 设置（朝向、关系名显示模式、关系清单等） |
| `created_at` | DateTimeField | 创建时间 |

### 2.10 TreeNode（关系树上的一格）

**这是什么**：树上的一个人（可以吸附到一张卡片），或一张纯文字备注。

| 字段名 | 类型 | 说明 |
| --- | --- | --- |
| `variant` | ForeignKey → TreeVariant | 属于哪棵树（`related_name="nodes"`） |
| `card` | ForeignKey → Document | 吸附到的卡片（可空，`related_name="tree_nodes"`） |
| `name` | CharField(120) | 名称，默认"新成员" |
| `subtitle` | CharField(120) | 副标题 |
| `image` | TextField | 图片 |
| `kind` | CharField(8) | 格类型：`person`（人物）/ `note`（备注），默认 `person` |
| `note` | TextField | 备注正文（只有备注格用） |
| `generation` | IntegerField | 世代（第几代） |
| `x` / `y` | FloatField | 画布坐标 |
| `position` | PositiveIntegerField | 排序 |
| `junction` | BooleanField | 是否交汇点 |
| `deceased` | BooleanField | 是否已故 |
| `favourite` | BooleanField | 是否重点人物（纯标记） |
| `group` | CharField(60) | 分组名 |
| `group_color` | CharField(24) | 分组颜色 |

### 2.11 TreeEdge（关系树上的连线）

**这是什么**：两个人之间的一条关系。

| 字段名 | 类型 | 说明 |
| --- | --- | --- |
| `variant` | ForeignKey → TreeVariant | 属于哪棵树（`related_name="edges"`） |
| `source` | ForeignKey → TreeNode | 起点（`related_name="out_edges"`） |
| `target` | ForeignKey → TreeNode | 终点（`related_name="in_edges"`） |
| `kind` | CharField(32) | 关系种类，取值见 `TREE_EDGE_KINDS`，默认 `parent` |
| `label` | CharField(40) | 自定义关系名（留空则用模板的名字） |
| `style` | CharField(10) | 线型：空 / `dashed` / `dotted` |

> 唯一约束：`(variant, source, target, kind)` 联合唯一，避免同一棵树里出现重复的连线。

### 2.12 MapLayer（地图图层）

**这是什么**：地图上的一层，标注都挂在某一层上，整层可以显隐和调透明度。

| 字段名 | 类型 | 说明 |
| --- | --- | --- |
| `document` | ForeignKey → Document | 属于哪张地图文档（`related_name="map_layers"`） |
| `name` | CharField(60) | 名称，默认"默认" |
| `position` | PositiveIntegerField | 排序，默认 1 |
| `visible` | BooleanField | 是否显示，默认 True |
| `opacity` | FloatField | 透明度，默认 1.0 |

### 2.13 MapMarker（地图标注）

**这是什么**：地图上的一个标注，三种形态——图钉 / 区域 / 文字。

| 字段名 | 类型 | 说明 |
| --- | --- | --- |
| `document` | ForeignKey → Document | 属于哪张地图文档（`related_name="map_markers"`） |
| `layer` | ForeignKey → MapLayer | 挂在哪个图层（可空，`related_name="markers"`） |
| `kind` | CharField(8) | 形态：`pin` / `zone` / `label`，默认 `pin` |
| `name` | CharField(120) | 名称 |
| `description` | TextField | 描述 |
| `x` / `y` | FloatField | 位置（百分比，默认 50/50） |
| `points` | JSONField | 区域多边形，形如 `[[x, y], …]` |
| `color` | CharField(16) | 颜色，默认 `gold` |
| `icon` | CharField(40) | 图标 |
| `scale` | FloatField | 大小，默认 1.0 |
| `rotation` | FloatField | 旋转角度，默认 0.0 |
| `card` | ForeignKey → Document | 关联到一张卡片（可空，`related_name="marker_links"`） |
| `position` | PositiveIntegerField | 排序 |
| `created_at` | DateTimeField | 创建时间 |

### 2.14 Membership（成员资格）

**这是什么**：谁可以进入这个世界，以及他的角色。第一个注册的人自动成为 `owner`。

| 字段名 | 类型 | 说明 |
| --- | --- | --- |
| `world` | ForeignKey → World | 哪个世界（`related_name="memberships"`） |
| `user` | ForeignKey → User | 哪个用户 |
| `role` | CharField(10) | 角色，取值见 `ROLES`，默认 `editor` |
| `invited_by` | ForeignKey → User | 是谁邀请进来的（可空） |
| `created_at` | DateTimeField | 加入时间 |

> 唯一约束：`(world, user)` 联合唯一——同一个人在一个世界里只有一条成员记录。

### 2.15 InviteCode（邀请码）

**这是什么**：注册用的邀请码。有了邀请码，新用户注册后会加入它指向的世界。

| 字段名 | 类型 | 说明 |
| --- | --- | --- |
| `code` | CharField(32) | 邀请码，唯一 |
| `world` | ForeignKey → World | 指向哪个世界（可空，`related_name="invites"`） |
| `created_by` | ForeignKey → User | 谁生成的（可空） |
| `note` | CharField(120) | 备注 |
| `role` | CharField(10) | 加入后的角色，取值见 `ROLES`，默认 `editor` |
| `max_uses` | PositiveIntegerField | 最多可用几次，默认 1 |
| `uses` | PositiveIntegerField | 已用几次，默认 0 |
| `expires_at` | DateTimeField | 过期时间（可空） |
| `created_at` | DateTimeField | 创建时间 |

### 2.16 PublishLog（发布记录）

**这是什么**：每次发布留一条，记录版本、范围，以及这次动了哪些文档。

| 字段名 | 类型 | 说明 |

## 4. 三个关键设计决定

### 4.1 决定一：一切内容都是 `Document`

**是什么**：文件夹、卡片、时间线、地图、看板、笔记……**全部**用同一张 `Document` 表，
只用一个 `document_type` 字段区分。

**为什么这么做（好处）**：

- 文档树只有**一种节点**，因此可以**任意嵌套**——卡片里放文件夹、文件夹里放时间线都行。
- 所有文档**共享一套通用字段**（名字、slug、位置、发布状态、隐藏、纪元、删除时间）。
- "版本、回收站、发布"这些**横切能力写一次**，就自动作用于所有文档类型。

**代价**：`Document` 上会出现一些"只对某种类型有意义"的字段（比如只有地图才用的 `map_data`）。
这是**用一点点冗余，换巨大的统一性**，非常划算。

> **比喻**：像把所有家具都做成"标准积木块"——虽然每个块上都印了些用不到的凹槽，
> 但正因为尺寸统一，你才能把它们随便拼。如果每件家具都定做，拼接就成了噩梦。

### 4.2 决定二：类型可以继承（`EntityType.parent`）

**是什么**：`EntityType` 可以指定一个父类型，子类型**自动继承**父类型的全部属性定义。

**怎么算继承**：`EntityType.all_properties()` 沿着 `ancestry()`（从根到自己的类型链）
逐层收集属性；**子类同名属性会覆盖父类**。

**为什么这么做**：想想"人物"类型已经定义了"姓名 / 生卒年"。现在要一个更细的"王室成员"，
它**天然也是人物**，只是多了"继承顺序"。有了继承，你只需让"王室成员"把"人物"设为父类型，
再加一条新属性即可，不必把"姓名 / 生卒年"重复定义一遍。

> **比喻**：像面向对象编程里的"类继承"——`王室成员` 继承 `人物`。
> 改一处父类，所有子类都跟着变。

### 4.3 决定三：图谱连线不落库（即时计算）

**是什么**：世界图谱的**节点与连线是每次请求现场算出来的**，数据库里只存"钉住了哪些节点"
这类视图状态。连线有三个来源：

| 来源 | kind | 规则 |
| --- | --- | --- |
| 引用属性 | `reference` | 卡片上 `value_type="reference"` 的属性值 → 一条线 |
| 事件关联 | `event` | 时间线事件挂的卡片 → 一条线 |
| 正文提及 | `mention` | 卡片正文写到别的卡片名 → 一条线 |

**为什么这么做（好处）**：任意时刻的图谱**永远和数据一致**，不会出现"改了卡片但图谱还是旧的"。
**代价**：每次要重算，所以有 `MAX_NODES` / `MAX_MENTION_SCAN` 这类上限兜住性能。

> **比喻**：连线不落库，就像"计算影子"而不是"拍照存档"。
> 太阳一变，影子立刻跟着变，永远是当前的；缺点是每次都要重新算一遍。

## 5. 重要方法逐个解释

方法写在模型类里，是"最贴身的读取逻辑"。下面逐个说明**它做什么、怎么算、为什么这么写**。

### 5.1 `publish_state(document)`（模块级函数）

**做什么**：算出某份文档相对当前站点的发布状态（就是第 3.4 节那五个值之一）。

**怎么算**：判断依据是**时间**，不是版本号：

```python
def publish_state(document) -> str:
    world = document.world
    if document.hidden or not document.is_published:
        return STATE_EXCLUDED                      # 被隐藏 / 不包含 → 排除
    if not world.is_published or world.publish_version == 0:
        return STATE_UNPUBLISHED                    # 世界都没发布过
    if document.published_at is None:
        return STATE_PENDING                        # 没上过站 → 待发布
    if document.updated_at and document.updated_at > document.published_at:
        return STATE_STALE                          # 上过站，但之后又改过 → 过时
    return STATE_LIVE
```

**为什么这么做**：`published_at` 是"上次进入站点的时刻"，`updated_at` 是"最后被改的时刻"。
`updated_at` 比 `published_at` 新，就说明"发布之后你又改了它"——这正是界面上那句
"Edited since you published"。

### 5.2 `slugify_name(name, fallback)` 与 `make_slug(*seeds)`

**这是什么**：生成"短链 / 标识"的两个函数。

**`slugify_name`**：把名称变成 URL 友好的 slug。步骤是：

1. 用 Unicode 规范分解、去掉音标符号（`é` → `e`）；
2. 去掉非"字母/数字/下划线/空白/连字符"的字符；
3. 转小写、把空白和下划线换成连字符；
4. 截断到 50 字符，去掉首尾多余的连字符；
5. 如果结果为空，就回退到 `fallback`（默认 `"untitled"`）。

```python
def slugify_name(name, fallback="untitled") -> str:
    normalized = unicodedata.normalize("NFKD", name or "")
    normalized = "".join(ch for ch in normalized if not unicodedata.combining(ch))
    normalized = re.sub(r"[^\w\s-]", "", normalized, flags=re.UNICODE).strip().lower()
    normalized = re.sub(r"[\s_]+", "-", normalized)
    normalized = normalized[:50].strip("-")
    return normalized or fallback
```

> 因为保留了中文（Unicode 词字符），所以文档的 slug 可以是中文——
> 只读站点路由也因此用 `<str:slug>` 而不是 `<slug:>`。

**`make_slug`**：生成一个 **6 位十六进制**的短码（形如 `a045ca`），用作世界短链、站点地址。
做法是把传入的种子字符串用竖线拼起来，算 SHA-1，取十六进制前 6 位：

```python
def make_slug(*seeds) -> str:
    raw = "|".join(str(s) for s in seeds if s) or str(timezone.now().timestamp())
    return hashlib.sha1(raw.encode("utf-8")).hexdigest()[:6]
```

**为什么这么做**：6 位十六进制 = 16⁶ ≈ 1677 万种组合，对本项目的规模足够短又足够不撞车；
用 `seeds`（如名称 + 时间）做输入，同一名字在不同时刻也会得到不同短码。

### 5.3 `Card.resolved_values()`

**做什么**：把卡片的**原始属性值**解析成前端**直接可用**的结构。
调用的是 `normalize.resolve_card_values()`，它会：

- 把 **引用属性**从"一个 id"展开成"带名称摘要的引用对象"（前端好显示）；
- 把 **公式属性**求值（`@[attack] * 2` → 具体数字）；
- 把多选/日期等按各自规则整理。

**为什么这么做**：数据库里存的是"最原始、最省空间"的值；而前端需要的往往是"已经算好、
能直接渲染"的值。把这段转换放在模型方法里，任何写入路径拿到的结果就始终一致。

### 5.4 `Card.mention_names()`

**做什么**：返回"能被自动识别成这张卡的名字"——**主名 + 全部别名**。

```python
def mention_names(self) -> list[str]:
    names = [self.document.name]
    names += [str(a) for a in (self.aliases or []) if str(a).strip()]
    return [n for n in names if n and n.strip()]
```

**为什么这么做**：正文里可能用别名提到这张卡（比如写"Harrowdeep"而不是全名）。
把别名也交给自动识别模块，链接才连得全。`autolink.py` 就是消费这个列表的。

### 5.5 `Card.visible_in_era(era_id)`

**做什么**：判断这张卡在某个纪元里是否出现。

**规则**（对应 `era_mode` 三种取值）：

| `era_mode` | 行为 |
| --- | --- |
| `universal` | 所有纪元都可见 |
| `only` | 只在 `era_ids` 列出的纪元里可见 |
| `hidden` | 在 `era_ids` 列出的纪元里**隐藏**，其它纪元可见 |

**细节**：如果卡片没选任何纪元（`era_ids` 为空），或者查询时没指定 `era_id`，
一律当"可见"。这样"没配置"就是安全的默认行为。

### 5.6 `Calendar.month_list()` / `clamp()` / `format_date()`

**`month_list()`**：返回清洗后的月份表。自定义历没配置（或配置不合法）时，
**退回通用的 12 × 30 地球历**（12 个月、每月 30 天）。这让"还没配置历法"的极端情况也能正常显示。

**`clamp(year, month, day, hour)`**：把越界的月 / 日 / 时**收进合法范围**。
因为自定义历的每个月天数各不相同，这个函数按目标月的实际天数收窄 `day`，按时长收窄 `hour`：

```python
def clamp(self, year, month=1, day=1, hour=0):
    months = self.month_list()
    month = min(max(int(month or 1), 1), len(months))       # 月份卡进 1..月数
    max_day = months[month - 1]["days"]
    day = min(max(int(day or 1), 1), max_day)                # 日卡进 1..当月天数
    hour = min(max(int(hour or 0), 0), max(0, self.hours_per_day - 1))
    return int(year or 0), month, day, hour
```

**`format_date(year, month, day, hour, precision)`**：按**精度**输出人类可读的日期：

| 精度 | 输出示例 |
| --- | --- |
| `year` | `Year -14` |
| `month` | `Month 3, Year -14` |
| `day` | `12 Month 3, Year -14` |
| `time` | `12 Month 3, Year -14 · 05:00` |

**为什么这么做**：精度是"用户知道的详细程度"。一个只知道"哪一年"的事件，
不应该强行显示"1 月 1 日"这种编造出来的细节。

### 5.7 `Document.root_doc` / `descendants()` / `is_descendant_of()`

这三个是操作文档树的"贴身工具"：

| 方法 | 做什么 | 复杂度 |
| --- | --- | --- |
| `root_doc`（property） | 沿 `parent` 一路向上，直到没有父文档，返回树根 | 等于该节点的深度 |
| `descendants(include_self=False)` | **宽度优先**遍历整棵子树，返回所有后代（文件夹批量操作用） | 等于子树大小 |
| `is_descendant_of(other)` | 沿 `parent` 向上爬，判断 `other` 是不是自己的祖先 | 等于自己的深度 |

**`descendants` 用的是 BFS（广度优先）**：用一个队列，先放入直接子节点，
每次取出队首、记录，再把它的孩子追加到队尾。这样会一层一层地遍历完整个子树。

**为什么需要它**：删除 / 移动 / 复制一个文件夹时，要连带处理它下面**所有**文档——
`descendants()` 一次就把它们全找出来。

### 5.8 `World.to_payload()`

**做什么**：把整个世界对象打包成前端友好的 JSON 字典，包含 `id / name / slug /
description / theme / ai_enabled / auto_link_enabled / link_entrance_enabled /
genres / publish`。其中 `theme` 是"配置 + 默认值合并"后的结果（前端只读这一份），
`publish` 是 `publish_summary()` 的结果（版本、范围、各状态文档计数）。

**为什么这么做**：前端不该自己去拼默认值、也不该分几次请求拿数据。
一次 `to_payload()` 给全，既省往返、又保证前端看到的字段永远完整。

### 5.9 `DocumentVersion` 的 `MAX_VERSIONS = 30` 与"90 秒合并"

**是什么**：每次保存文档都会留一版快照，但做了**两处优化**：

1. **90 秒内同一作者的连续保存会合并成一条**。判断逻辑是：如果上一版的作者就是我，
   而且离现在不到 90 秒，就**覆盖**上一版的内容，而不是新建一版。
2. **`MAX_VERSIONS = 30`**：每份文档最多留 30 版，超出就把最旧的删掉。

```python
last = document.versions.order_by("-index").first()
if last and last.author_id == author_id and (now() - last.created_at) < 90:
    last.payload = payload          # 合并：覆盖，而不是新建
    last.save(...)
    return last
# ……否则新建一版，再裁掉超过 MAX_VERSIONS 的最旧版本
```

**为什么这么做**：打字时你几乎每敲几秒就触发一次保存。如果每次都新建一版，
历史列表会被几十条"只差一个字"的记录刷爆。90 秒合并让"一段连续编辑"变成一条记录；
30 版上限则保证历史**既可用、又不会无限膨胀**。

### 5.10 `Presence.ONLINE_WINDOW = 60`

**是什么**：在线判定的时间窗口，单位秒。

**怎么用**：`Presence.touch()` 每次"心跳"就更新自己的 `updated_at`；
`Presence.online(world)` 查"`updated_at` 在最近 60 秒内的记录"，这些就是在线的成员。

```python
@classmethod
def online(cls, world):
    since = timezone.now() - timedelta(seconds=cls.ONLINE_WINDOW)
    return cls.objects.filter(world=world, updated_at__gte=since)
```

**为什么用心跳而不是长连接**：长连接（WebSocket）需要额外的服务与依赖，维护成本高。
心跳只是"定期发一个小请求报个到"，用最朴素的方式就能算出"谁在线"，
非常适合本项目"依赖越少越好"的取舍。

## 6. 树形结构：用"自引用外键"实现无限嵌套

**这是什么**：`Document` 有一个叫 `parent` 的外键，它**指向 `Document` 自己**：

```python
class Document(models.Model):
    parent = models.ForeignKey(
        "self",                          # ← 指向自己这张表
        null=True, blank=True,           # ← 顶层文档没有父节点
        on_delete=models.CASCADE,        # ← 父被删，子跟着删
        related_name="children",         # ← 反过来查"我的孩子"用 .children
    )
```

**这样怎么就成了一棵树？** 关键在 `parent` 既能"有值"也能"为空"：

- 一份文档如果 `parent` 是空的 → 它是**树根**（顶层）；
- 一份文档如果 `parent` 指向另一份文档 → 它是那份文档的**孩子**；
- 孩子还能再有孩子 → **任意层嵌套**。

反过来，从一份文档问"我的孩子是谁"，就用 Django 给的 `related_name="children"`：
`document.children.all()`。

**举个具体例子**。下面这棵树：

```
世界设定（parent 为空 → 树根）
├── 人物（parent = 世界设定）
│   ├── 亚瑟王（parent = 人物）
│   └── 梅林（parent = 人物）
└── 时间线（parent = 世界设定）
```

在数据库里就存成四行 `Document`，各自记着自己的 `parent`：

| id | name | parent |
| --- | --- | --- |
| 1 | 世界设定 | `NULL` |
| 2 | 人物 | 1 |
| 3 | 亚瑟王 | 2 |
| 4 | 梅林 | 2 |
| 5 | 时间线 | 1 |

**为什么用这种方式，而不是"每层一张表"？**
如果每层建一张表，世界的嵌套深度一变，数据库结构就得跟着改，维护会失控。
用自引用外键，**一张表就能装下任意深度的树**，加多深都不用改表结构。

**代价与应对**：每次"往上找根"或"往下找后代"都要一条条查询，像顺着一串珠子走。
所以模型里提供了 `root_doc`（向上）、`descendants()`（向下）、`is_descendant_of()`
这些顺手的方法，把常见的遍历都包好了。

> **比喻**：这就像**俄罗斯套娃**。每个娃娃只需要记住"我套在哪个娃娃里面"
> （`parent`），你就能从中任意一个娃娃出发，一路往外拆到最外层（找根），
> 或者一路往里拆出所有更小的娃娃（找后代）。娃娃只需要一个"我在谁里面"的信息就够了。
