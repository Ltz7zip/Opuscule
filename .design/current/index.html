决策落定与 v0.2 修订

2026-10-20 你拍板了五项决策。它们不是五个独立选项，而是一组会互相放大的范围变更： P3 对等切换锁定了发布门，重建 11 种工具把原方案明确排除的产品面重新纳入 v1， Collection 与区间 Hist 又要求模型在 P0/P2 就定死。下面先给结论，再给修订后的架构、 工期与已拍板项。v0.1 已快照到 .design/history/，本文以 v0.2 为准。

#决策v0.2 落地方式主要影响
1P3 功能对等切换不再保留 P2 先切的退路；先做 parity matrix，再谈日期；增加 P3.5 对等实验室 / 两次演练 / 30 天 hypercare。发布门变窄；地图、AI、11 工具任一延期都直接推迟切换。
2重建 11 种工具不做 11 个独立文档模型；按“视图 / 卡片 / 工具页 / 块 / 资产”五类宿主重建，逐工具写对等口径。相对 v0.1 约 +18–24 人周；P3 从 12–16 周升到 21–27 周（单人）。
3新增 Collection 树Card 单一 home collection；CollectionView 承载 table/board/radar 等视图；全局 slug registry；公开站 IA 待定。P0 必须进 schema；否则 P3 每条 Collection 都要迁移。
4Era → 区间 HistHist 增加 kind=interval|curated、区间、theme/icon/cover；草稿允许空/全量，发布时才要求真子集；旧 Era 逐条 diff。样本 19 事件：11 个自动归入、3 个显式冲突、2 个无区间；必须有人工 override 清单。
5React + Tiptap + Django 6.1Django 6.1.x + DRF 3.18.x + drf-spectacular 验证；Tiptap core 只做 MIT 部分；排期含 6.2 LTS 升级。DRF 3.16 不支持 6.1；6.1 主流支持到 2027-04，P3 上线窗口紧。
工期必须先说清楚 v0.1 的 32–42 周（单人）/ 19–24 周（双人）建立在“11 工具退役”上，已经失效。 按五项决策重估：单人约 50–68 周，双人约 30–38 周，另加 P3.5 的 3–4 周切换与 hypercare； 若设计/产品与工程由同一人兼任，P0–P2 的设计量约 19–22 周会与工程叠加，P0–P2 约 36–46 周， P3 工具设计另计。这个区间不是承诺，P0 结束必须重估。

0.1 工具重建：不是 11 个 ToolDoc，而是五类宿主

旧站的 11 种工具并不共享同一种数据形态：table 的每一行本来就是 Card，board/radar 是属性视图， canvas/soundscape 是场景 payload，media 是资产，embed/dice 是正文微件。把它们统一建成 11 个 独立文档表，会把旧站 Document 万能容器原样请回来，并让 LinkIndex、 Revision、SearchDoc、Publish 四个横切面全部开分支。

工具v0.2 宿主数据落点阶段
table / board / radar / todo / dictionary视图宿主：保存的 CollectionViewCard + PropertyValue；视图只存筛选/排序/分组/列配置P2 起，P3 对等
chapter卡片宿主：长文 CardTiptap body + Collection 顺序；不另造章节表P2
canvas / soundscape工具页宿主：Card.kind=tool + CardToolstate JSONB；canvas 大 payload 单独限流/快照P3
media资产宿主：Asset + 媒体库页对象存储 + 元数据；不塞进 Card.bodyP1 上传，P3 页面
embed / dice块宿主：Tiptap 节点bookmark / dice 节点 attrs；不建独立文档P1

计数：视图 5 + 卡片 1 + 工具页 2 + 资产 1 + 块 2 = 11。旧站还有 voice / note 两个边缘类型，不在你的 11 项清单内；ADR-0007 记为默认归档，线上占比高再评估。

ADR-0007 已定 视图行默认 Card + is_auxiliary：保留链接/属性/修订，但默认不进 Collection 树、搜索与公开站。 只有 table 10k 行 / board 500 卡的基准失败时，才为该工具单开 ADR 切 ToolItem；禁止同一工具混用两种行模型。

0.2 四个必须先改的架构点

Card + Collection 单一真值

Card 只存一个 home_collection；CollectionItem 的跨集合露出 v1 不做。Collection 拥有结构，Card 拥有内容；删除集合不得 CASCADE 删卡。视图配置放 CollectionView，不放 Card.body。

Hist 是区间 + 展示

区间 Hist 必须有 start/end、theme/icon/cover、calendar_version；成员可派生，草稿允许空/全量，发布时校验真子集。旧 Era 的迁移差异（11 个自动归入、3 个显式冲突、2 个无区间）必须逐条解释。

工具的五类宿主

视图工具不建 11 张表；页面工具用 CardTool 侧表；媒体进 Asset；embed/dice 进块。新增 assets 与 tools 两个 app，禁止把工具状态塞进 Card.body。

运行时与许可证

Django 6.1.x + DRF 3.18.x；Tiptap core 只白名单 MIT 包，不依赖 Pro UI；Redis 锁 7.2 或 Valkey，MinIO 仅 dev；BlockNote 旧内容迁移保留 MPL notice。

01

执行摘要

旧站已经证明了这个产品是成立的：它能建世界、写卡片、排时间线、画关系树、发布只读 Wiki， 并且有 519 条测试。问题不在“功能不够”，而在四个地基已经和下一阶段的产品目标错位： 文档是一个万能容器、引用是请求时算出来的、数据库是单文件 SQLite、协作模型没有定义。 这四件事都不是加一个页面能解决的。

结论 走 A 路线：新仓绿地重建 + 一次性单向迁移 + 旧站只读并行。 不做旧仓原地改造，也不做长期双写。旧站冻结在 legacy-0.8.1， 新站按 P0–P3 建到功能对等后切换；切换前旧站继续对外服务，切换后保留 30 天只读回滚窗口。

保留

  • 领域语义与算法：自动识别、公式求值、发布状态、AI 变更集、存档、导入导出。
  • 视觉语言、品牌、公开站 URL 形态、中文交互文案。
  • 旧站代码作为“行为说明书”，不直接复用模型层。

重建

  • Card / EntityType / PropertyValue 一等公民。
  • LinkIndex、CardRevision、Timeline/Hist、WorldMap/MapLink、Graph。
  • 11 种工具文档按五类宿主重建（视图 / 卡片 / 工具页 / 块 / 资产）。
  • SSR 公开面 + React 工作区 + DRF API + Postgres。

退役

  • Document 万能容器、blocks 与 blocks_doc 双模型。
  • 请求时实时算图谱、SQLite、单进程扛全部。
  • FMG 整包（待地图 spike 决定）；旧 AI 凭据与会话。

一年后的验收画面

  • 新增一种实体类型不需要迁移数据库；改卡片标题，所有反链与嵌入引用同步更新。
  • 每次保存都有不可变修订；同一作者 5 分钟内的自动保存合并；恢复历史 = 新建一条修订。
  • 公开 Wiki 首屏走 SSR + 边缘缓存，游客不下载工作区大包；工作区只在登录后加载。
  • 时间线支持时间点 / 时间段与 Hist 视角；关系图、流程图共用一套图数据层。
  • 11 种工具在公开站有只读页、在工作区有对应宿主；parity matrix 无空项。
  • AI 只产出建议集，用户确认后才写库；流式请求不在页面渲染进程里跑。

02

现状审计

先把旧站当成一份“已运行的行为说明书”来读，而不是当成要修补的代码。它有很多做对的地方， 也有几处结构性的天花板。分清这两类，才知道哪些该带走、哪些该留下。

2.1 它现在是什么

维度现状含义
框架Django 6.1.1 + SQLite + Gunicorn一个依赖顶一套；单文件数据库，备份就是拷文件。
应用7 个 app：world / documents / graph / maps / publishing / timeline / ai按主题拆开，但视图与模型仍集中在 world 的 16 个 view 文件。
两张脸/w/<slug> 工作区；/s/<slug>/ 只读站点同一个进程、同一套模板与 JSON 接口。
前端无构建原生 JS，工作区 workspace.js 约 10,364 行；正文是 React + BlockNote 孤岛唯一带构建的例外；面板每帧重建 DOM。
接口/api/world/* 约 118 条路由，函数视图直接返回 JSON没有 DRF / OpenAPI / 统一序列化层。

2.2 做对了什么

  • 世界作用域是认真的。 中间件先解析当前世界，再判读/写权限；平台身份与世界角色正交。这套语义可以直接带进新站。
  • 自动识别有真功夫。 中文最长匹配、不重叠、跳过已有链接、英文复数吞并、长度 ≥5 的拉丁词才做编辑距离容错；这不是随便一个 icontains。
  • AI 变更集的方向是对的。 AI 只生成 AiChangeSet / AiChange，用户确认后才写库；流式、BYOK、工具循环都已跑通。
  • 发布状态机与公开站是完整产品。 搜索、RSS、OG 图、密码、举报、纪元页都有；公开 URL 可以直接沿用。
  • 测试覆盖了真实行为。 519 条测试里包含权限、AI、时间线、地图桥、导入导出；新站可以用它们做回归对照。

2.3 哪里卡住

结构现在怎么做的为什么到顶
Document 万能容器文件夹、卡片、时间线、地图、看板、表格都是 Document，靠 document_type 变身；附带 settings JSON 与 map_data 大字段。16 种文档类型让模型越来越像“什么都装一点”；Card 不是一等公民；每加一种类型就多一套分支与迁移。新提案的 D3 要求单表 Card + 类型注册表，旧结构无法平滑演进。
引用图是算出来的世界图谱每次请求即时算：引用属性、事件关联、正文提及三路合并；没有 LinkIndex 表。反链只能靠重算；重命名传播只能改显示文本；块级锚点不存在；大世界必然 N+1。提案 D2 要求引用行是数据，不是文本。
SQLite + 单进程单文件数据库，Gunicorn 2 worker；缓存用文件缓存；搜索靠内存过滤。开放编辑 + 并发写 + 实时中继同时出现时 WAL 不够；没有 JSONB / tsvector / 部分索引；无法水平扩展。
时间线模型事件是单点（年/月/日/时）；Era 曾是独立坐标系，0.7.0 后改成命名区间；没有 Hist 视角分支。提案要求 Timeline + Hist，Hist 是 Timeline 的非空真子集；旧模型的 Era 语义与 Hist 不同，迁移需要重新解释。
地图一张地图 = 一份 Document + 一段 FMG map_data 文本 + 图层/标注表；子地图只靠文档树 parent。没有“多张独立大地图”“子地图对应父图视口”的显式模型；FMG 整包 23 MB，升级与部署都重；提案要求 WorldMap / MapLink / 瓦片。
世界与权限World 没有 kind；只有发布读密码；共建世界、编辑密码、匿名作用域都不存在。提案的 D5 与权限矩阵要求 shared/private、Argon2 能力令牌、每次写校验；这是安全边界，不能靠前端补。
前端形态10k 行原生 JS 持有全部状态，renderPanels() 每帧重建面板；编辑器靠 is-live-embed 搬迁 React 节点。编辑器、画布、图谱都是重交互；继续在每帧重建模型上加功能，复杂度和回归成本会指数上升。提案 D4 要求公开面与工作区分家。
接口契约函数视图 + 手写 JSON；前端按字段猜；没有 OpenAPI，没有生成客户端。新站有 SSR、SPA、AI 服务、移动端多个消费者；没有契约就会在联调期互相猜字段。

重构策略

3.1 三条路线，先排除两条

A. 绿地重建新仓按提案重写；旧站冻结；一次性 ETL；对等后切换。高中（集中在切换窗口）中低：一套模型、一套前端

B 看起来最稳，但它要求新旧两套模型共享同一份内容：Card ID、LinkIndex、修订、权限、搜索索引都要双写。 对一个单人/小团队来说，这等于把“重写成本”换成“长期双维护成本”，而且两套模型的语义会越走越远。 C 的问题更直接：D2（引用图）、D3（单表 Card）、D5（冲突模型）都是横切所有模型与视图的， 在旧结构上做等于一边飞行一边换发动机。旧站已经证明这套结构能到 0.8，但它到不了提案里的 1.0。

推荐 A 路线 + 安全网：旧站打 tag legacy-0.8.1 并保持只读可回滚； 新站建到功能对等后，用一次维护窗口完成最终导出、导入、校验、DNS 切换；旧站保留 30 天只读。 这样既拿到干净地基，又不在切换前承担双写复杂度。

一句话：一套领域核心，两个交付面，四类进程，三种存储。 领域核心是模块化单体，不是微服务；进程隔离只用于长连接，不用于拆业务。

6.3 引用图：LinkIndex

class LinkIndex:
    id, world_id
    source_card_id(null), source_tool_id(null), source_node_id(null)
    source_block_id
    target_card_id(null), target_timeline_id(null)
    target_map_id(null), target_graph_id(null)
    relation(mention|embed|property_ref|timeline_ref|map_ref|graph_ref|tool_ref)
    created_at
    check(num_nonnulls(source_*) = 1)
    check(num_nonnulls(target_*) = 1)
    unique NULLS NOT DISTINCT
      (source_card_id, source_tool_id, source_node_id,
       source_block_id, target_card_id, target_timeline_id,
       target_map_id, target_graph_id, relation)
    index(target_card_id), index(target_tool_id), index(source_block_id)
  • 不用 GenericForeignKey。 源与目标都用多个可空显式外键 + check constraint，保留数据库级引用完整性；唯一约束必须 NULLS NOT DISTINCT（PG15+），否则 NULL 目标会重复。
  • 源多态： 工具（table/board/canvas）与时间节点也会产生引用；source_* 至少一个非空，不能只支持 Card。
  • 写入时机： 卡片/工具保存后由 CardSaved / ToolSaved outbox 事件触发；解析 Tiptap JSON 的 cardLink 节点、属性引用、嵌入节点，diff 出增删行。
  • 重命名传播： 只改 Card.title，不重写链接行；引用显示文本由渲染时按 target 当前标题计算，另写一条修订记录。
  • 反链： 对 target_* 索引查询；按 relation 分组；分页。
  • 巡检： 每晚抽样/全量重解析，比较 LinkIndex；不一致写审计并修复，修复动作可回滚。

关键机制

7.1 编辑器与块 schema

编辑器是 Tiptap（ProseMirror）。块 JSON 是唯一权威，服务端不解析成 HTML 再存回。 节点分三组：文本块、媒体块、引用块。每个块必须有稳定 blockId， 它同时是修订 diff、链接锚点、AI 定点编辑、评论定位的共同前提。

组节点说明
文本doc, paragraph, heading, blockquote, bulletList, orderedList, listItem, taskList, taskItem, codeBlock, horizontalRule, hardBreak, text基础排版；标题级别限制 1–3；代码块不做语法高亮也可用。
媒体image, file, callout图片走对象存储；上传后只存 asset_id + alt；callout 是自定义节点。
引用cardLink, timelineEmbed, mapEmbed, graphEmbed, toolEmbed, bookmark, dice只存实体 ID + 视图参数；渲染时按权限与当前数据加载，不复制内容。
  • 工具不入编辑器： table/board/radar/todo/dictionary 走 CollectionView 页面；canvas/soundscape 走 CardTool 页面；Tiptap 只承载 embed/dice 等微件节点，避免 11 套编辑器扩展把 schema 撑爆。
  • 校验： 服务端用同一份 JSON Schema 校验；未知节点类型拒绝保存，导入器隔离到待审区，避免 XSS 与 schema 漂移。
  • 旧数据： BlockNote 的 blocks_doc 与旧 blocks 都转到 Tiptap JSON；映射表单独维护，迁移脚本带 dry-run。
  • 自动保存： 前端 2 秒空闲防抖 + 切换/关闭强制保存；请求带 If-Match: revision；冲突返回 409 + 当前内容，前端给“保留我的 / 用服务器 / 并排看”。
  • 本地草稿： IndexedDB 存最近一次未确认内容；刷新/断网可恢复；不作为权威。

7.2 保存事务：同步写最小数据，异步做重活

1鉴权 + 世界 ACL + edit token
→
2select_for_update 锁 Card/Tool；校验 revision
→
3校验块 JSON / 工具 schema / 属性值；生成 body_text
→
4写 Card + CardRevision，或 CardTool + ToolRevision，再写 Outbox
→

  • 同步部分只做：权限、乐观锁、schema 校验、Card/PropertyValue/Revision/Outbox 等少量表写入；链接与搜索索引不在请求链路。目标 P95 < 300 ms。
  • 链接与搜索索引异步：UI 显示“链接更新中/已同步”；失败重试 + 死信；提供手动重建。
  • 幂等：请求带 request_id；重复提交返回同一 revision，不重复写修订。
  • 冲突：If-Match 不匹配返回 409，body 带当前 revision 与内容摘要；不静默覆盖。

7.3 链接同步与重命名传播

  1. 解析卡片块 JSON / 工具引用 / 时间节点关联：收集 cardLink、引用属性、嵌入节点、工具视图引用的 target。
  2. 过滤同世界、未删除、目标存在；生成 (source_kind, source_id, block, target_kind, target_id, relation) 集合；源可以是 Card / Tool / TimeNode。
  3. 与 LinkIndex 现有行做 diff：插入新增、删除消失；不 update（关系变化 = 删 + 插）。
  4. worker 记录 source_revision；若卡片已更新则重跑；写入幂等，旧事件不能覆盖新索引。
  5. 重命名不重写链接行；引用显示文本按 target 当前 title 渲染；写一条 rename 修订。
  6. 反链查询走 target_card_id / target_tool_id 索引；按 relation 分组；只返回当前用户可读对象。
  7. 每晚巡检：重解析 + 对比；不一致写审计并修复；修复记录可回滚。

7.6 缓存与发布

  • 公开页缓存键：public:{world_slug}:{published_version}:{path}；发布时版本 +1，旧键自然失效。

8.4 LinkIndex 重建

旧站的图谱是即时算的，没有现成链接表；迁移时必须主动重建。来源五路：

  1. 正文 [[名称]] 与自动识别命中的卡片名/别名（复用旧 autolink.find_mentions）。
  2. 引用属性的目标卡片。
  3. 时间事件的 linked_cards 与时间节点引用。
  4. 关系树节点的 card 引用。
  5. 地图标注的 card 引用。
  6. 工具视图/画布里的卡片引用（table 行、canvas 节点、board 卡）。

重建后与旧 build_graph 的边集合对比：差集必须能解释（例如旧图只算了已发布卡片、新图算了全部）。 不能解释的差异阻断切换。

8.5 修订迁移

1,256 条旧快照不需要全部重放。每张卡：

  • 最新 payload → 一条 snapshot_json 基线（reason=import）。
  • 最近 10 条可解析 payload → 转成 delta；解析失败的跳过并记录。
  • 更早的 → 打包进归档 zip，附索引；需要时人工取回。
  • 工具 payload → ToolRevision 基线（canvas/soundscape）；视图工具与媒体不产生独立修订。

边界

  • 所有查询强制 world 作用域；IDOR 测试。
  • 密码 Argon2；token 短时；每次写校验。
  • CSRF / SameSite / CORS 收紧。
  • Admin 2FA（TOTP）必须；旧设备重新录入。

内容

  • 块 JSON 白名单；HTML 净化；CSP。
  • 工具 payload 按 ToolKind schema 校验；canvas 不执行用户脚本。
  • 上传 MIME/大小校验；图片重编码；私有 bucket；Asset 引用计数。
  • 公开页不渲染用户原始 HTML。

密钥

  • AI key 信封加密；日志脱敏；可删除。
  • SECRET_KEY / DB / S3 凭据走环境/密钥管理。
  • 依赖审计与定期升级。

10.7 香港源站 → 内地用户

  • 香港源站不需要 ICP；一旦使用大陆 CDN 节点，接入域名必须先备案。
  • 不备案时不要盲目套全球 CDN：内地流量可能被调度到境外 PoP，反而更慢；正确做法是香港源站 + 强 SSR 边缘缓存 + CN2/GIA 线路。
  • 延迟必须实测：电信/联通/移动 × 华南/华北 × 高峰/低谷；瓶颈通常是跨境抖动与丢包，不是平均延迟。
  • 优化：SSR + 边缘缓存、首屏包极小化、工作区延迟加载、Brotli、HTTP/3、BBR、移动端降级。

10.8 运行手册（必须写下来）

  • 迁移： 导出 → 导入 dry-run → 校验 → 正式导入 → 冒烟 → 切换。
  • 回滚： DNS 切回旧站；旧库不删；新站增量导出；公告数据边界。
  • 重建索引： 清空 SearchDoc / LinkIndex 分片 → 重放 outbox / 全量扫描 → 校验。
  • 恢复修订： 选快照 → 重放 → 生成新 revision → 通知作者。
  • AI 上游故障： 明确降级文案；不静默失败；配额与重试上限。

11.4 什么时候该重新评估这个方案

  • P0 结束时，如果占位模型、编辑器迁移或权限模型超过估算 50%，先停下来复盘，不要硬推。
  • 如果 11 工具 parity 实测超过 24 人周，或设计产能没有独立预算，P3 日期必须后移，不能靠加班补。
  • 如果线上真实内容远大于本机样本（例如数万张卡、数百 GB 媒体），迁移与性能策略要重做。
  • 如果 Django 6.1 在 P3 前进入安全支持尾期，或 DRF 3.18 出现阻断问题，先升 6.2 LTS 再继续。
  • 如果公开站 Collection 化导致旧 URL/SEO 大面积失效，回到“类型分区为主、Collection 为辅助”的 IA。
  • 如果团队扩到 5 人以上、需要独立扩缩容，再考虑把 AI/地图/搜索拆成服务；不要提前微服务化。

12.3 ADR 清单
